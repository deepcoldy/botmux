# Session Adopt

Seamlessly adopt a CLI process that's **already running in tmux, Zellij, Herdr, or Orca** into botmux, so you can view progress and interact via Lark on your phone. If a CLI is halfway through a task when you have to leave, send `/adopt` from Lark and keep watching and sending.

<video src="https://magic-builder.tos-cn-beijing.volces.com/uploads/1780421531476_adopt-video.aud.mp4" controls preload="metadata" style={{width:'100%',borderRadius:'8px'}}></video>

```
/adopt              # Scan adoptable sessions and pop up a selection card
/adopt 0:2.0        # Adopt the specified tmux pane directly (session:window.pane)
/adopt orca:term_xxx # Adopt the specified Orca terminal directly
```

> The selection card lists only sessions for the **CLI this bot is bound to** (a Pi bot won't list Codex/TRAE panes), and excludes botmux's own `bmx-*` persistent sessions.

Picker headings consistently show the workspace name, while “Target” shows the backend's human-readable session locator: `session:window.pane` for tmux, `session/pane` for Zellij, and the terminal title for Orca. Orca's internal handle remains the confirm/restore key but is not shown to users.

Orca sessions use the `orca` command already available in the current environment, automatically reusing Orca's local or SSH routing without a separate pairing configuration. Web Terminal uses non-disruptive text screen snapshots: viewing and keyboard input work, while source colors, exact cursor state, and mouse modes are not preserved yet. When Botmux can bind the exact CLI process and transcript on its own host, structured final replies work as with other adopt sources; Trae, Claude Code, and Codex also reconstruct scrollable user/assistant history from that transcript.

MTR, Hermes, and other unverified CLIs currently provide basic terminal access only: the live TUI, Lark input, and Web Terminal remain available, but structured transcript replies and scrollable history are not guaranteed. This is a transcript-ownership limitation, not a terminal I/O limitation. MTR's cwd fallback can be ambiguous when several sessions share one directory, while an externally started Hermes session has no Botmux session marker. Botmux does not guess from the newest session in the same directory because that could expose another terminal's conversation.

## It's a "bridge," not a takeover

Adopt uses a **zero-touch bridge**: botmux observes and writes to the selected terminal out of band and **never changes the original terminal's focus, layout, or size**. Your local terminal and Orca UI remain unaffected.

- **Shared mode**: after adopting, the local terminal (e.g., iTerm2) and Lark sync bidirectionally — the streaming card shows terminal output in real time, and input from the Lark chat box passes straight through to the terminal. The local tmux stays connected and untouched throughout.
- **Safe disconnect**: tap "⏏ Disconnect" on the streaming card (or send `/close`), and botmux stops observing and tears down only its own side's worker — it **never ends your CLI**; the original process keeps running in your local tmux.

> ⚠️ The old "🔄 Adopt Over" button on the card is **retired**: it's no longer rendered in bridge mode, and clicking it on a historical card is a no-op. Full rebuild into a standard botmux session via `--resume` (`/adopt --takeover`) is still on the roadmap and not yet shipped. Today, adopt is always the "shared bridge" form.

## Boundaries and caveats

An adopted session's lifecycle lives **on your machine**, outside botmux's control, so a few hard boundaries apply:

- **Cannot be relayed (`/relay`)**: the CLI runs on your computer and botmux doesn't control its tmux lifecycle, so relay is rejected. To continue in another group, use a new session + handoff.
- **Cannot resume**: an adopted session doesn't support `--resume` rebuild.
- **Ends when the CLI exits**: in adopt mode botmux does **not** auto-restart — once the adopted CLI exits on its own, the session ends with it (card frozen, worker reaped) rather than respawning like a persistent session.
- **Sandbox bots can't adopt**: a sandbox has to wrap a CLI it starts from scratch and can't wrap an already-running process (fail-closed rejection).
- **Orca identity must be verifiable**: a target must expose at least an incarnation or PTY identity. Targets without stable identity are not listed or restored, preventing a reused terminal handle from receiving input.
- **Restore after a daemon restart is careful**: on restart botmux first re-validates whether the adopted host CLI is still alive — it only closes the session if the target is confirmed gone; on an inconclusive (transient) probe it keeps the session closed and **re-validates on the next restore pass (e.g. another daemon restart)**, not automatically when the next message arrives.

## Typical usage

Running Claude Code in the tmux on your office computer and have to leave halfway through? Send `/adopt` from Lark on your phone → pick the session → instant sync. Keep going on your phone on the road, and tap "Disconnect" when you're back at your computer to pick up where you left off. **It's not remote control — it's true multi-device sharing.**
