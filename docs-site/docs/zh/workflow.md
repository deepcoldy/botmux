# Workflow（实验性）

Workflow（工作流）能把一个**需要好几步才能做完**的目标，变成一张自动执行的流程图：

- bot 先一问一答帮你把需求问清楚；
- 再把需求编排成一张 **DAG**（有依赖顺序的步骤图，每一步叫一个「节点」）；
- 你确认后自动执行，能并行的步骤一起跑；
- 跑通的流程可以存成 **Saved Workflow**，下次一句命令再跑一遍。

适合「调研三家竞品出一份对比报告」「拉日志分析后生成图表」这类**有明确终点、最后交一份产出**的任务。单步问答、普通改代码不需要它；需要多个 bot 长期分工、持续协调的项目，也不适合用 Workflow。

## 先打开开关

Workflow **默认关闭**。两种方式打开（任选一种）：

- Dashboard →「全局设置 → 工作流」→ 打开 **「启用工作流功能」**；
- 设置环境变量 `BOTMUX_WORKFLOW_ENABLED=true`。

开关改完，下一个会话就生效，不用重启。设置了环境变量时以环境变量为准，Dashboard 开关不再起作用。关闭时，新建即兴流程、运行和保存 Saved Workflow、`botmux goal run` 都会被拒绝；已经在跑的 run 仍可以用 `botmux workflow cancel / retry / grant` 收尾。

## 快速上手：发起一次即兴 workflow

在飞书话题里发：

```
/workflow 调研三家竞品的定价，整理成一份对比表
```

`/workflow <目标>` 等价于 `/workflow new <目标>`。也可以直接用大白话描述多步任务，bot 会先问你一句「要不要用工作流来跑」，你同意后才开始；发 `/workflow` 则跳过这一问。

接下来全程在当前话题里进行，你只需要回答问题、点确认：

```
 ① 拷问澄清 ──▶ ② 确认需求 ──▶ ③ 自动编排 ──▶ ④ 确认流程 ──▶ ⑤ 自动执行
   (grill)       (Gate-1)       (DAG)          (Gate-2)        (并行跑节点)
```

| 步骤 | 发生什么 | 你要做什么 |
|---|---|---|
| ① 拷问澄清 | bot 一次只问一个问题，每题都附推荐答案 | 回答；觉得够了就说「用默认 / 别问了」 |
| ② Gate-1 确认需求 | bot 给出需求摘要：分几步、各自产出、验收标准、不做什么 | 确认，或指出要改的地方 |
| ③ 自动编排 | 系统把需求编成一张流程图 | 等待 |
| ④ Gate-2 确认流程 | bot 讲清楚有哪些节点、先后顺序、哪些节点要停下等你审批 | 确认就开跑 |
| ⑤ 自动执行 | 节点按依赖顺序跑，没有依赖的同时跑 | 按需处理弹出的卡片（见下节） |

想改主意时：

- 需求要改 → `botmux workflow revise-spec <runId>`，退回重新澄清，原来的流程图作废；
- 只改流程 → `botmux workflow revise-dag <runId>`，只重新编排。

运行情况可以在 **Dashboard 的「工作流」页面**看，飞书卡片上的「Web 详情（需登录）」按钮能直达这个 run。

## 跑起来以后会弹哪些卡片

| 卡片 | 什么时候出现 | 按钮 |
|---|---|---|
| 审批卡 | 标了审批的节点（比如对外发消息）**动手之前** | 「✅ 通过 / ❌ 拒绝」，也可以是自定义选项；可以限定谁能批 |
| 运行中提问 | 节点做到一半需要你拍板或补信息 | 选项题点按钮，填空题在输入框里填，提交后这一步带着答案重跑 |
| 追加循环轮次 | 返工循环跑满设定轮数还没达标 | 「➕ 追加 1 轮」；不点就停在受阻 |
| 准许回溯 | 下游把上游打回重做的次数用完了 | 「➕ 准许回溯 +1」；不点就停在受阻 |
| 受阻卡 | 节点卡住（blocked），比如产出不合要求、缺权限 | 「🔄 重试」，以新一轮重跑这个节点 |
| 进度卡 | 整个 run 的进度汇总 | 「Web 详情（需登录）」 |

这些卡片都会落盘保存，daemon 重启后还在（或重新发出），不会丢审批。

## 流程里能有哪些结构

编排出来的流程不一定是一条直线，可能包含：

- **并行**：互不依赖的节点同时跑。
- **条件分支**：某个节点给出结构化结果后，只走命中的分支，没命中的分支直接跳过、不花钱。多个上游汇合时，可以要求「全部完成 / 任一完成 / 达到法定票数」。
- **返工循环（loop）**：「改到验收通过为止」会编成一个循环节点，比如 `写代码 → 跑测试` 反复跑到测试通过。跑满上限会停下来问你要不要追加轮次。
- **自动返工（revisit）**：下游发现上游的产出有问题，可以把上游连同它的下游一起打回重做，并附上「哪里错了、为什么」。有次数上限，防止死循环：同一对节点默认 1 次，整个 run 合计 8 次。
- **对外动作节点（host 节点）**：不调用模型、只做一件确定的事。目前有三种：在群里发消息（`feishu-send`）、在话题里回复（`feishu-reply`）、建定时任务（`botmux-schedule`）。这类节点**每次都要先过审批卡**，卡上会附带即将执行的具体内容；它们不会放进循环或返工范围里，避免重复执行。

## 保存与复用（Saved Workflow）

即兴 workflow 跑完后，可以存成 Saved Workflow，以后直接运行：

| 想做什么 | 飞书里发 | 命令行 |
|---|---|---|
| 保存最近一次 run | `/workflow save last [名称]` | `botmux workflow save last [名称]` |
| 保存指定 run | `/workflow save <runId> [名称]` | `botmux workflow save <runId> [名称]` |
| 运行 | `/workflow run <名称> [key=value ...]` | `botmux workflow run <名称\|workflowId> [--param key=value ...]` |
| 列出已保存的 | `/workflow list` | `botmux workflow list [--json]` |
| 查看定义 | `/workflow show <名称>` | `botmux workflow show <名称\|workflowId>` |
| 取消正在跑的 run | `/workflow cancel <runId>` | `botmux workflow cancel <runId> [--reason <理由>]` |

使用时注意：

- **只能保存已经停下来的 run**（成功、失败或受阻都可以）。还在跑（或在等审批）时会提示你跑完再存。
- **保存的是最终生效的版本**：run 运行中改过流程的话，保存的是真正跑完的那一版，确认消息会注明改过几次。
- **保存在哪**：默认只在**本群**可见。想在当前 Bot 的其它群也能用，本人在飞书里发 `/workflow save last <名称> --global`（需要你对这个 Bot 有操作权限）。
- **参数**：即兴 run 直接保存的流程是「原样复刻」，不带参数。想把其中的具体值（比如地区、日期）抽成参数，本人在飞书发 `/workflow save last <名称> --distill`：系统先给一张参数摘要卡，你整体确认后才保存到本群。这个能力还在实验阶段，目前只支持 Linux 上、没配启动 wrapper 的 Claude Code Bot，不能和 `--global`、`--ack-unsafe` 一起用。
- **传参**：飞书里写 `key=value`，值里有空格就加引号：`key="multi word"`。命令行用 `--param key=value` 传普通值，用 `--param-json key=<json>` 传对象或数组，例如 `--param-json tags='["urgent","cn"]'`。参数适合放**业务变量**（群、开关、阈值），任务本身的要求应该写在流程里，不要整段塞进参数。
- **疑似敏感内容**：保存时如果检查出疑似密钥或本机绝对路径，会拒绝保存并列出警告。确认无误后，本人在原命令末尾加 `--ack-unsafe` 重发。`--global`、`--distill`、`--ack-unsafe` 都只能由你本人在飞书里发，bot 不会替你加。
- 想发起一个以 `run` 开头的即兴目标，写成 `/workflow new run ...`，否则会被当成运行 Saved Workflow。
- 从 Saved Workflow 启动的 run 也能在运行中修改，只影响这一次；想更新保存的定义，要再保存一次。

## 运行中用命令介入

除了点卡片，也可以用命令行操作。`runId` 是贯穿全程的编号，卡片和 Dashboard 上都能看到。这些命令多数由主 Bot 在对话里替你调用，排障时也可以手动用：

| 命令 | 作用 |
|------|------|
| `botmux workflow start <runId>` | Gate-2 批准后交给 daemon 开跑（会发飞书审批卡） |
| `botmux workflow retry <runId> [--node <id>] [--reason <理由>]` | 重跑受阻的节点 |
| `botmux workflow grant <runId> [--loop <id>]` | 给轮数用完的循环追加一轮 |
| `botmux workflow cancel <runId> [--reason <理由>]` | 取消进行中的 run |
| `botmux workflow status <runId> [--json]` | 查看当前版本、各节点状态、待确认的修改 |
| `botmux workflow edit <runId> --patch-file <文件\|-> --base <版本> [--reason <理由>]` | 运行中修改流程（见下节）；`--base` 填 `status` 读到的版本号 |
| `botmux workflow ask-human <runId> --node <id> --reason <理由>` | 把某个节点交给人决定：停下它这一轮，转为受阻并发出受阻卡 |

三种「续跑」别混用：节点受阻用 `retry`，循环轮数用完用 `grant`；**回溯次数用完只能点飞书卡片放行**，没有对应命令。

## 运行中修改流程

run 开跑后，流程还能改：加节点、删节点，改节点的目标、完成标准、产出、超时、审批和依赖，改派执行的 Bot，或者让已完成的节点重做。

**怎么改**：在主话题里告诉主 Bot 要怎么改，它会读取当前版本并提交修改。

- 每次修改生成一个新版本（第 2 版、第 3 版……）；
- 一次修改里的几项要么全部生效，要么全部不生效；
- 两人同时改时先到先得，后到的由主 Bot 读取最新版本后重新提交。

### 谁的修改要确认

| 谁提的修改 | 结果 |
|---|---|
| **发起人本人**（在主话题里让主 Bot 改） | 直接生效。唯一例外：新增或修改对外动作节点（发消息、建定时任务），要发起人在「流程修改确认」卡上点「同意」 |
| **其他群成员** | 一律发「流程修改确认」卡，发起人点「同意」才生效 |
| **主 Bot 自己根据运行情况决定**（包括定时任务触发的那一轮） | 命中下面任一条就要发起人确认，其余直接生效 |

主 Bot 自己决定的修改，以下情况需要确认：

- 用到本 run 还没批准过的 Bot（新增节点或改派）；
- 新增或修改对外动作节点；
- 去掉或放宽人工审批（去掉审批、改批准选项、改审批人；**新增**审批不用确认）；
- 扩大额度：调高循环最大轮数、把超时改长、节点总数超过最初批准时的 2 倍。

发起人本人改动时，这些情况都直接生效；用到的新 Bot 也就此算进本 run 的批准范围，之后受阻卡改派也能选到它。

<details>
<summary>细则：插话、并发修改、等待确认期间</summary>

- 「是不是发起人本人提的」，看**触发这一轮的那条消息**是谁发的。主 Bot 因运行事件或定时任务自己开始的一轮里，发起人中途插话也仍算主 Bot 自己的修改（它可能还没看到那条消息）；其他成员插话则按该成员的修改处理。排在后面的自动回合（子任务回报、另一次事件唤醒、定时任务）不算插话。
- 确认卡上会列出新增、删除、修改的节点，用到的新 Bot，以及需要确认的原因。
- 等待确认期间，涉及的节点暂停派发，其余节点照常跑；这些节点上的提问卡暂时不能作答，受阻卡暂时不能改派，先处理确认卡。
- 确认前又有别的修改直接生效时：两次修改涉及同一批节点，或待确认的内容套到新版本上会变，待确认那张卡作废，主 Bot 会说明原因；互不相关的话，待确认的修改顺延成新版本继续等，确认卡原地更新，点旧卡也算数。

</details>

### 改了正在跑的节点会怎样

| 节点当前状态 | 修改后 |
|---|---|
| 正在跑 | 这一轮作废（停掉进程或 Bot 的这一轮，之后交上来的结果不算数），按新定义重新开始 |
| 在等审批 | 审批卡作废，显示「流程已修改，本次审批作废」，按新定义重新走审批 |
| 受阻 | 只改定义时保持受阻，等重试；改派会直接在新 Bot 上重跑。之前审批通过过的，要重新审批；之前的提问卡作废，只留「🔄 按新定义重跑（需重新审批）」，点了才重新开始 |
| 还没开始 | 直接按新定义调度 |
| 已跳过 / 已取消 | 不能再改，需要的话加新节点 |
| 循环正在跑 | 不能改循环体，可以改循环的下游 |

### 已完成的节点只能重做

已完成的节点不能删、也不能改定义（下游可能已经用了它的产出），只能**重做**，或在它下游加节点。重做会连带用过它旧产出的下游一起重跑，并消耗回溯次数（和自动返工共用：同一对节点默认 1 次，整个 run 合计 8 次）。次数用完时：

- 发起人本人要求的重做：自动补足需要的次数并生效，不用再点卡片；
- 其他情况：主话题出现「追加重做额度」卡，发起人点「➕ 追加 1 次」后，让主 Bot 重新提交这次修改。旧卡点了会提示已过期。

### 在哪看版本

- **进度卡**：显示「第 N 版 · 最近修改：…」；有修改在等确认时会注明。
- **Dashboard 工作流页**：按当前生效的版本画图，新加、改过、待确认的节点有标记；「流程版本」面板列出每个版本的时间、操作人、摘要和是否经过确认。

> ⚠️ **改过流程的 run 不要降级 daemon。** 旧版本 daemon 不认识版本记录，会忽略修改、按第 1 版继续跑：可能执行已删掉的节点、按旧定义跑改过的节点，也会绕过待确认的修改。确实要降级，先取消这些 run 或等它们结束。看板上版本号大于 1 的 run 就是改过的。

## 节点交给群里的 Bot 执行（实验性，默认关闭）

默认情况下，每个节点由 daemon 临时起一个 CLI 进程执行，做完就销毁，群里看不到过程。

打开 Dashboard「全局设置 → 工作流」里的 **「节点交给群里的 Bot 执行」** 后，节点改由群里的 Bot 在自己的会话里执行，过程在群里看得见：

```
主话题（run 的发起处）
 ├─ 节点话题 A：节点卡 + 交接卡 @文档Bot ──▶ 文档Bot 干活 ──▶ botmux report 交回产出
 ├─ 节点话题 B：节点卡 + 交接卡 @代码Bot ──▶ ...
 └─ 主话题里的小活：交接卡直接回复在主话题 @某个Bot
```

- **只影响之后批准的 run**：批准时（Gate-2，或启动 Saved Workflow 时）把执行方式定下来，已经在跑的 run 按原方式跑完。
- **仍用临时进程的情况**：私聊发起的 run、没有话题根的 run，或本机关闭了[「多话题协作」](/multi-topic)时，批准结果里会说明原因。
- 拿不准，或者不希望群里多出节点话题和 Bot 之间的对话，就保持关闭。

### 谁来执行哪个节点

- 澄清需求时说「这步让文档Bot 做」，这个节点就点名给它。
- 没点名的节点，编排时从群里当前可用的 Bot（在群、在线、CLI 支持）里挑一个并写理由；拿不准就交给主 Bot。
- Gate-2 摘要会逐个列出「节点 → 执行 Bot（CLI）：理由」，点名的 Bot 用不了（不在群、离线、找不到）会标 ⚠️。要改就退回改稿。

### 两种落点：节点话题 / 主话题

| 落点 | 适合 | 样子 |
|---|---|---|
| **节点话题**（默认） | 大多数节点 | 主 Bot 在群里发一张节点卡开新话题，再在话题里发交接卡 @执行 Bot。交接卡写明要做什么、完成标准、输入（上游产物作为附件）、要交的产出、期限和交付命令；节点卡随状态就地更新 |
| **主话题** | 一步能做完的小活：汇总、改写、格式化、查一个数 | 交接卡直接回复在主话题 @执行 Bot，卡片顶部的状态行就地更新，不另开话题 |

编排时会给每个节点定好落点并写理由，Gate-2 摘要里每行都标着「主话题」或「节点话题」。批准前可以 `revise-dag` 重排，开跑后只能改还没开始的节点。

<details>
<summary>主话题落点的规则与限制</summary>

- 执行 Bot 在主话题里已有会话就接着用，没有就新开；主 Bot 自己的节点就在主会话里跑。
- 那个会话正忙时，交接先排队，排上就算接单，期限从这一轮真正开始时算；最多再等一个节点超时（至少 1 小时），一直没开始会受阻并写明原因，建议改用节点话题。
- 同一个 Bot 在主话题里只有一个会话，所以同一个 Bot 的两个主话题节点必须有先后依赖；主 Bot 自己的主话题节点也一样。另一个 run 的主话题节点交给正在忙的同一个 Bot 时，节点会受阻并说明原因。
- 主 Bot 在本群是「整群一个会话」模式时，不能用主话题落点。执行 Bot 的 daemon 版本太旧、不支持主话题交接时，节点受阻并说明原因。
- 节点进行期间，在主话题里对这个 Bot 说的话都算节点的一部分，节点被停（超时、取消、改派）时会一起停，期间并进这一轮的消息需要重发。要和它另聊，等节点结束或改用节点话题。
- 这个会话不会因此变成节点会话：技能不变，提交只在这次执行期间有效，排队期间和执行结束后提交都会被拒绝。
- Dashboard 节点详情里能看到主话题节点的交接时间和交接卡标题，方便在主话题里找到。

</details>

### 执行的 Bot 怎么交活

做完后，执行 Bot 运行：

```bash
botmux report --dispatch-root <交接消息 id> --status completed \
  --output <key>=<路径> --result-file result.json --content-file summary.md
```

- 按节点要求校验通过才算完成；不通过会列出缺什么，补齐后在同一轮重新提交即可。
- 做不了就 `botmux report ... --status blocked "原因"`，节点转为受阻，主话题发重试卡。
- 单个文件 ≤4 MiB、一次合计 ≤8 MiB；更大的产物把分支名或链接写进 `result.json`。
- 主 Bot 离线时照常提交，结果先暂存，主 Bot 上线后自动入账。
- 执行节点的会话只做这个节点：看不到工作流相关技能，也看不到再派活的技能（`botmux-orchestrate`、`botmux-handoff`）。例外是主话题里复用的已有会话，以及技能注入方式设为「全局目录」的 CLI。

### 超时、受阻和改派

- **超时**：默认 30 分钟，从接单起算。超时后转受阻，并停掉执行 Bot 当前这一轮。
- **取消**：取消工作流会停掉各节点当前这一轮，但不关闭它们的会话。
- **改派**：受阻卡上多一个「选择接手的 Bot」下拉框，列出本 run 已批准、现在仍可用的 Bot（批准时选定的，加上运行中修改加入的）。只有发起人能点「🔀 确认改派」，确认后节点交给新 Bot 重跑。要换成范围外的 Bot，让主 Bot 提交流程修改，由发起人确认。

### 主 Bot 什么时候被叫醒

主 Bot 不会盯着每个节点，只在这三种时候被唤醒：

1. 节点受阻或失败；
2. 执行 Bot 报告做不了；
3. 标了**检查点**（`checkpoint: true`）的节点完成。

被唤醒后，主 Bot 自己决定重试、改派（限本 run 已批准的 Bot）、改流程，或用 `botmux workflow ask-human` 交给人，并在话题里说明做了什么。自动重试、改派、重做都必须写理由，节点卡上显示最近一次「主 Bot 自动重试 / 改派 / 重做：理由」或「交给人决定：理由」，Dashboard 节点详情列出全部记录。

- 主会话正忙时，唤醒会等这一轮结束再单独开始一轮，不会混进别人的对话；主话题里没有在用的会话时会新开一个。
- 同一个事件只唤醒一次，daemon 重启也不会重复。
- 交给人的节点会停下显示「等人工确认」，主话题出现受阻卡（重试 / 改派 / 取消），不设超时；交给人之后，执行 Bot 再提交也不算数。

**检查点**：适合「做完这一步要看结果再决定后面怎么走」的节点。编排时会自动标，Gate-2 前也可以要求加或去掉；运行中改它直接生效。检查点完成后，依赖它的节点先暂停，等主 Bot 看完、这一轮结束再继续。主 Bot 在本机跑 Claude Code 且装了 botmux 的提交 hook（默认就是这样）时，要先确认它的 CLI 真的收下了唤醒消息，之后的结束才算数：消息还停在输入框里时界面空闲，不算这一轮结束。唤醒送不出去、主 Bot 会话被关、或等了一小时还没结束（包括一直没确认收下）时，按原流程继续，节点卡和看板会注明。检查点只在「节点交给群里的 Bot 执行」的 run 里生效。检查点后面必须至少有一个依赖它的节点：它是最后完成的节点时 run 直接结束，主 Bot 不会被叫来，所以编排、批准和运行中修改都会拒绝没有下游的检查点（去掉标记，或在后面加一个汇总节点）。

### 批准前会检查什么

每个节点的执行 Bot 必须：是本机配置的 Bot、已经在本群、daemon 在线、能和主 Bot 建立群内协作授权；普通群里它的回复模式不能是「整群一个会话」；节点不能声明目录型产出。不满足会拒绝批准并逐个列出原因。botmux **不会自动把 Bot 拉进群**。

<details>
<summary>指定工作目录：approve-dag --working-dir</summary>

`botmux workflow approve-dag <runId> --working-dir <目录>` 可以让所有节点在同一个目录里跑。节点在执行 Bot 自己的会话里跑，所以对**每个**执行 Bot（包括主 Bot）分别判断：

- **发起人能操作这个 Bot**：此刻能在它的话题里用 `/cd`（比如发起人是它的管理员），并且**人还在这个群里**。这时目录存在即可，和 `/cd`、`/repo <路径>` 一样。
- **发起人不能操作这个 Bot**（比如同事的 Bot，或发起人已经退群）：目录必须在它允许的范围内——它的默认工作目录（或 Oncall 目录），或仓库目录（`workingDir` / `workingDirs`）本身及其子目录。
- 「能不能操作」由执行 Bot 自己按它的配置、授权和群成员判断，发起人的身份会先换算到这个 Bot 的飞书应用下。
- **暂时无法确认**（身份换算或群成员查询失败、超时，某个 daemon 不在线或版本过旧，节点开始时读不到这个 run 的批准记录或事件日志）时，按「不能操作」判：范围内的目录照样能用，范围外的会被拒绝，并写明「暂时无法确认」和原因，可以稍后重试。

其他规则：

- 目录必须已经存在，不会自动创建。比较前会展开 `~`、去掉末尾 `/`、解析软链接，所以范围内指向范围外的软链接不算。
- 不满足时拒绝批准，并逐个列出「节点 → Bot：原因」。不指定时，每个 Bot 用自己的默认目录。
- 批准后目录就定下来了。执行 Bot 开会话前会按它**当时**的配置和授权再核对一次：目录没了，或发起人已不能操作它、目录又不在范围内，节点直接受阻（不会悄悄换成默认目录）。把目录加进它的配置后点「重试」，或改派给别的 Bot。主 Bot 自己执行的节点，发节点卡前先核对目录和发起人能否用 `/cd`，发起人是否还在群里要到节点开始时才核对：发起人已退群、目录又不在范围内时，卡片会先发出，节点随后受阻。
- 运行中修改带进来的新 Bot，也在它开会话时按同样规则核对。
- 主 Bot 自己在主话题执行的节点就在主会话里跑，而主会话在发 `/workflow` 时已经在它自己的目录里起来了，所以这类节点只能用主会话的目录。指定了别的目录时批准会被拒绝，提示改成节点话题、不指定目录，或指定为主会话的目录；运行中修改把节点改成这类节点（挪到主话题、改派给主 Bot、新增）、受阻卡上改派给主 Bot 时同样拒绝。主会话没固定过目录时，按主 Bot 的默认目录算。读不到主会话的目录时不在批准时拦，节点开始时再判断；批准之后主会话再 `/cd` 到别处，节点仍会在运行中受阻，按受阻卡改成节点话题或改派即可。
- 节点话题里已经有这个 Bot 在别的目录跑的会话（比如有人先 @ 过它，或 `/cd` 过），节点同样受阻；关掉那个会话后重试即可。
- 执行 Bot 的 daemon 版本比主 Bot 旧、不认识指定目录时，节点受阻并写明「版本过旧」。

</details>

### 交接带发起人身份（实验性，默认关闭）

同一区块里的另一个开关 **「交接带发起人身份」**，只对「节点交给群里的 Bot 执行」的 run 生效。

- **关闭时（默认）**：执行 Bot 用它自己的身份干活。
- **打开后批准的 run**：批准时记下发起人（即兴 run 是在 Gate-2 批准的人，Saved Workflow 是发 `/workflow run` 的人，须是本人在群里发的消息），以及发起人当时在主 Bot 上能以本人身份使用的工具（主 Bot「按触发人鉴权」里的工具）。之后每次交接，执行 Bot 如果开了「按触发人鉴权」，就以发起人本人的身份调用这些工具，范围只会比发起人在主 Bot 上更窄。

<details>
<summary>身份委托的有效范围与例外</summary>

- **只在这次交接期间有效**：run 没结束、交接没被取消/超时/重试/改派替代、节点没完成；只在本群；只给本 run 批准范围内的 Bot。节点提交结果或交接被停下时立即撤回，执行 Bot 每次调用工具都会重新核对。发起人被移出群不会打断正在跑的这一轮，从下一次交接起生效。
- **拿不到身份不会卡住流程**：照常批准、照常交接，只是不带发起人身份，原因写在批准结果和交接消息里。拿不到的情况包括：在定时任务等自动回合里批准、主 Bot 缺通讯录权限、主 Bot 没开「按触发人鉴权」、发起人已不在群里或对执行 Bot 没有对话权限、执行 Bot 不在批准范围。
- 执行 Bot 真用到需要个人授权的工具时，会提示授权（照常走 `botmux auth request`），也可以 `botmux report --status blocked` 说明需要什么权限；**任何时候都不会改用 Bot 或 owner 的身份**。
- 节点里的 Bot 再用 `botmux dispatch` 或 `botmux send --mention` 派活给本 run 批准范围内、本群的 Bot 时，身份会跟过去（只会更窄），并随这次交接一起失效；派给其他 Bot 时照常派发，但不带身份。

</details>

### 在飞书侧边栏看流程图

这种模式下，节点卡、交接卡、执行 Bot 的回复卡和回报卡，签名行右侧有一个 **「工作流 ›」** 按钮；主话题的进度卡、流程修改确认卡和「追加重做额度」卡上，原来的「Web 详情」也换成这个按钮。点开就在飞书侧边栏看到这个 run 的实时流程图（每 2 秒刷新，点节点看详情）。临时进程执行的 run 没有这个按钮。

打开后能看到什么，按身份决定（链接本身不带任何凭证）：

| 身份 | 能看到 |
|---|---|
| Dashboard 管理员 | 完整视图，和 Dashboard 详情页一样，含终端和日志入口 |
| 本群当前成员 | 精简视图：节点名、目标、负责 Bot、状态、耗时、落点链接、流程版本历史；不含终端、日志、产物内容、参数值和错误详情。退群后最多一分钟内失去访问 |
| 其他人 | 无权查看 |

群成员通过「飞书 H5 免登」确认身份。配了 H5 免登（`BOTMUX_DASHBOARD_FEISHU_H5_*`）时，群成员拿到的是「只能看工作流侧边栏」的权限，进不了 Dashboard 的其它页面。**没配 H5 免登时只有管理员能看**：按钮改为在浏览器里打开 Dashboard 的运行详情页，用已有的 Dashboard 登录查看。

## 并发上限

一个 run 里同时跑多少个节点，受三层上限约束，取最紧的那层：

| 层 | 含义 | 默认 |
|---|---|---|
| `global` | 整个 run 同时在跑的节点数 | 4 |
| `perBot` | 同一个 Bot（飞书应用）同时在跑的节点数 | 1 |
| `perCli` | 同一种 CLI（claude-code、codex…）同时在跑的节点数 | 2 |

默认值偏保守：每个节点都起一个完整的 CLI 进程，同一种 CLI 通常共用一个订阅账号，容易撞限流。按默认值，同一个 Bot 的节点是一个接一个跑的。上限按 run 计算，两个 run 同时跑时各自都能用满。

如果你的 CLI 按量计费、机器内存也够，可以在 `~/.botmux/config.json` 里放开：

```json
{
  "workflow": {
    "enabled": true,
    "concurrency": {
      "global": 16,
      "perBot": 4,
      "perCli": 2,
      "perCliById": { "claude-code": 8 }
    }
  }
}
```

- 每个字段都可选，没写的保持默认；取值为 1–64 的整数，非法值会被忽略。
- `perCliById` 按 CLI 单独设置，没列出的 CLI 用 `perCli`。
- 每次驱动 run 时重新读取，改完对下一次启动或续跑生效，不用重启 daemon。
- 节点交给群里的 Bot 执行时，只受 `global` 和 `perBot` 约束，`perCli` 不生效。
- ⚠️ 同一个 Bot 的节点都在这个 Bot 的工作目录里跑。`perBot` 大于 1 时，多个节点会同时读写同一个目录；节点要改文件的话，确认它们改的不是同一批文件，或者分给不同的 Bot。

## 限制

- 临时进程执行的节点，目前只支持这几种 CLI 的 Bot：**claude-code、codex、seed、traex、relay、minimax**。编排到其它 CLI 的 Bot 会在启动时报错。
- 对外动作节点只有 `feishu-send`、`feishu-reply`、`botmux-schedule` 三种，且一定要过审批。
- 正式运行请走飞书 `/workflow` 或 `botmux workflow start`（带审批卡）；`botmux v3 run` 只用于开发调试，没有审批卡。

## 进阶

### 底层状态机

即兴 workflow 底层是一串 `botmux workflow` 子命令推动的状态机，通常由 bot 自动调用，排障时也能手动驱动：

| 命令 | 状态流转 |
|------|----------|
| `botmux workflow new "<目标>"` | 建 run，返回 `runId` / `specPath` → `grilling` |
| `botmux workflow spec-finalize <runId>` | 校验需求文档 → `spec_ready` |
| `botmux workflow approve-spec <runId>` | Gate-1 通过 → `spec_approved` |
| `botmux workflow architect <runId>` | 编排并校验流程图 → `dag_ready` |
| `botmux workflow approve-dag <runId>` | Gate-2 通过 → `dag_approved` |
| `botmux workflow start <runId>` | 交给 daemon 开跑 |

run 的数据存放在 `~/.botmux/v3-runs`。

### 命令行无头跑一个目标：`botmux goal run`

不经过飞书、不走澄清和编排，直接让一个 Bot 在后台把一个目标做完，适合脚本或其它 agent 调用：

```bash
botmux goal run "整理 docs/ 下的过期链接，输出一份清单" --run-id docs-links-1 --json
```

| 参数 | 说明 |
|---|---|
| `<goal>` | 目标文本；也可以改用 `--goal-file <文件>` 或 `--stdin`，三者只能选一种 |
| `--run-id <id>` | run 编号；不填自动生成。想重放或续跑就自己指定 |
| `--bot <id\|name>` | 用哪个 Bot（填 App ID 或名字）；不填用 `bots.json` 里的第一个 |
| `--working-dir <目录>` | 在哪个目录跑；不填用这个 Bot 的默认工作目录 |
| `--timeout <秒>` | 总时限，最多 14370 秒；到点按取消处理。不填时按节点默认超时（30 分钟） |
| `--codex-home <绝对路径>` | 自己准备好的 Codex 配置目录（`CODEX_HOME`），这次 run 用它的凭据和配置；必须和 `--model`、`--reasoning-effort` 一起传 |
| `--model <模型>` | 这次 run 用的 Codex 模型，覆盖 Bot 和目录里的默认值 |
| `--reasoning-effort <档位>` | `low`、`medium`、`high`、`xhigh`、`max` 或 `ultra`，必须是该模型支持的档位 |
| `--json` | 结束时在 stdout 输出一行 JSON 结果（`schemaVersion` 为 `botmux.goal-run-result/v1`），含 `state`、`summary`、`artifacts`、`error`，以及 `runtime`（CLI 实际上报的模型和档位，上报了才有） |

它只有一个节点，没有审批卡，也不发飞书消息；执行方式和临时进程节点一样，所以只支持上面「限制」里列的 CLI。数据同样落在 `~/.botmux/v3-runs/<runId>`。

**指定 Codex 配置目录、模型和档位**：三个参数要一起传，只支持没有 wrapper、没开沙箱的 Codex Bot。目录必须属于当前用户、权限 0700，写真实路径（路径上不能经过软链）；`config.toml` 是 0600 的普通文件；`auth.json` 可以是指向一份共享凭据的软链，但指向的文件必须是当前用户的 0600 普通文件，且里面有凭据。有一条不满足，或模型不支持这个档位，开跑前就以 `RUN_AUTHORIZATION_FAILED` 拒绝。结束时 botmux 会比对 Codex 实际用的模型和档位：对不上返回 `GOAL_RUNTIME_MISMATCH`，一直没上报返回 `GOAL_RUNTIME_UNVERIFIED`，两种都算失败（退出码 10）。

**结果看退出码**：

| 退出码 | `state` | 含义 |
|---|---|---|
| 0 | `succeeded` | 完成 |
| 10 | `failed` | 失败 |
| 11 | `blocked` | 受阻 |
| 12 | `cancelled` | 被取消：Ctrl-C、SIGTERM 或超时 |
| 13 | `conflict` | run-id 冲突，或这个 run 正由别的进程在跑 |
| 14 | `error` | 参数错误、未开 Workflow、没配 Bot 等 |

**同一个 `--run-id` 再跑一次**，参数要和第一次完全一样（目标、`--bot`、`--working-dir`、`--timeout`、`--codex-home`、`--model`、`--reasoning-effort`）：

- 已经结束的 run：不会重跑，直接返回当时的结果和退出码。即使 `bots.json` 后来改了或删了也一样。
- 没结束的 run（比如进程崩了、机器重启）：从断点接着跑，沿用第一次定下的 Bot、目录和设置，不会按当前配置重新挑；但仍需要 `bots.json` 里有这个 Bot 的凭据。
- 另一个进程正在跑同一个 run：返回冲突（13），不会重复执行。
- 参数和第一次不一样：返回冲突（13）。要跑新目标，换一个 run-id。

### 旧版 v2 模板（已下线）

v2 模板已下线：`/template run`、`botmux workflow resume / tail / validate` 等命令会直接报错。还有旧的 `~/.botmux/workflows/*.workflow.json` 定义或历史 run，用离线工具处理：

| 命令 | 说明 |
|------|------|
| `botmux template migrate-v3 [workflowId\|path ...] [--all]` | 默认只预览；加 `--commit` 把能转换的 v2 定义存成 v3 Saved Workflow |
| `botmux template archive-runs [--commit] [--verify <archiveId\|path>]` | 扫描、归档或校验已结束的 v2 历史 run；不会执行 v2 workflow，也不直接删除历史数据 |

### 开发自测：`botmux v3 run`

`botmux v3 run <dag.json> [--max-parallel <n>] [--max-per-bot <n>] [--max-per-cli <n>]` 在本地真实的临时进程池上跑一张**手写的** v3 dag.json，审批在终端里输入 y/N，**没有飞书卡片**。三个参数只对这一次生效，覆盖上面的并发配置；`--max-per-cli` 对所有 CLI 生效，会盖过 `perCliById`。
