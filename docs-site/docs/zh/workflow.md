# Workflow（实验性）

一句话模糊目标 → 自动拷问澄清、编排 DAG、并发执行；跑通的流程可以存成 **Saved Workflow** 反复复用。run 存放在 `~/.botmux/v3-runs`，运行情况在 **Dashboard 的 v3 视图**看（每张飞书卡片都带「Web 详情」链接直达）。

> ⚠️ Workflow **默认关闭**。在 Dashboard 设置页打开「工作流功能」开关，或设置环境变量 `BOTMUX_WORKFLOW_ENABLED=true` 后才可用。关闭时即兴编排与 Saved Workflow 的运行/保存都会被拒绝，但进行中的 run 仍可用 `botmux workflow cancel / retry / grant` 管理。

## 即兴 workflow

### 怎么用

在飞书话题里直接说出你的目标，或显式发 `/workflow <目标>`（等价于 `/workflow new <目标>`）。bot 带你走一条龙，整个过程在当前话题里一问一答，你只需回答问题和点确认：

1. **拷问澄清（grill）**：bot 一次问一个问题，每个都给推荐默认答案。觉得够了随时说「用默认 / 别问了」。
2. **Gate-1 确认需求**：bot 给一份需求摘要（做哪几步、各自产出、验收标准、明确不做什么），你确认。
3. **自动编排 DAG**：系统把需求编译成一张可执行的依赖图。
4. **Gate-2 确认流程**：bot 讲清楚节点、依赖顺序、哪些节点执行期要停下等审批，你确认就开跑。
5. **并发执行**：节点按依赖顺序并发跑（默认上限见下文「并发上限」），过程中按需在本话题弹卡片（见下）。

### 运行起来后会遇到什么（人机协作）

节点跑起来后，可能在本话题弹这几类卡片等你处理：

- **审批卡**：编排时标了审批的节点（如对外发送）干活**前**弹卡，你点「✅ 通过 / ❌ 拒绝」。可自定义选项、限定谁能批。
- **运行中提问**：节点干到一半若需要你拍板或补信息，会弹卡问你——选项题（点按钮）或填空题（输入框打字），你答完它带着答案重跑这步继续。
- **追加循环轮次**：返工循环（见下）跑满设定轮数仍没达标，弹卡问你「➕ 追加 1 轮」，不点就停在受阻。
- **准许回溯**：下游把上游打回重做的次数到上限时，弹卡问你「➕ 准许回溯 +1」。
- **节点重试**：节点因契约 / 语义问题受阻（blocked）时弹卡，你点「🔄 重试」以新一轮重跑。

> 这些卡片都持久化到磁盘，daemon 重启后仍在 / 会重发，不会因重启丢审批。

### workflow 能表达什么（节点能力）

architect 自动编排时能用上这些结构，所以你在 Gate-2 看到的流程可能不是简单的直线：

- **顺序依赖 + 并发**：无依赖的节点并行跑。
- **条件分支**：某节点产出结构化结果后，下游边按结果激活——只走命中的分支，没走的分支零成本跳过；多个上游可按「全部 / 任一 / 法定票数」汇合。
- **结构化返工循环（loop）**：把「改到验收通过」建模成一个循环节点（如 `code → test` 反复跑到测试通过），到设定上限会停下问你是否追加轮次。
- **自动返工（revisit）**：下游发现上游产物不行，可把上游连同其下游一起打回重做，并带上「为什么、哪里错」的反馈；有次数上限防死循环。

### 运行中介入（CLI）

除了点卡片，也能用命令驱动（`runId` 是贯穿全程的钥匙）：

| 命令 | 作用 |
|------|------|
| `botmux workflow start <runId>` | approve-dag 后交 daemon 开跑（带飞书审批卡） |
| `botmux workflow retry <runId> [--node <id>] [--reason <理由>]` | 重跑受阻（blocked）节点；主 Bot 被运行事件唤醒时必须带 `--reason` |
| `botmux workflow grant <runId> [--loop <id>]` | 给轮数耗尽的循环追加一轮 |
| `botmux workflow cancel <runId> [--reason <text>]` | 取消进行中的 run |
| `botmux workflow status <runId> [--json]` | 查看运行中流程的当前版本、各节点状态和待确认的修改（在该 run 的主话题里用，通常由主 Bot 调用） |
| `botmux workflow edit <runId> --patch-file <文件\|-> --base <版本> [--reason <理由>]` | 运行中修改流程：一次提交一组修改，整体生效或整体拒绝；`--base` 填 `status` 读到的当前版本（通常由主 Bot 调用，见下节）；主 Bot 被运行事件唤醒时必须带 `--reason` |
| `botmux workflow ask-human <runId> --node <id> --reason <理由>` | 把节点交给人决定：停下它正在跑的这一轮，转为受阻（等人工确认），主话题出现受阻卡；只在发起人本人的回合或本 run 事件唤醒的回合里可用（通常由主 Bot 调用，见「节点交给群里的 Bot 执行」） |

改主意：需求要改 → `botmux workflow revise-spec <runId>`（退回重新澄清，原 DAG 作废）；流程要改 → `botmux workflow revise-dag <runId>`（只重编流程）。

> 三个「续跑」入口不能混用：受阻节点用 `retry`、循环轮数耗尽用 `grant`；而「回溯额度耗尽」**只能点飞书卡片放行，没有对应 CLI 命令**。

### 运行中修改流程

run 跑起来以后，流程还能改：加节点、删节点、改节点的目标 / 完成标准 / 产出 / 超时 / 审批、改依赖、改派执行的 Bot、重做已完成的节点。你只需要在主话题里跟主 Bot 说要怎么改，它会读取当前版本、提交修改。每次修改都会生成一个新版本（第 2 版、第 3 版……），一次修改里的几项要么全部生效，要么全部不生效。两个人同时改时先到先得，后到的那次由主 Bot 读取最新版本后重新提交。

**谁能改、什么时候要确认**

- **发起人本人**在主话题发消息让主 Bot 改的：直接生效。唯一的例外是新增或修改对外动作节点（如发飞书消息、建定时任务这类 host 节点），会在主话题发「流程修改确认」卡，等发起人自己点「同意」。
  - 用到本 run 还没批准过的 Bot 也直接生效，这个 Bot 就此算进本 run 的批准范围，之后受阻卡改派也能选到它。
  - 去掉或放宽人工审批、调高循环的最大轮数、把超时改长、节点总数超过最初批准时的 2 倍，都直接生效。
- **其他群成员**提的修改：一律转成「流程修改确认」卡，等发起人点「同意」或「拒绝」，确认前不生效。
- **主 Bot 自己根据运行情况决定的修改**（包括定时任务触发的那一轮）：命中下面任意一条就要等发起人确认，其余直接生效：
  - 用到本 run 还没批准过的 Bot（新增节点或改派）；发起人同意后，这个 Bot 同样算进批准范围；
  - 新增或修改对外动作节点；
  - 去掉或放宽人工审批：去掉审批、改批准选项、改审批人（新增审批不需要确认）；
  - 扩大额度：调高循环的最大轮数、把超时改得比原来长、节点总数超过最初批准时的 2 倍。

谁算「发起人本人提的」，以触发这一轮的那条消息的发送者为准。主 Bot 因运行事件或定时任务自己开始的那一轮，中途发起人插话也仍算主 Bot 自己决定的修改（插话那条消息它可能还没看到）；其他成员插话则按该成员提的修改处理。排在这一轮后面的自动回合（子任务回报、另一次事件唤醒、定时任务）不算插话。确认卡上列出新增、删除、修改的节点、用到的新 Bot 和需要确认的原因。等待确认期间，修改涉及的节点暂停派发，其余节点照常跑；这些节点上的提问卡暂不能作答、受阻卡暂不能改派，先处理确认卡。确认之前又有修改直接生效时：两次修改涉及同一批节点，或待确认的修改套到新版本后内容会变、已无法生效，待确认的那张卡作废，主 Bot 会说明原因；互不相关，待确认的修改顺延成新版本继续等确认，确认卡原地更新，点旧卡也算数。

**改了正在跑或在等审批的节点会怎样**

- **正在跑的节点**：当前这一轮作废（停掉正在执行的进程或 Bot 的这一轮，它之后交上来的结果不再算数），按新定义重新开始。
- **在等审批的节点**：这张审批卡作废，冻结为「流程已修改，本次审批作废」，按新定义重新走审批。
- **受阻的节点**：只改定义时节点保持受阻，等之后重试；改派会直接让它在新 Bot 上重跑。如果它的审批之前已经通过，改了定义后要重新审批：重试或改派时会先发新的审批卡，批准后才执行。它之前弹出的提问卡也会作废，卡上只留「🔄 按新定义重跑（需重新审批）」，点了才会重新走审批，不点不会自动开始。
- **还没开始的节点**：直接按新定义调度。
- 跳过、已取消的节点不能再改，需要的话加新节点；循环运行中不能改它的循环体，可以改循环的下游。

**已完成的节点只能重做**

已完成的节点不能删、也不能改定义（下游可能已经用了它的产出），只能重做，或在它下游加节点。重做会连带用过它旧产出的下游一起重跑，并消耗回溯额度（与自动返工共用：同一个节点默认 1 次，整个 run 合计 8 次）。额度用完时：

- 发起人本人提的重做：自动补足所需的额度并生效（一次重做几个节点就补几次），记为发起人本人追加，不用再点卡片。
- 其他情况（主 Bot 自己决定的重做，或这次修改还要等确认）：主话题会出现「追加重做额度」卡，发起人点「➕ 追加 1 次」后，让主 Bot 重新提交这次修改即可。同一次用完只发一张卡；之后额度又用完会发新卡，旧卡点了会提示已过期。

**怎么看版本**

- **进度卡**：显示「第 N 版 · 最近修改：…」；有修改在等确认时，会注明「第 N 版待发起人确认，涉及的节点暂停派发」。
- **看板（Dashboard v3 视图）**：按当前生效的版本出图，新加、改过、待确认的节点有标记；「流程版本」面板列出每个版本的时间、操作人、摘要和是否经过确认。

**保存成 Saved Workflow**

`/workflow save last` 保存的是 run **最终生效的版本**，也就是真正跑完的那份流程；保存确认卡上会注明这个 run 在运行中修改过几次。从 Saved Workflow 启动的 run 也能运行中修改，只影响这个 run；想更新已保存的定义，要再保存一次。

**两种执行方式都支持**

节点由临时进程执行，还是交给群里的 Bot 执行（见下节），都能运行中修改。交给群里 Bot 的节点改了定义或改派时，会在原来的位置发新的交接，注明要求已修改。

> ⚠️ **改过流程的 run 不要降级 daemon。** 版本记录不在旧版本 daemon 认识的范围内，降级后它会忽略这些修改、按第 1 版继续跑：可能执行已经删掉的节点、按旧定义跑改过的节点，也会绕过还在等确认的修改。确实要降级，先把这些 run 取消，或者等它们结束再降级。看板上版本大于 1 的 run 就是改过流程的。

### 节点交给群里的 Bot 执行（实验性，默认关闭）

默认情况下，每个节点由 daemon 起一个临时 CLI 进程执行，做完就销毁。Dashboard「全局设置 → 工作流」里紧挨「启用工作流功能」有一个实验性开关 **「节点交给群里的 Bot 执行」**，打开后：

- **只影响之后批准的 run**：Gate-2 批准（或 Saved Workflow 启动）时把执行方式写进 run 冻结，已经在跑的 run 按原方式跑完。
- **每个节点开一个节点话题**：主 Bot 在群里发一张节点卡作为新话题（不 @ 任何人），再在话题里发交接卡 @ 执行这个节点的 Bot（没指派时就是主 Bot 自己）。交接卡写明要做什么、完成标准、输入（上游产物会作为附件放进它的会话）、要交的产出、期限和交付命令；节点卡会随状态就地更新（交接中 / 进行中 / Bot 已停下未提交 / 已完成 / 已停下及原因 / 已取消）。
- **按结构化产物判定完成**：执行的 Bot 做完运行 `botmux report --dispatch-root <交接消息 id> --status completed --output <key>=<路径> --result-file result.json --content-file summary.md`，按节点契约校验通过才算完成；不通过会列出缺什么，补齐后在同一轮重新提交即可。做不了就 `--status blocked "原因"`，节点转受阻，在主话题发重试卡。单个文件 ≤4 MiB、一次合计 ≤8 MiB，更大的产物请把分支名或链接写进 result.json。
- **执行节点的会话只做这个节点**：它看不到工作流相关技能，也看不到把活再派给别的 Bot 的技能（`botmux-orchestrate`、`botmux-handoff`），用 `botmux skill show` 读取也会被拒绝。两种情况例外：在主话题交接时复用的已有会话（启动时已经加载了这些技能），以及技能注入方式设为「全局目录」的 CLI（技能文件在本机共享目录里，无法按会话区分）。
- **超时与取消**：节点超时（默认 30 分钟，从接单起算）转受阻并停掉执行 Bot 当前这一轮；取消工作流同样会停掉各节点当前这一轮，不关闭它们的会话。
- **何时仍用临时进程**：私聊发起的 run、没有话题根的 run，或本机关闭了「多话题协作」时，批准结果里会说明原因并照旧用临时进程。
- **批准前检查**：每个节点的执行 Bot 必须是本机配置的 Bot、已在本群、daemon 在线，并能和主 Bot 建立群内协作授权；普通群里它的回复模式不能是「整群一个会话」（chat / shared，节点话题会并进群会话）；节点不能声明目录型产出。不满足会拒绝批准并逐个列出原因。botmux 不会自动把 Bot 拉进群。
- **指定工作目录（`approve-dag --working-dir <目录>`）**：节点在执行 Bot 自己的会话里跑，所以这个目录必须在每个执行 Bot（包括主 Bot 自己）配置的目录范围内：它的默认工作目录（或 Oncall 模式的目录），以及仓库目录（`workingDir` / `workingDirs`）这几个目录本身或它们下面。目录必须已经存在（不会自动创建）；比较前会展开 `~`、去掉末尾的 `/`、解析软链接，所以范围内指向范围外的软链接不算；指定的是软链接时，实际用的是它指向的目录（之后再改这个链接，不影响这个 run）。有节点的执行 Bot 不允许这个目录（或者它根本没配目录），就拒绝批准并逐个列出「节点 → Bot：原因」。不指定时，每个 Bot 照常用自己的默认目录。
  - 批准时目录冻结进 run；执行 Bot 起节点会话前，会按它**当时**的配置再核对一次。批准后它的配置改了、目录不在范围内了，这个节点直接受阻并写明原因（不会悄悄改用它的默认目录），把目录加进它的默认工作目录或仓库目录后点「重试」，或改派给别的 Bot。
  - 运行中修改带进来的新 Bot（改派、新增节点）不在批准时检查，同样在它起会话时按这条规则核对。
  - 节点话题里已经有这个 Bot 的会话、但它在别的目录跑（比如有人先在话题里 @ 过它，或 `/cd` 过），节点同样受阻，不会把任务交给那个会话；关掉那个会话后重试即可。
  - 执行 Bot 的 daemon 版本比主 Bot 旧、不认识指定目录时，不发交接，节点受阻并写明「版本过旧」；升级后重试，或改派。
- **主 Bot 离线时**：执行 Bot 照常提交，结果先暂存，主 Bot 上线后自动入账。
- **谁执行哪个节点**：澄清需求时说「这步让文档Bot 做」，会记成该节点的点名（`assignee`），编排时照用；没点名的节点由编排按群里当前可用的 Bot（在群、在线、CLI 支持）挑一个并写一句理由，拿不准就交给主 Bot。Gate-2 摘要逐个列出「节点 → 执行 Bot（CLI）：理由」，点名的 Bot 用不了（不在群、离线、找不到同名 Bot）会标 ⚠️。要改就退回改稿后改点名。
- **受阻卡上的「改派」**：节点受阻时，受阻卡多一个「改派」下拉框，列出本 run 已批准、现在仍可用的 Bot（批准时选定的，加上运行中修改加入的：发起人直接改入的，或发起人在修改确认卡上同意加入的）；只有发起人能确认改派，确认后节点以新 attempt 交给新 Bot。要换成范围外的 Bot，请让主 Bot 提交流程修改，由发起人在修改确认卡上确认。节点有待确认的修改时，先处理修改确认卡再改派。

- **主 Bot 按事件被唤醒**：只在三种时候唤醒主 Bot——节点受阻或失败、执行 Bot 报告做不了、标了检查点（`checkpoint: true`）的节点完成；其他节点完成不会唤醒它。主 Bot 在主话题里收到一轮，看完情况后自己重试、改派（本 run 已批准的 Bot 内）、改流程，或交给人，并在话题里说明做了什么。主会话正忙时，唤醒先在 daemon 侧等这一轮结束，再作为独立的一轮开始，不会混进别人正在进行的那一轮；主话题里没有在用的会话时，在主话题里开一个新会话（与有人在话题里发消息一样），不会恢复被关掉的会话。同一个事件只唤醒一次，daemon 重启也不会重复。
- **每次都写明理由**：主 Bot 被唤醒后的自动重试、改派、重做必须带 `--reason`；交给人用 `botmux workflow ask-human <runId> --node <id> --reason <理由>`。不限次数，什么时候交给人由主 Bot 判断（反复失败、拿不准、需要人提供信息或取舍等）。节点卡上显示最近一次「主 Bot 自动重试 / 改派 / 重做：理由」或「交给人决定：理由」，看板节点详情列出全部记录。交给人时节点停下、显示「等人工确认」，主话题出现受阻卡（重试 / 改派 / 取消），不另设超时；决定落盘后执行 Bot 再提交也不算数。已交给人的节点不会再因为之前的受阻唤醒主 Bot。
- **检查点**：编排时会给「做完这一步要看结果再决定后面怎么走」的节点标 `checkpoint: true`，Gate-2 前也可以要求加上或去掉；运行中用流程修改的 `updateNode` 改它，直接生效，不会作废正在跑的执行。检查点节点完成后，依赖它的节点先暂停，主 Bot 看完结果、这一轮结束后再继续（这一轮里它可以改后面的流程）。几个检查点同时完成时，主 Bot 一次看一个，每个在自己那一轮结束后才放行。唤醒送不出去、主 Bot 的会话中途被关掉或 CLI 停了、或等了一小时还没结束时，按原流程继续，节点卡和看板会注明。检查点只在「节点交给群里的 Bot 执行」的 run 里生效；run 已经结束时不再暂停任何节点。

拿不准、或群里不希望多出节点话题和 Bot 之间的对话时，保持关闭。

#### 交接带发起人身份（实验性，默认关闭）

同一区块里紧挨着的另一个开关 **「交接带发起人身份」**，只对上面「节点交给群里的 Bot 执行」的 run 生效：

- **关闭时（默认）**：子 Bot 用它自己的身份执行，和没有这个开关时完全一样。
- **打开后批准的 run**：批准时冻结发起人（即兴 run 是在 Gate-2 批准的人，Saved Workflow 是发 `/workflow run` 的人，须是本人在群里发的消息）和发起人当时在主 Bot 上能以本人身份使用的工具（主 Bot「按触发人鉴权」里的工具）。之后每次交接都由主 Bot 按这份记录单独签一份委托；子 Bot 开了「按触发人鉴权」时，就以发起人本人的身份执行这些工具。委托只能比发起人在主 Bot 上的范围更窄，也不会因为某个节点的回报而传给下一个节点。
- **委托只在这些范围内有效**：这次交接还在进行（run 没结束，没有被取消、超时、重试、改派替代，节点也还没完成），本群，以及本 run 批准范围内的 Bot（批准时选定的，加上运行中修改由发起人直接改入或在修改确认卡上同意加入的，发起人本人改派到的也算；别人提出、还没确认的修改不算）。节点提交结果、或交接被停下时，立即撤回子 Bot 这一轮已拿到的身份；子 Bot 每次调用这些工具也都会重新核对，即使停止信号没送到也会拒绝。发起人被移出群不会打断已经在跑的这一轮，在下一次发布身份时生效。
- **身份只在真正要用时才要，不会提前卡住**：拿不到发起人身份时照常批准、照常交接，只是不带发起人身份，原因写在批准结果和交接消息里。拿不到的情况包括：在定时任务等自动回合里批准、主 Bot 缺通讯录权限或查询失败、主 Bot 没开「按触发人鉴权」、发起人已不在群里或对子 Bot 没有对话权限、子 Bot 不在批准范围。子 Bot 那边的校验暂时跑不了时，会先在约 1 分钟内自动重试几次。子 Bot 真正用到需要个人授权的工具时会被拒绝并提示授权（缺个人授权时照常走 `botmux auth request`），它可以用 `botmux report --status blocked` 说明需要什么权限，由主 Bot 交给人处理；任何时候都不会改用 Bot 或 owner 的身份。
- **节点里的 Bot 再派活**：用 `botmux dispatch` 或 `botmux send --mention` 派给本 run 批准范围内、本群里的 Bot 时，发起人身份会跟着过去（只能更窄），并随这个节点的这次交接一起失效；派给其他 Bot 时照常派发，只是不带发起人身份。接收方会话如果把身份存在文件里、不能每次调用时重新核对，转派过来的身份不会发给它，需要个人授权的工具会直接提示拒绝原因。

#### 在飞书侧边栏看流程图

这种模式下的任务消息——节点卡、交接卡、执行 Bot 在节点话题里的回复卡和回报卡——签名行最右侧有一个「工作流 ›」按钮；主话题里的进度卡、流程修改确认卡和「追加重做额度」卡，原来的「Web 详情（需登录）」也换成同一个按钮。点开在飞书侧边栏看这个 run 的实时流程图（竖排，每 2 秒刷新，点节点展开详情）。临时进程执行的 run 和普通会话的卡片没有这个按钮；Dashboard 地址确定不了时也不出按钮。

链接本身不带任何凭证，打开时按身份决定能看到什么：

- **Dashboard 管理员**：完整视图，和 Dashboard 详情页一样，含终端和日志入口。
- **本群当前成员**：精简视图，只有节点名、目标、负责 Bot、状态、耗时、落点链接，以及流程版本历史（运行中改过流程时出现：已生效的每个版本的版本号、时间、谁改的——主 Bot / 发起人 / 其他成员、改动摘要、是否经过发起人确认；不含修改说明，也不显示还在等确认的修改）；不含终端、日志、产物内容、参数值和错误详情。是否在群由主 Bot 实时核对，退群后最多一分钟内失去访问。
- **其他人**：无权查看。

群成员靠「飞书 H5 免登」确认身份，不另加开关：配了 H5 免登（`BOTMUX_DASHBOARD_FEISHU_H5_*`）时，不在免登名单里的成员也能打开，但只拿到「只能看工作流侧边栏」的会话，进不了 Dashboard 的其它页面。免登名单里的人在 Dashboard 里本来就看不到运行详情，侧边栏里同样按群成员给精简视图。

**没配 H5 免登时只有管理员能看**：侧边栏是独立的浏览器环境，带不过去 Dashboard 的登录态，所以这时按钮改为在浏览器里打开 Dashboard 的运行详情页（和原来进度卡上的「Web 详情」一样），用已有的 Dashboard 登录查看。

### 并发上限

一个 run 里同时跑的节点数受三层上限约束，三层同时生效，取最紧的那层：

| 层 | 含义 | 默认 |
|---|---|---|
| `global` | 整个 run 同时在跑的节点数 | 4 |
| `perBot` | 同一个 bot（飞书应用）同时在跑的节点数 | 1 |
| `perCli` | 同一种 CLI（claude-code / codex…）同时在跑的节点数 | 2 |

默认值偏保守：每个节点都会起一个完整的 CLI 进程，同一种 CLI 通常也共用一个订阅账号，容易撞限流。按默认值，同一个 bot 上的节点是串行的。注意上限是按 run 计算的，两个 run 同时在跑时，各自都能用满自己的上限。如果你的 CLI 走按量计费的 API、机器内存也够，可以在 `~/.botmux/config.json` 里放开：

```json
{
  "workflow": {
    "enabled": true,
    "concurrency": {
      "global": 16,
      "perBot": 4,
      "perCli": 2,
      "perCliById": { "claude-code": 8 }
    }
  }
}
```

- ⚠️ 同一个 bot 的节点都在这个 bot 的工作目录（`workingDir`）里执行。`perBot` 大于 1 时，多个节点会同时读写同一个目录。如果节点会改代码或文件，请确认它们改的不是同一批文件，或者给不同节点分配不同的 bot。
- 每个字段都可选，没写的字段保持默认值；取值为 1–64 的整数。非法值读取时会被忽略，之后在 Dashboard 改 workflow 设置时会被清掉。
- `perCliById` 按 CLI 类型单独设置，没列出的 CLI 用 `perCli`。
- 每次驱动 run 时都会重新读取配置，改完对下一次启动或续跑生效，不需要重启 daemon。
- 节点交给群里的 Bot 执行时（`nodeExecutor: "bot"`），只受 `global` 和 `perBot` 约束，`perCli` 不生效。

### 限制

- 即兴 workflow 的节点目前只能用 **claude-code / codex / seed** 三种 CLI 的 bot；编排到其它 CLI 的 bot 会在启动时报错。
- `host` 节点（feishu-send 等不走 LLM 的确定性副作用节点）schema 里保留了，但目前未启用——一切产出由 `goal`（LLM）节点完成。
- `botmux workflow start` 才是带飞书审批卡的正式跑法；`botmux v3 run` 是开发态终端路径（见末节），没有审批卡。

### 底层状态机（进阶）

即兴 workflow 在底层是一串 `botmux workflow` 子命令推动的状态机——通常由 bot 自动调用，排障时也能手动驱动：

| 命令 | 状态流转 |
|------|----------|
| `botmux workflow new "<目标>"` | 建 run，返回 `runId` / `specPath` → `grilling` |
| `botmux workflow spec-finalize <runId>` | 校验 spec.md → `spec_ready` |
| `botmux workflow approve-spec <runId>` | Gate-1 通过 → `spec_approved` |
| `botmux workflow architect <runId>` | 编排并校验 DAG → `dag_ready` |
| `botmux workflow approve-dag <runId>` | Gate-2 通过 → `dag_approved` |
| `botmux workflow start <runId>` | 交 daemon 驱动开跑 |

## 保存与复用（Saved Workflow）

即兴 workflow 跑通后，可以把它存成 Saved Workflow，之后带不同参数反复跑：

| 入口 | 作用 |
|------|------|
| 飞书 `/workflow save last [名称]` / CLI `botmux workflow save [last\|runId] [名称]` | 把最近一次（或指定 runId）的 run 存为 Saved Workflow |
| 飞书 `/workflow run <名称> [key=value ...]` / CLI `botmux workflow run <名称\|workflowId> [--param key=value ...]` | 运行 Saved Workflow |
| 飞书 `/workflow list` / CLI `botmux workflow list [--json]` | 列出已保存的 workflow |
| 飞书 `/workflow show <名称>` / CLI `botmux workflow show <名称\|workflowId>` | 查看定义 |

入参（params）：CLI 用 `--param key=value` 传标量，用 `--param-json key=<json>` 传 object / array（如 `--param-json tags='["urgent","cn"]'`）。params 适合传**业务变量**（chat id、模式开关、阈值），不要把整段任务指令通过 params 传——节点的任务定义应固化在 workflow 里。

## 旧版 v2 模板（已下线）

v2 模板 runtime 已下线：`/template run`、`botmux workflow ls / tail / resume / validate` 等命令都会直接报错。仍有旧 `~/.botmux/workflows/*.workflow.json` 定义或历史 run 的，用离线工具处理：

| 命令 | 说明 |
|------|------|
| `botmux template migrate-v3 [workflowId\|path ...] [--all]` | 默认 dry-run；加 `--commit` 把可转换的 v2 定义固化为 v3 Saved Workflow |
| `botmux template archive-runs [--commit] [--verify <archiveId\|path>]` | 扫描、归档或校验已终态的 v2 历史 run；不会执行 v2 workflow，也不直接删除历史数据 |

## 开发 / 自测：`botmux v3 run`

`botmux v3 run <dag.json> [--max-parallel <n>] [--max-per-bot <n>] [--max-per-cli <n>]` 在本地真实 ephemeral worker 池上跑一张**手写的** v3 dag.json，humanGate 走终端 y/N，**无飞书卡片**。仅用于开发 / 调试 v3 编排；正式跑即兴 workflow 请走飞书 `/workflow` + `start`。三个参数单次覆盖上面的并发配置，`--max-per-cli` 对所有 CLI 生效，会盖过 `perCliById`。

> Workflow 是实验性能力，仍在演进。日常用法在飞书里 `/workflow <目标>` 即可；本页其余命令面向运维 / 排障与编排开发。
