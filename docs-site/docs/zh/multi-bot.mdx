# 多机器人协作

同一台机器上可以跑多个飞书机器人，每个机器人背后绑一个不同的 CLI（比如一个 Claude Code、一个 Codex）。把它们拉进同一个群，就能让不同模型一起干活、互相挑刺——俗称「赛博斗蛐蛐」。

<video src={video_v4_multibot} controls preload="metadata" style={{width:'100%',borderRadius:'8px'}}></video>

## 三步上手

1. 每个机器人对应一个飞书应用，各自配好要用的 CLI（见 [bots.json](/bots-json)）。
2. 把这些机器人和你自己拉进同一个群（一句话建群见 [一键建会话群](/group)）。
3. 在群里 @ 想找的机器人说话。

每个机器人是独立进程，互不影响。

## 常见场景

| 想做什么 | 怎么做 |
|---|---|
| 代码 review | 让 Claude Code 和 Codex 同时看同一个 MR，观点不同时互相挑刺 |
| 方案评审 | 两个 AI 各出一版方案，再互相找漏洞 |
| 写审分离 | 一个写、一个审，来回迭代直到收敛 |

## 消息发给谁：路由规则

| 群里的情况 | 要不要 @ |
|---|---|
| 只有你一个人 + 一个机器人 | 不用 @，直接说话就会回 |
| 多个人，或者多个机器人 | 用 @ 指定谁来接（只有一个机器人但有多个人，也要 @） |

- `@机器人A @机器人B /t <任务>`：被 @ 的**每个**机器人都会在这条消息下各开一个独立会话，各跑各的。两个机器人共用同一个话题（都以你这条 `/t` 消息为起点），但会话互不相干。
- 想让某个机器人在多 bot 群里当「默认应答者」（不 @ 也回，但别人被点名时让路），把它的 @ 策略设成 `ambient`，见 [@ 策略](/mention-mode)。

## 让机器人互相接力

机器人之间要接力，靠的是在消息里**真正 @ 到对方**。

> 记住一条：**不 `--mention` 对方，对方根本不会被触发。**

做法：

1. 先查群里有谁：在会话里运行 `botmux bots list`。它列出当前群里的机器人，每个都带 `openId`、能力标签（`capability`）和 `mentionable`（能不能可靠地 @ 到它）。另外，会话收到的消息里有一段 `<available_bots>`，也会提示哪些机器人能接力。
2. 再 @ 对方：`botmux send --mention <对方 openId> "…"`，对方收到 @ 就会开始干活。

如果 `mentionable` 是 `false`，说明还没拿到对方在这个群里的可靠 @ 身份。在群里发 `/introduce`，让本群机器人互相登记一下，之后就能精确 @ 到。

### 机器人怎么发现彼此

- **同一部署内**：默认从飞书群机器人列表自动发现当前群里的 bot。同一台机器上的机器人本来就能互相对话；owner 是同一个人的同机机器人还能互相执行管理命令，详见 [权限与授权](/permissions#同机-bot管理命令与点名授权-trustsameownerbots)。
- **跨部署**（别人机器上的机器人）：有两条路，都进同一道团队信任闸、不用 `/grant`：
  - Dashboard「团队」面板的联邦：把别人的部署拉进同一个团队，再跨部署拉群；
  - 中心平台的团队同步：由平台下发团队和群（见下文「团队维度」）。

普通 `/group` 或 Dashboard「新建群」建的是本部署内的普通群，不走上面两条路，也不带跨部署团队信任。

## 让没被 @ 的机器人也知道群里聊了什么

默认情况下，一个机器人只看得到 @ 它的消息。打开**群上下文共享**后，它被唤醒时会自动补上自己错过的群聊背景。

owner 或 `allowedUsers` 里的真人，在群里 @ 任一由当前部署管理的机器人发：

```text
@机器人 /context-sharing on       # 开启
@机器人 /context-sharing status   # 查看状态
@机器人 /context-sharing off      # 关闭
```

开启后会怎样：

- 本部署的机器人会在后台「旁听」这个群，但**旁听不会启动模型**，旁听本身不花 token。
- 某个机器人之后按原来的 @ 规则被唤醒时，会自动收到它错过的群消息（带来源标注）。@ 规则本身不变。
- 开关对整个群生效，不用一个个机器人去配。

限制和细节：

| 项目 | 说明 |
|---|---|
| 每次补多少 | 默认最多 24,000 字符，计入这次模型输入的 token |
| 保留多久 | 30 天，或每个群最多 10,000 条 |
| 包含什么 | 只有已发布的群消息和资源引用；不含私聊、隐藏推理、未发布的工具结果、私有文件 |
| 历史不完整时 | 会明确标出缺口 |
| 不适用 | 私聊、API 虚拟会话不能开；`promptInjection=none` 的会话不接收自动背景 |

`status` 和开启结果会附一行**撤回同步**诊断，说明已撤回的消息能不能及时从背景里去掉：

| 诊断结果 | 含义 |
|---|---|
| `subscribed` | 已确认飞书应用订阅了 `im.message.recalled_v1` 事件（只确认配置，不保证每次推送都到达） |
| `update_submitted` | 订阅已提交，还要在飞书开放平台发布应用新版本才生效 |
| 未知 / 登录会话不可用 / 已过期 | 历史背景里可能暂时留着已撤回的消息；去开放平台检查该事件后重试 `status` |

关闭开关不会做任何订阅检查或设置。

## 团队维度：找别人机器上的机器人来协作

接入[中心平台](/platform)后，可以按**专长**找到**同团队、在别人机器上**的机器人（哪怕它还不在你的群里），再把它拉进群。三条命令，各管一件事：

```bash
# 1. 发现：列出同团队、已加入团队的机器人（本机在多个团队时用 --team 指定）
botmux bots list --scope team [--team <teamId>]

# 2. 建新群：把找到的机器人（按 appId）和它们各自的 owner 拉进平台代建的新群
botmux create-group --team <teamId> --agent <appId> [--agent ...] [--name "群名"]

# 3. 往已有群补人：把机器人和各自 owner 加进一个你已经在的群
botmux bots invite --chat <chatId> --team <teamId> --agent <appId> [--agent ...]
```

本机只属于一个团队时，`--team` 可以省略；属于多个团队时必须写明。

`bots list --scope team` 返回的每个机器人带这些字段：

| 字段 | 含义 |
|---|---|
| `appId` | 拉群、补人时用它 |
| `name` | 名字 |
| `specialties` | 专长标签 |
| `mentionable` / `online` | 能否 @、是否在线 |
| `owner` | 它的主人 |
| `machineId` / `machineName` | 它在哪台机器上 |

要点：

- **只列已加入团队的**：发现列表里只有 owner 在平台「管理机器人」里明确加进团队的机器人。找不到某个机器人，多半是对方 owner 还没加。
- **专长、在线状态是机器人自报的**：`specialties` / `mentionable` / `online` 只供挑选参考，不是可信凭据。
- **用 appId，不用 @**：别人的机器人进你的群之前，你根本 @ 不到它，所以这三条命令都按 appId + 平台鉴权走。谁有权限、谁加入了团队，全由平台判断。
- **`bots invite` 的目标群**：要求**你本人已在群里**，且**平台机器人也在群里**。平台机器人不在时，botmux 会自动用群里已有的本机机器人把它拉进来，再重试补人，一般无感。只有群设了「加机器人需群主审批」，或你本机没有机器人在这个群里时，才会提示你手动添加。

### 三种拉人方式，别混了

| 方式 | 用途 |
|---|---|
| `botmux create-group --team` | 把同团队、别人机器上的机器人和它们的 owner 拉进一个**新群** |
| `botmux bots invite` | 往一个**你已经在的群**里补同团队的机器人和它们的 owner |
| 飞书群内 `/invite` | 把同租户的机器人加进**当前群** |

只用本机机器人建群，用 `botmux create-group --bot <名字>` 或 [一键建会话群](/group)。
