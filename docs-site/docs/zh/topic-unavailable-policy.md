# 原话题不可用时停止发送

AI 在话题里干活时，原话题可能会被人撤回。默认情况下，Botmux 沿用原来的发送规则：比如引用的消息被撤回了，回复会改发到群顶层。

如果你不希望这种「换个地方发」的行为，可以给机器人打开**停止发送**策略：发送前先确认原话题还在，不在或确认不了就不发，也不改发到别处。

## 怎么开

二选一：

- **Dashboard**：进入「Bot 配置」，选中机器人，在「回复投递」区块把「原话题不可用时」改成「停止发送」。保存后立即生效。
- **斜杠命令**：在飞书里对机器人发送

  ```sh
  /botconfig set topicUnavailablePolicy stop
  ```

想恢复默认，执行下面任意一条：

```sh
/botconfig set topicUnavailablePolicy legacy
/botconfig unset topicUnavailablePolicy
```

这个配置按机器人单独生效，写在 `bots.json` 对应机器人的 `topicUnavailablePolicy` 字段里。

## 两种策略的区别

| 策略 | Dashboard 显示 | 行为 |
| --- | --- | --- |
| `legacy`（默认） | 默认 | 沿用原有发送规则，不额外查询话题状态。引用消息被撤回等原有兜底场景，仍会改发群顶层。 |
| `stop` | 停止发送 | 发送前先查原话题状态。话题已撤回或状态确认不了，就停止发送，不改发顶层、跨群或新建话题。 |

## 开启后会检查哪些发送

开启 `stop` 后，下面这些发送都会先确认原话题：

- AI 在会话里执行的 `botmux send`，以及每轮结束时自动发出的最终回复
- 用 `--into` 显式指定的目标话题，也会一并检查
- 显式改发到群顶层或其他话题时，**仍然要先检查原话题**，不能借此绕开
- 更新已发出的卡片、消息（比如流式卡片刷新）前，也会检查它所在的话题

不会额外查询的情况：

- 没有来源话题的广播，没东西可查
- 已经发送成功的消息被重放时，直接复用之前的回执，不会再查询、也不会重发

## 被拦下时会看到什么

| 错误码 | 含义 | 该怎么办 |
| --- | --- | --- |
| `TOPIC_SEND_BLOCKED` | 原话题已撤回（包括飞书返回错误码 `230011`） | 不要重试，也不要换个地方发 |
| `TOPIC_SEND_CHECK_FAILED` | 查询失败，或者消息状态确认不了 | 可以稍后重试原话题的查询；这不代表话题已失效，也不能据此改发别处 |

- 命令行里会输出 `botmux send refused: …`，退出码为 `2`。
- 自动最终回复遇到 `TOPIC_SEND_BLOCKED` 会立即停止重试，这条回复保持「未投递」。原话题收不到通知，所以 Botmux 会把这个会话放进 Dashboard「需要你」一栏，显示阻塞原因；不会往其他会话补发提醒。
- 同时会触发 `session.requires_attention` 事件（原因 `topic_send_blocked`），可以用 [Hooks](/hooks) 接到你自己的通知渠道。

## 注意事项

- 这个策略只管「发不发」。它不会取消正在执行的任务，也不代表原任务的内容应该被删除。
- 查询结果有短暂缓存：同一次发送里，确认可用的结果最多复用 1 秒；查询失败或状态不明的结果从不缓存。
- 即使发送前检查通过，如果飞书在真正发送时返回「引用已撤回」，`stop` 模式下也会停下来，而不是走原来的改发顶层兜底。
