# 话题结束时自动挂起

收到话题根消息的删除或撤回事件后，Botmux 默认终止当前执行并挂起该话题绑定的 worker，释放执行进程占用的内存。无需配置开关，不做周期轮询。

逻辑会话保持有效：话题绑定、已落盘的上下文、工作目录和 Git worktree 都保留。下一次有效任务触发时，Botmux 按原有冷恢复流程重新启动 CLI 并继续该会话。

## 触发与反馈

| 操作或状态 | 行为 |
| --- | --- |
| 删除或撤回话题根消息，收到 `im.message.recalled_v1` | 立即进入 suspend 流程，终止正在执行的任务；不等待本轮自然完成 |
| 撤回普通回复 | 不挂起话题 worker |
| 已经挂起，没有存活 worker | 幂等，无需再次操作 |
| 飞书原生右键「关闭当前话题」 | 实际可订阅事件尚未确认，本版本不宣称已接入 |
| 手动 `/close`、卡片关闭会话 | 保持原有显式关闭会话的语义 |

Dashboard 显示「已挂起 · 话题已删除或撤回」。已不可用的话题中不额外发送通知。daemon 的 `[topic-suspend]` 日志记录挂起结果；未确认成功时会记录失败，不显示已成功挂起。

## 支持边界

- 当前 suspend 路径支持 tmux、herdr、zellij 和 zmx 本地持久终端。PTY 和远端后端保留现有不支持挂起的保护，不强行关闭或丢弃会话。
- 只影响当前机器人在该群中绑定到该根消息的线程 worker，不影响群级会话、其它话题或其它机器人的 worker。
- 依赖应用已发布生效的 `im.message.recalled_v1` 订阅；本功能只处理收到的事件，不用轮询补偿未收到的事件。
- 会话迁移、受保护的执行归属或无法证明执行进程已退出时，沿用底层 suspend 的拒绝机制。durable primary 多副本模式尚未接入这条自动挂起入口。
- 挂起会终止未完成的工作，恢复依据已落盘记录，无法恢复被终止工具的内存状态。

[原话题不可用策略](/topic-unavailable-policy) 控制发送与兜底位置，独立于这项默认挂起行为。
