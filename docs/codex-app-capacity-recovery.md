# Codex App 容量不足续跑

`codexCapacityRecovery` 同时覆盖 Botmux 托管的 Codex 和 Codex App 飞书会话，默认关闭。管理员用 `/botconfig set codexCapacityRecovery on` 开启，`off` 关闭。开启后，明确的模型容量失败最多追加两条恢复输入，分别等待 15 秒、45 秒；沿用原会话、原模型和工作区 checkpoint，不重发原始任务。

Codex App 的原生 `turn/completed` 必须明确失败，且错误被识别为容量不足，才进入这条续跑路径。模型答复中的相同文字、普通 503、限流、鉴权失败和结果未知的传输错误不获得自动续跑权限。签名 final 将结构化失败码传给 worker，worker 的失败 IPC、持久 terminal 和执行结束事件保持一致。合并执行的早期 HTTP 成员随真实 final 一起失败，不能把容量错误当作成功结果。

续跑只使用原逻辑轮次在接收时保存的真人来源。原应用、发送人及非机器人证明缺失时停止并提示人工处理；不使用当前聊天发送人或管理员补权限。准备新轮次身份后才投递，等待期间的新输入、停止或关闭配置会取消旧恢复。定时任务仍按其原有创建人来源处理。adopt、HTTP 和会议接收会话不自动续跑。

App 签名 final 的 ledger、ACK high-water 和待处理 terminal 收据在同一次 sessions 文件替换中保存。即使 worker 在 ACK 后、额外 terminal IPC 前退出，失败也不会永久静默。首步保存失败回滚三者；后续恢复投影写入失败保留已提交收据，重放或启动时核对。进程重启沿用既有保守策略：已确认成功可以结算，待恢复失败转为需要人工继续，不自动重放请求。

验证使用原生协议 fixture、真实签名验证与队列、生产 worker/daemon 闭包和真实恢复协调器。假时钟覆盖两次上限、原发送人保持、人工干预、部分保存、重启、负 ACK 重放和 HTTP steer 失败结算；故障注入不访问真实模型或用户凭据。飞书失败卡沿用现有组件。
