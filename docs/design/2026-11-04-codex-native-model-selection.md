# Codex 原生模型选择在重启后保留

问题：在 Codex 终端用 `/model` 选择 B 后，Botmux 恢复同一个原生会话时仍传入 bot 默认 A，覆盖 Codex 已保存的选择。

会话的 `model` 继续只记录启动模型，不能重新把所有老会话冻结在默认值上。新增 `codexModelSelection` 保存原生会话 ID、最近一次实际启动的模型和时间，以及确认过的会话覆盖。模型优先级为：dispatch 固定规格、单次 trigger 覆盖、原生会话覆盖、话题默认、bot 默认、跨 CLI 历史兜底。

在 cold spawn 和 live-worker restart 解析启动参数之前，从该会话自己的 rollout 读取完整的 `thread_settings_applied`。使用文件身份与完整行 cursor 处理新设置，单独保存最近观察的模型与等待确认的启动模型。只有确认的设置变化才创建覆盖：请求新启动但 IPC 失败时，旧进程的相同设置仍是旧基线。`turn_context`、模型回复中的字符串和自动降级运行模型都不能创建覆盖。启动基线也记录单次 trigger 的模型，因此单次调用本身不会变成永久覆盖。

worker 在真正的 `backend.spawn` 前采集旧 rollout 的完整行 frontier，成功创建新进程后发布 `codex_model_launch`。只有当前 worker、相符模型/会话且不早于本次启动请求的回执才建立新进程基线；只重新附着旧 pane 不发布回执。这样即使新进程还没有初始设置快照，手动切回旧模型也能被识别，旧进程最后的快照不会被误认为新选择。

真实 backend spawn 与确认发布复用同一个可执行入口。发布前原子保存每会话一份私有启动回执，恢复解析前重读：即使确认遇到 SQLite busy 或 daemon 在保存前退出，实际启动事实也不会仅留在丢失的 IPC 里。回执不包含凭证，旧模型/旧会话/早于当前启动请求的回执不生效。

恢复时重新读取原生记录，无需等待下一次成功回答，也不依赖 worker 的显示事件先完成落盘。读不到记录时保留已经持久化的覆盖；写入失败沿用 session-store 的回滚和错误路径，中止 restart IPC，下一次恢复仍可重新读取原生选择。扫描以完整行结束，半行补齐后仍能在下次重试读取，最多读取尾部 4 MiB；旧版本没有结构化设置记录时继续原有默认行为。

覆盖绑定原生会话 ID，不跨 `/new`、外部接管或不同 CLI 泄漏。首轮仅支持本地 Codex PTY/tmux；Claude、TraeX、codex-app、adopt、远端 app-server 和 dispatch 会话继续现有策略。默认解析的共享路径需要验证其他 CLI 与群默认均不回归。

原生会话轮换时清除旧覆盖，并且只有 exact-session resolver 已验证的新 rollout 才能继续读取；新会话第一条设置是新基线，后续手动变化可在它的首次恢复时保留。

原生选择回到当前继承模型时清除覆盖。话题内 `/models inherit` 明确恢复跟随默认，下次重启生效；它先 checkpoint 当前原生设置，再清除覆盖，避免同毫秒旧记录或后续相同模型快照重建覆盖。不能读取当前设置时拒绝重置，避免保存不准确的基线。

限制：既没有显式启动模型，也没有原生初始设置记录时，无法区分首个快照是 CLI 默认还是手动选择。首个快照只作为基线，后续确认的变化才持久化；不猜测或冻结未知默认。尾部 4 MiB 之外且之后再无设置快照的变化无法捕获。

验证覆盖：A → 原生选 B → live restart/cold resume；未手动选择时默认 A → C；设置已写但未成功回答；单次模型不永久冻结；自动降级不创建覆盖；原生会话轮换；缺失/损坏/半行记录；重置与稍后的默认更新；持久写入失败后重试。持久化变更在 push 前进行异常交叠探针和变异复验。
