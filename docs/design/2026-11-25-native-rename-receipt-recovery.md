# 原生会话改名缺少确认时恢复排队输入

## 现象

TRAE 会话完成一次回复后，worker 发出原生改名命令。CLI 已经回到空输入框，
但保存的名字与请求的名字不同，例如分隔标点发生变化。
`session_index.jsonl` 没有本次精确标题的回执，后续追问一直停在 worker 队列中。

精确回执校验必须保留。空输入框也可能是 CLI 尚未消费改名命令之前的旧画面；
直接按超时放行，会再次把用户消息拼进 `/rename` 命令。

## 恢复方式

从改名命令送出起等待至少一分钟，满足以下条件时，在 worker 内重新启动一次 CLI：

- 当前输入框被 TRAE 解析器明确判断为空，且有尚未提交的普通消息或 raw 命令。
- CLI 为 TRAE，后端为本地 pty、tmux 或 hc，属于此 worker，而非 adopt 或外接 app-server。
- 没有重启、升级、终端人工写入或其他输入写入正在进行。
- 从当前 TRAE 进程的 rollout FD 重新证明唯一原生会话，且与本次改名的会话 ID 一致。
- 本 worker 尚未执行过此恢复。

通过现有 `restartCliProcess` 路径保留 pending 队列，并固定恢复原生会话 ID。
该恢复不消耗会触发 FRESH 的崩溃预算；原会话不可恢复或旧进程退出不能被证明时，
继续使用既有的错误处理，不降级到新对话，不叠加另一个进程。

原进程退出前不解除改名输入保护。新进程没有旧改名命令或粘贴缓冲，
在其正常的输入就绪检查通过后处理队列，期间到达的新消息也留在队列中。
用户会收到恢复通知，不需要重新发送追问。

恢复只允许一次，且同一个失败标题的自动同步在此 worker 中不再重新安排，
以免每次回复都再次卡住。用户明确请求的改名和不同标题仍可进入已有流程。

无法识别的界面、用户草稿、对话框、忙碌界面、共享进程、无法证明会话身份，
均保留原来的提示和手动恢复方式，不通过猜测释放输入。

## 影响范围与验证

只为本地、独占的 TRAE 会话增加恢复；Codex、Claude、远端后端以及 adopt 会话不增加自动重启。
使用现有跨平台 rollout 所有权检测与后端退出/恢复路径，不增加平台命令或凭据操作。
共用的启动/重启入口补充关闭检查，关闭已开始时不再创建替代 CLI；这项关闭保护适用于所有 CLI。

- 策略与 worker 函数测试：超时边界、一次恢复、raw 输入、共享/占用状态、原生会话切换、
  FD 歧义和自动标题抑制。
- 真实 worker + 隔离假 TRAE：改名写成另一标题、空输入框一直缺少精确回执、
  等待到超时后恢复；重启期间再加入追问，两个追问各提交一次，原生改名只执行一次。
- 既有改名回归：输入框中仍留着改名命令、用户手动完成改名、未知页脚、其它 thread 的回执。
- 异常时序探针：人工占用期间跨过截止时间、退出操作部分失败、重启等待期间增加消息；
  修改关键守卫验证测试会失败。

本次在隔离 HOME、数据目录和私有后端中验证，不使用业务凭据或生产会话。
