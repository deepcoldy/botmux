# Durable coordination provider runtime

## Goal

BotMux needs to consume a durable coordination implementation without linking a database client or deployment-specific credentials into the public binary. The runtime therefore starts one operator-selected JSONL provider process and exposes it through the existing `DurableCoordinationStore` interface.

The process is a trusted runtime extension, not a plugin for model code. BotMux launches it directly without a shell, never copies provider stderr into protocol errors, and validates every response before it reaches daemon state.

## Protocol

Every line is one JSON request or response with:

- protocol `botmux.durable-coordination-provider`;
- wire version `1`;
- a stable `requestId`;
- an initial `hello` that proves durable contract version `4`; older providers are intentionally rejected because lane-aware inbox/control operations and semantic Lark receive deduplication are breaking contract changes;
- a `call` for one public store method.

The provider may respond out of order. BotMux correlates by `requestId`, bounds line size and request time, rejects unknown request ids, and terminates the provider after a timeout or malformed response. Provider failures carry a bounded public code, a redacted message, and explicit retryability; retryability never changes outbox ambiguity rules.

## Configuration

The default remains disabled. The public runtime reads only provider-neutral settings:

| Variable | Meaning |
| --- | --- |
| `BOTMUX_COORDINATION_MODE` | `disabled`, `shadow`, or `primary` |
| `BOTMUX_COORDINATION_PROVIDER_BIN` | Absolute executable path; required outside `disabled` |
| `BOTMUX_COORDINATION_PROVIDER_ARGS_JSON` | Optional JSON string array; no shell parsing |
| `BOTMUX_COORDINATION_PROVIDER_HANDSHAKE_TIMEOUT_MS` | Optional bounded hello timeout |
| `BOTMUX_COORDINATION_PROVIDER_REQUEST_TIMEOUT_MS` | Optional bounded call timeout |

The provider inherits the daemon environment because it is selected by the operator and may need file-based credential references. Provider code must keep secrets out of stdout, stderr, argv, receipts, and durable JSON values.

## CLI state and deployment responsibility

Durable coordination covers BotMux routing, canonical Session snapshots, inbox ownership and single-message outbox settlement. It does not replicate a CLI provider's transcript, auto-memory, working tree, role/knowledge files or other filesystem state. An operator-supplied provider may additionally advertise `turn_recovery`: after `resume`, its `ready` event can identify one already-submitted, generation-fenced turn that survived the host process. BotMux then restores that turn's attribution and waits for its terminal event without resubmitting the prompt. Providers without this capability retain the earlier fail-closed boundary.

The first primary release requires one of two deployment policies: keep a live CLI runtime sticky to the replica that owns its provider state, or use an operator-supplied remote runner/filesystem layer that makes the provider state visible after takeover. When a provider buckets resume or memory state by an absolute working-directory path, every eligible replica must expose the same logical state at the same path. `BOTMUX_REMOTE_RUNNER_STATE_ROOT` is only an opaque value forwarded to the selected runner; BotMux neither mounts nor interprets it.

When an Inbox claim lands on a replica without the canonical active Session, primary mode now keeps the route fenced until that replica acquires the Session lease and advances the canonical revision under its new owner epoch. The owning primary runtime renews active Session leases until the snapshot closes or the daemon stops; a foreground CAS conflict or transient read/write error must re-arm that renewal with the newly acquired lease, while a stale write reports lease loss and retires the local worker. Write-scoped facades release an acquired lease before propagating a read/write error. Every active route revalidates that lease even when the canonical Session is already materialized locally, so a restarted stale replica cannot bypass the owner fence merely by restoring its disk row. Only an ordinary Remote Runner Session with persisted `remoteSessionId` and an explicitly required `turn_recovery` capability may be materialized into the local store and registry. Replica-local PID, Web Terminal and preview fields are discarded; the worker generation advances locally and the runner receives `resumeMode=reattach`. Unsupported lifecycle shapes, a live prior lease, a changed canonical identity, a local anchor collision or a rejected worker start all remain retryable failures before the follow-up reaches a session handler.

Coordination between different Sessions that write a shared memory or knowledge directory is also outside the Session lease. The deployment's runner/filesystem layer must provide the required isolation, locking or merge policy. Until that layer proves otherwise, replica takeover guarantees routing and delivery recovery only; it must not be described as lossless active-turn or CLI-context failover. A `turn_recovery` provider must durably retain the exact turn id, caller, remote generation and pre-submit transcript baseline before prompt submission, plus the dispatch attempt when the original turn carried one; incomplete legacy state cannot claim takeover. While `ready.recoveredTurn` remains active, transport readiness and startup timeouts cannot publish `prompt_ready`, release the recovered caller authority or submit a successor; the exact recovered terminal releases that fence and then drains queued input. Pending provider-to-host operations may be re-emitted only with their original operation ids, so durable output dedupe or read-only tool semantics prevent duplicate side effects; after the caller consumes a host result, its durable replay marker must be retired before the result receipt is removed. If the owning daemon survives but its worker does not, the next claimed Inbox row is a recovery trigger rather than a busy signal: it must reserve the worker-null start boundary, reattach the provider with the original dispatch attempt and durable-primary marker, and keep the Inbox row retryable until the replacement worker reports provider submission. A concurrent start, pending repository choice or retained activation journal remains retry-only and must not be double-forked.

## Rollout boundary

`shadow` starts the provider, verifies the exact public contract, and keeps the process alive through daemon shutdown. After the Lark SDK callback has returned to the ACK path, `im.message.receive_v1` is also mirrored into the durable inbox with a stable message-derived `eventId` and the existing raw chat ingress lane as `partitionKey`.

The mirror runs beside the current SQLite route. A slow or failed provider is logged but does not block that route; a duplicate is accepted, while a conflicting duplicate is surfaced as an error. A boot-unique shadow consumer claims mirrored rows, revalidates the Lark app/message identity and routing partition, and marks valid rows completed. It performs no user-visible routing or output and does not change Session ownership. Invalid envelopes are retried with a bounded delay so schema drift remains visible instead of being acknowledged. Provider failures leave claims recoverable after their lease, and daemon shutdown stops the consumer before closing the provider. Message edits and non-message event families remain outside this original shadow ingestion slice; primary adds the bounded receive-message reconciliation described below.

The shadow runtime also owns a provider-neutral `DurableSessionFacade`. It creates a boot-unique owner, serializes updates per stable session key, coalesces queued snapshots to the newest value, and performs `acquire lease → read revision → CAS write`. Occupied, conflicting and stale writes remain distinct observable outcomes. Different session keys are independent, while graceful shutdown stops admission, bounds the drain and releases retained leases before provider close.

The same facade now exposes a separate exact-write lane for primary admission. Exact writes share the per-Session FIFO but are never coalesced, always perform an independent CAS (including identical retries), and return the actual lease plus record used for the mutation. A current-aware variant builds its value only after the lane has acquired the lease and read the current revision, closing a read-merge-write gap for additive admission state. This prevents two inbox events from sharing one later revision while preserving the existing coalescing behavior for shadow snapshots.

A full primary Session projection wraps the existing persisted `Session` JSON together with a bounded oldest-to-newest history of exact inbox admission identities. The latest single `admission` field remains for version-1 reader compatibility, while the `admissions` list retains at most 64 distinct turns so type-ahead turn N+1 cannot erase turn N's output authority. It contains no runtime-only process object or worker token beyond the existing Session row contract. A primary admission merges this history inside the exact lane and mints the committed receipt only from the returned lease epoch and record revision. Restore parsing recomputes the routing key and rejects mismatched Session/app/event/partition identities. The primary daemon path uses this projection for every admitted message and supported output.

A canonical-dispatch bridge defines the callback seam used by the primary consumer. The canonical handler must explicitly return either an admitted Session snapshot or an ignored reason. Only an exact full-Session CAS can turn the admitted result into committed; aborts, unknown/queued results and Session coordination failures remain retryable errors. The primary daemon path constructs this provider-neutral bridge around the existing router.

Only a narrow versioned projection is eligible for this stage: session id, application id, routing anchor, scope, active/closed status and lifecycle timestamps. Prompt content, titles, identities, paths, attachments, tokens and provider/terminal state are excluded. The daemon invokes this mirror only after an ordinary Lark session has committed to SQLite and won active-session registration. It is therefore shadow evidence, not a complete Session source: restore, close, multi-row transactions, lineage batches and the synchronous Session API remain SQLite-only.

A provider-neutral primary inbox consumer now defines the later claim-to-admission state machine without enabling it. Multiple boot-scoped slots can process independent partitions. Each claim is revalidated before dispatch, renewed while dispatch is active, and completed only after a validated `committed` or explicitly `ignored` receipt. A committed result must carry a versioned durable-admission receipt that binds the claimed event/app/partition to the fenced Session key, lease epoch, record revision and store timestamp. A bare committed marker or a receipt copied from another event is retried instead of completing the inbox row. Dispatch errors retry only while ownership is still proven. A stale/failed renewal aborts the callback and leaves the row for lease-expiry recovery; bounded shutdown likewise never fabricates a completion.

Durable control operations use a separate table and stable `operationId` to fence lifecycle side effects such as close or resume. Enqueue requires the current Session lease; `beginControlOperationAttempt` is the side-effect boundary and binds one exact attempt to the current owner and epoch. A proven pre-effect failure may return that attempt to `pending`, but an ownership change freezes an in-flight attempt as `ambiguous` instead of replaying it. Only the exact late completion token or backend reconciliation with non-empty evidence may settle ambiguous work.

Shadow mode keeps its ACK-after-live-route mirror unchanged. Primary instead constructs the consumer, replaces the live callback with enqueue-before-ACK and completes the claim only after the canonical Session receipt validates. Store-generated inbox sequence and application ingress leadership provide the cross-replica ordering authority.

A provider-neutral durable outbox pump is also present without daemon wiring. It reserves independent Session heads concurrently, commits `attempting` before invoking transport, and accepts only delivered, explicitly safe retry, or ambiguous outcomes. Exceptions, timeouts and malformed retry proofs become ambiguous. Timed-out callbacks may report a late result for reconciliation, but the automatic pump never turns that observation into a delivered receipt.

A settlement bridge follows the authoritative outbox row after fenced enqueue until `delivered` or `ambiguous`. It deliberately polls the shared store instead of trusting a process-local pump callback, so delivery completed by a takeover replica still releases the originating final-output drain. Aborting a local wait never mutates the durable row. Primary ordinary and in-session CLI output both use this bridge.

A Session-output bridge exact-writes the latest full Session snapshot, then enqueues the frozen outbox message with that same fresh lease proof and returns the authoritative settlement. It validates the output Session key before either mutation and never falls back to direct transport on coordination failure.

A final-output bridge synchronously joins the existing daemon final-drain before starting those asynchronous mutations and releases it only after terminal shared-store settlement or a proven pre-enqueue/local-wait failure. Ordinary worker output uses it only in primary; disabled and shadow modes retain direct delivery.

The Lark adapter now defines a frozen, versioned single-message envelope without wiring it into the daemon. It binds the app, send chat or reply parent, reply mode, message type/content, stable provider UUID and JSON hook context. It reuses the existing send/reply clients, Feishu error classifier and one-hour provider TTL. Retry is allowed only for classified retryable failures while the UUID window still has a safety margin; otherwise the result is ambiguous.

Session/epoch authority is revalidated immediately before provider invocation. Protected hook capability is never persisted: the current owner must dynamically provide `beforeHook` and `hookOrigin` for the first attempt. UUID reconciliation suppresses later hooks. A withdrawn reply remains ambiguous instead of silently falling back to top-level send under the same UUID, because provider dedupe does not bind the reply parent. Attachments, multi-message sequences, card patches and non-IM effects remain outside this envelope.

The daemon constructs the adapter only inside primary. Unsupported multi-effect shapes are rejected or suppressed as documented below and never fall back to this adapter's direct transport dependencies.

A provider-neutral primary Lark ingress component owns the disabled-state admission boundary. Every primary replica keeps one Lark SDK connection because the official long-connection transport runs in cluster mode and assigns each event to one random connected client; a replica that is not the recovery leader must therefore still persist the realtime event before its callback may ACK. Realtime insertion uses the store's idempotent inbox operation and accepts both inserted and duplicate results; conflicting duplicates and provider failures fail the callback for platform retry. A separate application-scoped lease elects only the replica allowed to perform REST history recovery, whose inserts remain atomically fenced by that lease.

Inbox ordering no longer treats caller `createdAt` as cross-leader authority. The store must allocate an insertion sequence transactionally and use it for every per-partition earlier fence. The SQLite reference uses an autoincrement side table with deterministic legacy backfill; remote providers must use a database sequence/identity or equivalent serialization point.

Admission is serialized per raw routing partition at API entry. An ACK timeout rejects the callback but leaves the real enqueue in the partition tail, so redelivery cannot let N+1 overtake N and a later successful first write becomes a duplicate. Cross-replica duplicate delivery is resolved by the shared store's stable event id. Graceful stop first closes that replica's SDK transport, then drains admitted writes and leadership cleanup before lease release, all under one shutdown deadline. Client timestamps only order one process lifetime; the component does not claim a strict total order across independent connections without the store-generated sequence and the platform's event-delivery ordering contract.

This ingress component is constructed only in `primary` and does not alter disabled or shadow routes.

`DurableLarkPrimaryRuntime` composes the recovery leader, cluster-capable realtime ingress, primary inbox consumer, canonical Session admission bridge, durable outbox pump and Session facade around one store. Consumer and pump start before the replica opens its SDK connection. Graceful stop uses one absolute budget and orders `WS cleanup → ingress/recovery drain → inbox drain → outbox drain → Session lease release`; fatal termination aborts every component. The runtime factory still requires an explicit in-process proof, and the daemon grants it only at the call site that assembles this complete path.

The daemon builds one reusable Lark event runtime after Session restore and opens one SDK connection on every primary replica. Feishu cluster delivery selects one live client; whichever replica receives a realtime message or supported card callback writes it directly and idempotently to the shared Inbox before ACK, so losing the recovery leader no longer creates a socket-free window for first-ever p2p or WS-only traffic. On recovery leadership acquisition, the elected replica separately performs one bounded history scan, waits for its SDK transport to become ready if necessary, then performs two post-ready scans separated by a bounded quiet period. Both post-ready scans cover the same acquisition-time window and must produce the same message-id fingerprint before recovery is declared complete; a retry never advances the lower cutoff and ages a missed message out. `onReconnecting` and the terminal-failure watchdog re-arm recovery only on the elected replica, while standby sockets remain available for realtime delivery. REST recovery enumerates group chats and enqueues recovered `im.message.receive_v1` under the same message-derived event id and chat partition as realtime delivery. Because the list endpoint can reduce an interactive card to an upgrade placeholder and omit its mentions, recovery fetches the authoritative single-message detail before enqueue when a card has no mention projection, then maps a self `app_id` mention to the already-probed bot `open_id`; the claimed consumer resolves the full card before routing. A missing detail or unresolved bot identity keeps recovery fail closed instead of completing a card that may have addressed the bot. Chatless update lookups start in parallel at frame arrival, while every primary message callback synchronously reserves a lightweight app-wide arrival slot; the slot is released only after its already-running lookup has resolved and the real per-chat ingress tail is registered. A chatless `im.message.updated_v1` must resolve its authoritative `chat_id` within the ACK budget and use the real chat partition, otherwise the callback fails for redelivery instead of entering a parallel `__chatless__` lane. Membership events are also cluster-delivered to only one replica, so a primary consumer must not authorize the one-human/one-bot mention bypass from its process-local membership cache; each such routing decision performs a fresh membership read and degrades to requiring an explicit mention if that read fails. Public close/resume card callbacks use a separate durable control lane. An exact typed `/close` first commits its ordinary message admission and only then appends a user-authorized control to that lane; a trusted Dashboard/host close appends the same versioned control and waits for its operation to appear in the canonical Session before reporting success. A primary-mode daemon never falls back from either path to a replica-local close. If a failed remote creation left generation zero without a remote Session or agent thread, the control may materialize a closed local projection and commit it without attempting a nonexistent provider cancellation. If the exact Session owner disappears while a live remote generation exists, a peer waits for the old lease to expire, claims the canonical Session, materializes the Remote Runner runtime locally, and then applies the lifecycle action; the callback is therefore not stranded until the original Pod returns. Chat-list failure, request timeout, unstable post-ready snapshots or a scan window exceeding its configured cap keeps only recovery fail closed and retrying; realtime clients continue to persist selected events. The official chat-list API still excludes p2p, so full-cluster downtime cannot be reconstructed from REST alone, but one-replica failure and rolling replacement retain an already-connected peer and no longer depend on that incomplete inventory. The legacy message-listener poller is disabled in primary because the general group recovery path already feeds the canonical Inbox and direct local listener dispatch would bypass fencing.

The Inbox duplicate contract recognises realtime and REST snapshots of one valid Lark receive event as the same immutable app/message/partition plus canonical sender/content/routing projection even when an identity representation omits an optional alias. Sender extraction accepts both wrapper and nested event shapes; every overlapping open/union/user/app identity must agree, and mention identities follow the same rule. Mention display names are excluded from the identity projection because they are mutable presentation metadata and the list, detail and realtime APIs populate them inconsistently; placeholder key and stable identities remain checked. Interactive content is considered compatible only when the other projection is the known Lark “upgrade client” placeholder; two distinct complete card bodies still conflict. The first persisted payload remains canonical; a later snapshot never overwrites it. A different app, message id, lane, partition, chat, sender, ordinary content, message type, root/thread/parent, mention identity projection or create time still conflicts. Recovery enqueues atomically check the exact recovery lease owner/epoch, while realtime enqueues deliberately use the shared idempotent store operation on every SDK client. Contract version 5 adds fenced `readAuxiliaryState` / `writeAuxiliaryState` records in a table separate from canonical Sessions, so chat-level recall tombstones and later sessionless state cannot pollute Dashboard enumeration or `session_count`; older external providers are rejected at handshake. Both ordinary `im.message.receive_v1`, `im.message.updated_v1`, and `im.message.recalled_v1` use the canonical partitioned admission path in primary. A recall is committed to shared auxiliary state before its Inbox claim completes, and each replica hydrates the shared tombstones before composing later group context. Claimed message rows re-enter the same routing/permission/canonical handlers without a WS connection and resolve the exact admitted Session snapshot. Recovery leadership loss aborts only the scan lifecycle; the replica's realtime SDK connection remains active until daemon shutdown.

Primary configuration writes use the same auxiliary-state fencing without copying configuration payloads or credentials into the coordination database. A config transaction acquires one shared lease per document, verifies the current file SHA-256 against the last committed revision, records a prepared marker, performs the existing atomic file update, and commits a hash-only audit entry with changed field paths. A process that dies after preparation is reconciled from the shared file before another mutation proceeds; an out-of-band edit after a committed revision is treated as drift and blocks the next write. Supported `bots.json` RMW paths, Dashboard global settings, and group context settings run in separate transaction scopes, while direct low-level writes fail closed in primary mode. Deployments that need cross-replica global and group context settings must point `BOTMUX_GLOBAL_CONFIG_FILE` and `BOTMUX_GROUP_CONTEXT_SETTINGS_FILE` at their respective shared canonical files.

Ordinary bridge `final_output` freezes the existing reply target/card/provider UUID, resolves the requesting turn's own bounded admission, exact-writes the current Session snapshot while retaining other in-flight turn admissions, enqueues outbox under that epoch, waits for shared-store settlement, then continues the existing delivery bookkeeping with the provider message id. The per-turn check prevents an ultra-fast final from reusing another input's Session admission without rejecting an earlier type-ahead turn. Legacy/shadow keep the existing direct transport byte-for-byte.

In-session `botmux send` routes its already-rendered single message to the owning daemon over the existing authenticated Session IPC. The daemon revalidates the current admission turn, exact-writes the Session, enqueues the message under the fresh lease epoch and returns only an authoritative delivered provider id. Final sends derive their provider UUID from the logical app/scope/anchor/turn identity rather than the replica-local Session UUID, so a rebuilt local Session conflicts with or reconciles the same outbox row instead of sending a second final. The CLI retries a lost daemon response and bounded startup 5xx responses with the exact same turn, payload and UUID; this closes the process-crash window between the Session transaction and outbox enqueue without pretending the two transactions are atomic. Durable ambiguity, payload conflict and permanent responses remain fail-closed. Progress and auxiliary sends receive a per-command UUID that remains stable for every outbox retry. A lost/stale Session owner therefore cannot bypass fencing through the short-lived CLI.

The first primary release deliberately narrows unsupported multi-effect shapes instead of pretending they are atomic:

1. voice, attachments, urgency, attention and managed-listener output are rejected before any upload/provider effect;
2. dynamic reply-card PATCH is disabled, so a supported send creates one fenced outbox message;
3. sessionless commands and pre-session grant/hall replies are suppressed without side effects and completed as explicitly ignored;
4. delayed forward-followup admission remains disabled: primary requires zero wait, dispatches zero-wait seeds immediately and refuses pending legacy seeds at boot.

These limitations are observable feature gates, never fallback routes. Tests also cover type-ahead output, zero-wait topic seeds and durable message-edit admission. A two-runtime SQLite integration test admits and delivers 100 independent Sessions across ingress-leader shutdown and takeover, while the provider contract suite continues to verify stale lease, claim and outbox fencing independently.

## Shutdown

Graceful daemon shutdown requests provider `close` and bounds the response. Fatal process exit terminates the child synchronously. A provider close failure is logged without provider stderr, the child is terminated, and the daemon continues its existing bounded shutdown.

## Verification

Tests cover handshake compatibility, round-trip calls, redacted retryable errors, malformed results, timeouts, disabled defaults, primary fail-closed behavior, shadow claim/validation/retry, lifecycle cleanup, and recovery after a transient bootstrap poll failure. Session facade tests additionally cover shadow coalescing, exact FIFO writes, cross-key independence, revision CAS, lease proof, occupied/conflict/stale outcomes, renewal after conflict or transient failure, stale-write lease-loss reporting, write-scoped error release and bounded stop/release. Primary Session tests cover full snapshot round-trip, routing identity validation, concurrent event revisions, exact retry revisions and receipt payload separation. Primary consumer tests cover committed/ignored receipts, rejection of bare or mismatched committed receipts, invalid envelopes, dispatch retry, claim renewal/loss, abort behavior and bounded shutdown. Admission-receipt tests cover lease/record construction, serialized identity validation and invalid Session proofs. Outbox pump tests cover begin-before-side-effect ordering, delivered receipts, safe retry proofs, ambiguous defaults, timeout/late result fencing, stale reservations and shutdown. Lark adapter tests cover frozen identity, UUID TTL retry, hook fencing/suppression, withdrawn-parent containment, authority aborts and corrupt envelopes. Primary ingress tests cover application lease leadership, occupied standby, configured renewal cadence, identity validation, inserted/duplicate/conflict outcomes, per-partition FIFO, ACK timeout tails, lease loss, activation cleanup, history fingerprint drift during the settle window, and a single bounded drain/cleanup/release deadline. Primary runtime tests cover component startup, leadership lifecycle ordering, shared shutdown budget and invalid-stop containment. CLI/daemon IPC tests prove primary sends avoid direct Lark delivery and reply-card PATCH, reject unsupported multi-effect shapes before provider calls, and return only authoritative outbox settlement. A two-runtime integration test covers 100 Session admissions, ingress failover, stale-owner output rejection and exactly one delivered outbox row per Session. The existing durable contract suite continues to cover state-machine semantics independently of transport.
