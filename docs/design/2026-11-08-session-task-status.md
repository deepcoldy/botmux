# 会话任务状态：做完了要马上看得出来

## 问题

任务在群里做完了，会话控制页和决策看板却要过很久才看得出来；需要人处理的和已经做完的混在一起。
看板列只看运行态（idle / working），「空闲」既可能是交付完了，也可能是中途失败、从没跑过。
手动拖过的卡片永远停在原列，状态变了也不动。

## 统一推导

看板列、表格状态、概览计数、状态色条和决策看板共用 `src/core/session-task-status.ts` 的
`deriveSessionTaskStatus()`。它只读 daemon 已有的事实，不新增任何需要人维护的字段。
优先级从上到下，命中即停：

| # | 状态 | 条件 | 数据来源 |
|---|---|---|---|
| 1 | 已关闭 | `status === 'closed'` | 会话行 |
| 2 | 需要你 · 等你拍板或回答 | 举手且 `source === 'agent'` | `botmux send --attention` → `ds.agentAttention` |
| 3 | 需要你 · 等你选 | `tuiPromptActive` | 屏幕识别的 TUI 选择框 |
| 4 | 需要你 · 待选仓库 | `pendingRepo` | 会话行 |
| 5 | 需要你 · 额度受限 | `status === 'limited'` | 运行态 |
| 6 | 需要你 · 长时间无进展 | `status === 'stalled'` | 运行态 |
| 7 | 需要你 · 本轮中断 | daemon 自己举的手（没有 `source`） | 失败卡、投递失败、续跑失败、审核拦截等处举手 |
| 8 | 进行中 | 运行态 starting / working / analyzing / active | 屏幕状态；`busySinceAt` = 这一段忙碌的开始时刻（提示缓存保活自己的忙碌段不记） |
| 9 | 需要你 · 本轮中断 | 本轮结果 `interrupted` | `Session.lastTurn` |
| 10 | 本轮已交付 | 本轮结果 `delivered` | `Session.lastTurn`（时间 + 最终回复第一行） |
| 11 | 没做完 | `openTodos.remaining > 0` | TODO 快照 |
| 12 | 空闲 | 其余（从没跑过、结果读不到、结果已被新消息盖过） | — |

「本轮结果」只在比最近一条消息新时有效（`max(lastTurn.at, lastTurn.heldThrough) >= lastMessageAt`）：
之后来了新消息，旧结果就不算「本轮」，落到没做完 / 空闲。`heldThrough` 是自动压缩这类 daemon 代发的维护输入
留下的：它们会刷新会话活动时间，但不是新任务。读不到、格式不对、`no_output` 一律不判成已交付。
休眠会话超过 24 小时的「本轮中断」不再算需要你（落到没做完 / 空闲），免得旧失败越积越多。
已交付排在没做完前面：这一轮已经给出了最终回复，剩下的 TODO 由回复本身交代。

举手（第 2、7 行）只在真人回复时清除，bot 协作群里可能一直挂着。举手之后又开了新一轮——正在跑且
`busySinceAt` 晚于举手，或本轮结果的 `startedAt` 晚于举手——就按新一轮算，不再拦在「需要你」。举手那一轮自己结束不算：
agent 常常在一轮中间举手、随后结束这一轮。读不到两边时刻时当举手还有效。
提示缓存保活打进去的那一句会让运行态短暂转忙，但不是新一轮：这段忙碌不记 `busySinceAt`，举手照样拦着。
保活还没回到空闲就派发了真的一轮时，这段忙碌归真的一轮，从派发这一刻起记。保活被 worker 拒收、
或打出去 10 分钟还没回到空闲（比如网页终端接着敲了字），就不再当保活：屏幕还在忙时，下一次屏幕上报补记。

最终回复投递失败会每隔几秒重试一次，每次失败都走到 daemon 举手；重试按未结的投递记录跑，早就开了新一轮时旧轮的记录
也还在重试。daemon 的举手还挂着时，重试保留第一次的举手时刻（`raiseDaemonAttention`），不然看板的「等了多久」、
手动列失效和管家提醒的去重都会把每次重试当成新的举手。只有投递失败的那一轮是在这次举手之后才开始的，才用自己的
时刻（bot 协作群里前一次的手没人放下：上面把早于新一轮的举手当成已被接管，沿用旧时刻会让这次失败显示成空闲）。
更早一轮的记录在新一轮开始后重试失败，仍保留原时刻，否则新一轮正常交付也会被重新拦回「需要你」；两轮的记录都在
重试时，时刻停在较新那轮的举手上，不来回刷新。读不到那一轮的开始时刻（daemon 重启前开始的轮）时保留原时刻。

### 本轮结果怎么记（`src/core/turn-outcome.ts`）

在 `turn_terminal` 处记一条 `Session.lastTurn = { turnId, outcome, at, startedAt?, summary?, errorCode? }`，持久化并推一个
`session.update` 补丁。`startedAt` 是 daemon 把这一轮输入交给 CLI 的时刻（`beginNewTurn`），只在内存里记，
daemon 重启前开始的轮没有。

- `delivered`：终态 `completed`，且本轮有最终回复的送达回执（`turnTerminalCarriers` 里非 progress /
  auxiliary 的那条）。daemon 兜底投递的回执在飞书往返之后才记，可能晚于终态，所以先等本轮投递落地
  （`waitForTurnFinalOutputDeliveryDrain`，上限 30 秒，覆盖 0/5/15 秒重试）。只发了进度消息、没有最终回复的
  轮不算交付。structured CLI「已完成但没匹配到最终文本」的诊断消息虽然也走最终输出通道，带
  `emptyCompletedNotice` 标记，不算最终回复。
- `interrupted`：群里会看到「⚠️ … 中断了这一轮」的那些失败（`shouldNotifyTurnFailure` 为真，且没被自动续跑接管）。
- `no_output`：其余（正常结束但没有最终回复、用户中断、被新输入顶掉、续跑接管）。如果上一个结果还代表现状
  （这一轮之前没有新消息），`no_output` 不覆盖它：提示缓存保活、HTTP 等待、没有输出的定时任务都不是新任务。
  例外：这一轮在上一个结果落定之前就开始了（`startedAt < 上一个结果的 at`），说明它是上一轮收尾时追发的消息——
  上一轮的结果要等投递落地才落定，追发消息的时间反而早于它，光比最近消息时间看不出来。这时以这一轮为准。
- 不记：自动压缩（`auto-compact:*`，阈值和空闲两种）、HTTP 回合、`botmux wait` / 异步触发器的回合、会议接收会话。
- 等待期间来了新的终态：旧的不写（每个会话一个递增序号）。会话在等待期间关闭：不写（整行写回会把已关闭的行改回 active）。
  写盘失败：内存里退回原值。
- 回执晚于等待上限（transcript 滞后补发等）：同一 `turnId` 的 `no_output`（包括上面没写盘的那种）补成 `delivered`；
  只补终态为 `completed` 的轮（失败、取消的轮后来送达的是失败提示），之后已经来了新消息就不补。
  走最终输出通道的失败卡（`turnFailed`）不记作最终回复。
- 第一行：daemon 兜底投递的正文（去掉重启恢复提示那一行），或 `botmux send --response-kind final` 记在 turn-sends
  里的预览。匿名只读面板去掉它。
- 只用 `botmux send` 且没带 `--response-kind final` 的轮没有最终回复回执，记 `no_output`（宁可显示空闲也不猜已交付）。

## 会话控制页看板

| 列 | 进来的会话 |
|---|---|
| 待办池 | 手动放进来的、停起未开始（queued）的 |
| 待办 | 没做完、空闲 |
| 进行中 | 进行中 |
| 需要你 | 需要你（任一原因） |
| 已完成 | 本轮已交付、已关闭（已关闭置灰） |

- 手动拖动记下放置时刻 `kanbanColumnAt`，只管到下一次任务状态变化：新消息、开始新一轮、一轮结束、举手
  （`taskStatusChangedAt` 晚于放置时刻即失效）。自动压缩刷新的最近消息时间被本轮结果的 `heldThrough` 盖住，
  不算新消息（没有仍有效的本轮结果时无从续期，仍按新消息算）。没有放置时刻的手动列来自升级之前：那时的最近消息时间
  一定晚于拖动，不拿来比，只在升级后第一次开跑、一轮结束或举手时失效。
- 待办池只管到会话开始：开跑（运行态忙、`busySinceAt` 或本轮结果晚于放置时刻）即失效。
- 两处仍会暂时放开、回到空闲后恢复：自动压缩自己那段忙碌仍记 `busySinceAt`，压缩跑着时手动列失效、agent 的举手
  被盖过（要给阈值和空闲两种压缩都补进行中标记才能区分）；待办池按运行态判断，保活那几秒卡片也会暂时离开待办池。
- 休眠会话照旧不上看板，只有最近一轮在 24 小时内结束的例外；仍有效的手动放置也留在看板上。
- 卡片上一行写状态：「需要你」写原因，「进行中」写已运行多久，「已交付 · 12 分钟前」下面写最终回复第一行，
  「没做完」写还剩几项。表格、概览计数、状态色条用同一套推导；状态筛选按任务状态，旧的运行态筛选值
  （analyzing、stalled 等）映射到对应任务状态。

## 决策看板（第二个 PR）

### 群状态

管家 daemon 对事项关联的每个群（排除管家群）读本机所有 bot 在这个群里的会话，逐个用上面的推导，再合成群状态：

| 群状态 | 条件 |
|---|---|
| 没有会话 | 本机没有任何 bot 在这个群里开过会话 |
| 已关闭 | 有会话但都已关闭 |
| 需要你（原因） | 任一会话需要你（中断以外的原因优先） |
| 本轮中断 | 任一会话本轮中断 |
| 进行中 | 任一会话进行中 |
| 读不到 | 以上都不是，且有会话读不到（所属 daemon 不在线、接口失败） |
| 本轮已交付 | 任一会话本轮已交付（取最近的一个：时间 + 第一行） |
| 空闲 | 其余 |

本 bot 的会话直接读内存；其他 bot 的会话用 daemon 之间已有的 `GET /api/sessions/:id`（本机 HMAC）读，读不到就是
「读不到」，不猜。只看本机现在配置着的 bot：已经移除的 bot 留下的会话库里还有「开着」的会话，却没有 daemon
会回答，不过滤会让群永远停在「读不到」。

等你选、待选仓库、额度受限、长时间无进展这几种「需要你」没有发生时刻，在群状态里照样显示，但自己出不了提示；
这时用同群其他会话的结果算提示（本轮中断优先；没有会话在跑、也没有读不到时才用已交付），不让它们挡掉别的会话的结果。
它们也不在需求列出的提醒触发事件里（一轮结束、举手、中断），所以没有为它们各补一个时刻字段。列表行和详情：单群写状态、时间、第一行和群链接；多群写汇总（「3 个群：1 进行中 · 2 已交付」）。
「进行中」视图里，群里有新结果（结果时间晚于管家最后一次更新这一项）的事项排在前面。

### 提示与提醒

- 新提示「子任务已交付」「子任务等人处理」「子任务中断」：群里有新结果、且管家还没在这之后更新过这一项时显示。
  只是提示，不改事项状态；管家一更新这一项就消失。
- 提醒是事件驱动的：任一 daemon 记下本轮结果或举手时，按群通知本机开着「子任务提醒」的管家 daemon
  （本 bot 直接调用，其他 bot 走本机 IPC）。通知只带群 ID，管家自己重新读状态，不信任通知内容。
  举手按举手时刻判断是不是新的一次，和提醒的去重 key 一致：之前没有举手、agent 又举了一次、清掉后再举、
  后一轮又失败（在这次举手之后才开始的那一轮投递失败，用自己的时刻）都发；同一次举手反复推送不发：最终回复投递
  每隔几秒的重试（包括新一轮开始后更早一轮的记录还在重试）、期间别的信号再推补丁、原因变了但时刻没变。
- 防抖：管家收到第一个事件后等 2 分钟再统一核对，期间同一群、不同群的事件合进同一轮；核对时状态已经变了
  （比如又开始跑了）就不提醒。
- 去重：提醒 key = `task:<结果类型>:<会话>:<turnId 或举手时刻>`，按事项记在单独一列（不挤占现有提示的 key 历史）。
  同一次交付只提醒一次；管家在结果之后更新过这一项就不提醒。「管家最后一次更新」取
  `max(createdAt, updatedAt, stewardEventAt)`：`updatedAt` 只有管家的写入会动（改任何字段、记历史），
  巡检标提示、owner 提交决定都不动它。
- 一轮核对出的所有条目合成一条，经现有 `deliverHintNotice` 送进管家会话；送不出去撤销「已提醒」并稍后重试，
  沿用现有的投递次数上限。
- 管家设置里单独一个开关「子任务提醒」，默认关（新增的主动提醒，不改变现有管家的行为），只在打开时写盘；
  与「自动发现可以关的项」互不影响。
  开着时 `botmux board guide` 多一小节，说明收到这种提醒怎么处理。
