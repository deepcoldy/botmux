## 0. 摘要

### 0.1 改什么

维护者看了演示后提出：工作流现在只能在飞书话题里编排，不符合预期。要做四件事：

1. **在 Dashboard 上编排**：Dashboard 有「新建工作流」入口。先选编排 Bot（主 Bot），再填目标；需求澄清、spec、流程图都在页面上完成；每个节点可以选执行的 Bot；两道人工确认也在页面上点。编排完点「拉群开始」：建话题群，拉进编排 Bot、各节点的执行 Bot 和发起人，在群里开主话题启动 run，之后按现有的群内交接执行。飞书里的 `/workflow` 入口保留。
2. **复用**：跑完的工作流可以保存成模板（现有的 Saved Workflow），在 Dashboard 上列出来，填参数后一键再跑。
3. **基于历史创建**：从历史 run 或已保存的工作流复制一份，改目标、节点、执行 Bot、参数后，存成新模板或直接启动。
4. **身份和权限**：在 Dashboard 上发起的人就是发起人（用 Dashboard 或平台的登录身份）；谁能看到、使用哪些工作流，能选哪些 Bot，按 Dashboard 现有权限来；平台部署（m- 域名）下也要能用。

### 0.2 一句话方案

编排的状态机（需求澄清 → spec → 流程图 → 两道确认）本身不依赖飞书，依赖飞书的只有三处：发起人身份只能从当前飞书回合取得、run 与群的绑定只在创建时产生、模型和人对话靠 `botmux send`。本设计把这三处换成 Dashboard 版本：

- 身份：Dashboard 请求的登录身份，由主 Bot 的 daemon 换成主 Bot 应用视角的 open_id。
- 绑定：先建一个**没有群的草稿**，两道确认都记在草稿上；点「拉群开始」后才建群、开主话题、补齐绑定，再写 `run.json` 并启动。`run.json` 仍然只写一次。
- 对话：需求澄清用主 Bot 的一个**无飞书会话**（headless 会话）在 Dashboard 页面里一问一答；拉群后把这个会话迁进主话题，主 Bot 带着澄清时的上下文继续工作。

### 0.3 待确认与已定

- 第 11 节列出 13 个身份 / 权限 / 审批相关的选择，每个都写了推荐，等维护者确认后再实现对应部分。
- 其余选择（第 12 节）按推荐直接做。
- 贯穿全系列的原则同样适用：只有模型确实要用别人的身份、手上又没有时，才停下来要权限；不在批准、交接、派发环节提前卡住用不到身份的节点。

## 1. 现状和缺口

| 环节 | 现在怎么做 | 缺什么 |
|---|---|---|
| 入口 | 飞书话题里 `/workflow <目标>`，daemon 把它改写成「先读 botmux-workflow skill」交给主 Bot 的会话 | Dashboard 没有入口 |
| 需求澄清 | 主 Bot 的模型按 skill 用 `botmux send` 一问一答，没有独立 worker | Dashboard 上没有和 Bot 对话的面板；无飞书话题的会话里 `botmux send` / `botmux ask` 都会被拒 |
| 发起人身份 | `workflow new` 从当前飞书回合认人，写进 `chatBinding.ownerOpenId`，之后不能改 | Dashboard 请求没有「当前飞书回合」 |
| run 与群绑定 | `workflow new` 时产生，`approve-dag` 冻结进 `run.json`；daemon 启动要求有绑定 | 不能先编排、后建群 |
| 两道确认 | 用户在话题里回复「确认」，模型执行 `approve-spec` / `approve-dag`；代码只校验「本轮是发起人开的」 | 页面上没有确认按钮；`authorizedByOpenId` 实际记的是 grill 发起人，不是点确认的人 |
| 节点选 Bot | Architect 按群里当前可用的 Bot 名单分配（#2728），名单要求 Bot 已在群里 | 群还没建时没有名单 |
| 建群 | CLI `create-group` 支持话题群、写 Bot 间协作授权，但只拉建群 Bot 的第一个管理员、不能按 union_id 拉人；Dashboard 的建群接口能按 open_id 或 union_id 拉人、转让群主，但不支持话题群、不写协作授权 | Dashboard 建群接口补话题群模式和协作授权 |
| 开主话题 | 没有现成接口；建群时的 kickoff 消息不能 @ 主 Bot 自己 | 参照决策看板的做法：daemon 发一条消息作为话题根，起一个绑定该话题的会话（本设计用卡片，见 4.5） |
| Dashboard 工作流页面 | 运行列表、详情、流程图、取消（`/api/v3/runs*`）；只列出已开始的 run | 没有草稿、没有启动接口、没有模板页面 |
| 模板 | Saved Workflow：只能把自己发起、同群、已结束的 run 原样保存（参数为 0）；`--distill` 能提取参数但只支持 Linux 上的 claude-code；保存、追加、列表、运行四个入口都要求有群上下文；没有 Dashboard API | 列表、详情、带参数运行、手工声明参数都要补；服务层要加「没有群上下文」的调用形态 |
| 复制历史 | 没有入口 | 底层零件有（把 run 转成模板草稿的纯函数、草稿校验、追加版本），要新加包装 |

调研中顺带确认的几个事实：

- Architect 现在由 CLI 进程直接起一次性 worker，整段持锁，最长 10 分钟。
- 「拉新群带管家」（#2291）会把管家静默拉进新群；Architect 的 Bot 名单没有排除管家，管家可能被分到节点。
- 平台 m- 域名上，Dashboard 页面的请求只带平台注入的 actor（union_id）和 scopes，不带 role；带 role 的只有 `/s` 终端子域（`host-terminal.ts` 的说明和对应用例）。机器端遇到不带 role 的请求，会把它当成本机管理身份，而且不记录登录用户的 union_id（`request-identity.ts` 的 legacy 分支）。定时任务已有绕法：确认请求来自平台隧道后，读平台注入的原始 `X-Botmux-Actor`。
- 非 owner 的登录用户能否经平台到达某些路径（例如结果页），取决于平台侧是否按路径放行，本仓库里无法确认。`/plugin-result` 的登录链（`/open/<machineId>?next=/plugin-result-access/...`）是按「非 owner 的登录用户能到达、机器端再按 union_id 卡资源」设计的。**如果平台并不按路径放行**，群内 Bot 接力设计 §11.3 的群友精简视图和 `/plugin-result` 的非 owner 访问，在平台部署下都到不了。这一点需要平台侧确认；本 PR 把 §11.3 的表述同步写成条件句。

## 2. 名词

| 名词 | 含义 |
|---|---|
| 草稿 | Dashboard 上还没拉群开始的工作流。有 runId 和 run 目录，状态从需求澄清走到两道确认；没有 `run.json` |
| 编排 Bot / 主 Bot | 负责需求澄清、Architect、拉群、主话题里的进度和运行中调整的 Bot |
| 执行 Bot | 某个节点交给的 Bot |
| 发起人 | 在 Dashboard 上创建草稿的人，存成主 Bot 应用视角的 open_id 加 union_id |
| 澄清会话 | 主 Bot 为这个草稿起的无飞书会话，页面上的对话面板就是它 |

| 模板 | 现有的 Saved Workflow 定义及其版本 |

## 3. 整体流程

```text
Dashboard「新建工作流」
  │ 选编排 Bot、填目标
  ▼
草稿（runId，无群）── 澄清会话（主 Bot 的无飞书会话）
  │ 页面对话面板一问一答
  ▼
spec 预览 ──［确认需求］(第一道确认，发起人点)
  │
  ▼
Architect（主 Bot 的 daemon 后台跑，按「计划中的群」给节点分配 Bot）
  │ 流程图 + 每个节点的执行 Bot（可改）
  ▼
［确认流程］(第二道确认，发起人点；记下确认时的流程摘要)
  │ 填群名、可选的额外成员
  ▼
［拉群开始］
  ├─ 记下建群意图（群名带标记）
  ├─ 建话题群，拉编排 Bot、执行 Bot、发起人（不发 kickoff）
  ├─ 主 Bot 发卡片作为主话题根
  ├─ 澄清会话迁进主话题
  ├─ 实时检查执行 Bot
  ├─ 给通过检查的执行 Bot 写协作授权
  ├─ 写 run.json（发起人、确认时间、流程摘要）
  └─ 启动 run
  ▼
群内交接执行（与飞书里发起的 run 完全一样）
```

飞书里的 `/workflow` 走原来的路径，两条入口产出的 run 在执行期没有区别。

## 4. Dashboard 上的编排

### 4.1 入口和选编排 Bot

- 入口：工作流页面标题区的「新建工作流」按钮，路由 `#/workflows/new`；草稿页 `#/workflows/drafts/<runId>`。现在 `#/workflows/<任意段>` 都会被当成 runId，所以 `new`、`drafts`、`library` 三个段要在路由表里排在运行详情之前，并在解析 runId 时排除。
- 编排 Bot 下拉框列出本机配置的 Bot，每个标出能不能用：
  - CLI 不支持工作流节点的（例如 pi、cursor、opencode），关了 CLI bypass 的，配了 Codex profile 的：不能选，写明原因；
  - 管家 Bot（decision-board 管家开关打开即算，不要求选了管家群，`isStewardBot`）：不能选；daemon 的建草稿接口在 `birthRun` 之前直接拒绝（`orchestrator_ineligible`），不建 run 目录、不起澄清会话；
  - daemon 不在线：不能选；
  - 发起人不能操作这个 Bot（第 11 节 I1）：不能选。
- 项目：选完编排 Bot 后出现。Bot 有默认目录（`effectiveDefaultWorkingDir`）就直接显示「项目：<目录>」；没有就必须从下拉里选一个，候选和飞书仓库选择卡一样（扫 Bot 的工作目录，列不列 worktree 跟 `repoPickerMode`）。daemon 建草稿时按同样的范围再校验一次，不接受任意路径，存进 draft.json 的 `projectDir`。澄清会话、「继续」、换编排 Bot 后的新会话、运行模板时主 Bot 的会话都开在这个目录，不再退回 daemon 自己的进程目录。运行模板和复制为新工作流也一样选项目。拉群开始后，没有默认目录的节点 Bot 也在这个项目里起节点会话（7.3 的 `nodeProjectDir`）。
- 目标：一个多行输入框。

前提：工作流总开关和「节点交给群里的 Bot 执行」开关都要开。只开了总开关时，入口提示「Dashboard 编排需要打开『节点交给群里的 Bot 执行』」，不进入编排。

### 4.2 需求澄清：页面里的对话面板

- **会话**：点「开始」后，主 Bot 的 daemon 创建草稿和一个无飞书会话（现有的 headless 会话能力）。页面上的对话面板每发一条消息就是会话里的一轮，回复取这一轮的最终输出。页面按运行详情页现有的方式轮询刷新：`/events` 里没有工作流相关的事件，第一版不新增。
- **提示词**：用一份 Dashboard 版的澄清提示，和现在的 botmux-workflow skill 共用规则（一次一问、给推荐答案、凑齐每个节点的要素、用户随时可以说「够了」），区别只有两点：
  - 不用 `botmux send` / `botmux ask`，问题直接写在这一轮的最终输出里；
  - 不运行任何 `botmux workflow` 命令。需要定稿时，在输出里给出 spec（和现在 spec.md 的格式一样），由 daemon 读取。
- **问题的展示**：输出里如果带一个约定格式的问题块（问题、选项、推荐答案），页面渲染成选项按钮，点了就作为下一轮发出去；没有问题块就按普通文字展示。用户也可以直接打字。
- **状态推进由 daemon 做，不由模型做**：模型只负责对话和产出 spec 文本。草稿状态的每一次变化（spec 定稿、确认、Architect、改 Bot、退回）都是 Dashboard 调主 Bot daemon 的接口完成，身份是 Dashboard 的发起人。这样不需要让无飞书会话里的命令去认「当前回合是谁」。
- **澄清会话的生命周期**：
  - 会话记录随草稿一起落盘。daemon 重启后不主动拉起进程；下一次在页面上发消息时，按这个会话记录的 CLI 会话 id 恢复（与普通会话重启后的恢复同一机制）。恢复不了时按第 9 节「会话已断开」处理。
  - 草稿 30 分钟没有新消息就关掉 CLI 进程，会话记录保留，下次发消息时再恢复，避免挂着的草稿长期占进程。
  - 拉群开始后会话迁进主话题（4.5），之后由主话题会话的生命周期管理。
  - 草稿放弃或删除时，关闭进程并删除会话记录。

### 4.3 spec 和第一道确认

- 模型给出 spec 后，daemon 用现有的 spec 校验写出 spec.json；校验不过时把问题列表显示在页面上，并作为下一轮发给模型修改。
- 页面并排显示 spec（标题、目标、每个节点的要素、默认值、未定的点），可以直接改文本再「重新校验」。
- 「确认需求」按钮：只有发起人能点（I6），对应现有的 approve-spec。
- 「退回修改」：回到对话面板。

### 4.4 流程图、节点选 Bot、第二道确认

- **Architect**：由主 Bot 的 daemon 在后台跑，页面显示「正在编排」和已用时间，可以取消。现在 Architect 由 CLI 进程起，整段持锁；改成 daemon 后台任务后，锁和超时规则不变。
- **计划中的群**：群还没建，Bot 名单按「这些 Bot 会被拉进一个话题群」来判断：
  - 建群前就能判断的照常判断：CLI 是否支持、bypass、Codex profile、是否配置在本机、daemon 是否在线、显示名 / CLI / 模型 / 能力说明、用户点名能否解析、节点是否有目录型产出；
  - 话题群里所有 Bot 都能开话题会话，这一项直接通过；
  - 「是否在群」「协作授权」留到拉群时实测（4.5）。
  - 管家 Bot 不进名单。飞书入口（#2728）的名单现在没有排除管家，D2 改成两个入口共用同一条排除规则，避免两条入口分到的 Bot 不一样。这对飞书入口是一处小的行为变化，只影响打开了「节点交给群里的 Bot 执行」开关的部署（默认关），管家本来就不该执行节点。
- 编排 Bot 本身也不能是管家：D2 的建草稿接口（`WorkflowDraftService.create`）按与名单同一个 `isStewardBot` 判定在创建前拒绝。这条拒绝只作用于 Dashboard 草稿入口；飞书 `/workflow new` 入口 D2 刻意不改——管家 Bot 仍可作为主 Bot 在飞书发起 run，其节点按默认选择器落在它自己身上，「管家不执行节点」在飞书入口只体现在上面那条节点名单排除。若以后要让飞书入口也禁止管家当主 Bot，作为独立改动评估。
- **流程图**：复用运行详情页的流程图组件（要导出），每个节点显示执行 Bot 和 Architect 写的理由。点节点可以：
  - 换执行 Bot：下拉框只列名单里能用的 Bot，不能用的标出原因（例如「pi：CLI 不支持工作流节点」）；
  - 看节点要素。

  换 Bot 写回草稿的流程定义并重新校验；用户点名过的节点被换掉时标 ⚠️。
- **退回**：「重新编排」（给 Architect 补一句说明后重跑）、「退回改需求」（回到 4.2）。
- **「确认流程」**：只有发起人能点（I6）。点下时记录确认人、确认时间和当时的**流程摘要**；之后流程定义再有任何改动，这次确认作废，要重新确认。
- **流程摘要**（确认、4.5 第 7 步写 `run.json` 前的核对、5.1 保存模板、7.3 授权段记录里的「摘要」都指这一份；4.5 第 4 步迁入后在主话题发的那条「摘要」是给人看的进度消息，不参与比对）由三部分组成：
  - 节点 → 执行 Bot（CLI）：理由，用户点名没满足的标 ⚠️（与现在的 Gate-2 摘要相同）；
  - 对外动作清单：每个宿主动作节点及其动作类型（与模板里的 `sideEffects` 同口径，`computeSavedWorkflowSideEffects`）；
  - 人工确认清单：每道 Gate 的位置和审批规则（与模板里的 `gateDigest` 同口径，`computeSavedWorkflowGateDigest`）。

  页面展示这三部分；记录时存三部分的规范化内容和它的哈希。

### 4.5 拉群开始

确认流程后，页面显示群设置：群名（默认取工作流标题）、可选的额外成员（按邮箱或从成员列表选）。点「拉群开始」后，主 Bot 的 daemon 依次执行：

1. **记下建群意图**：先在草稿目录里落盘「要建群」的意图（群名、成员），再调建群接口。群名末尾带草稿 runId 的随机段作为标记：runId 形如 `<目标 slug>-<时间戳>-<8 位随机十六进制>`（`mintV3RunId`），标记取最后那 8 位随机段（例如 runId 为 `...-a1b2c3d4` 时标记是「#a1b2c3d4」）。不能取 runId 的前 8 位——那是目标 slug 和日期：中文目标的 slug 恒为 `run`，同月所有中文草稿前 8 位都是 `run-2611`，同标题的草稿也会相同，按它反查会认回别的草稿建的群；随机段才是跨草稿唯一的防撞部分。标题过长时只截标题、不截标记。
2. **建群**：话题群模式，建群 Bot = 主 Bot，建群时不发任何 kickoff 消息，所以万一留下孤儿群，里面也不会唤起任何 Bot。拉进各节点的执行 Bot、发起人和额外成员，发起人设为群主（I7）。发起人按两条通道之一加入，不混用：
   - 拿到了发起人的 union_id（平台登录）：走建群接口的 `ownerUnionIds` + `transferOwnerUnionId`；
   - 本地 token 登录：发起人就是主 Bot 的 owner，取 `getOwnerOpenId`（配置的 owner 还在管理员名单里就用它，否则取名单里的第一个），走 `userOpenIds` + `transferOwnerTo`，与 CLI 建群现在的做法相同。

   「拉新群带管家」按现有规则执行。
3. **开主话题**：主 Bot 在群里发一张卡片作为主话题根：工作流标题、发起人、节点数，签名行带侧边栏入口。决策看板「Dashboard 发起 → 群里开话题」的先例发的是文本横幅；这里要放按钮，所以用卡片。话题群里的顶层消息本身就是话题根，不靠 Bot @ 自己。
4. **迁入澄清会话**：把澄清会话迁进主话题（现有的 headless bind 能力），主 Bot 在主话题里保留澄清时的上下文，之后的运行中修改和事件唤醒都在这个会话里。迁入后在主话题发一条摘要：目标、确认过的 spec 要点、流程图链接。
5. **实时检查执行 Bot**：在群、daemon 在线、能开话题会话（群内 Bot 接力 #2710 的批准前检查，这里只检查、不写授权）。有 Bot 没拉进来或不合格时，停在这一步，页面列出原因，用户可以给该节点换 Bot 后重试，或者重试拉人。
6. **写协作授权**：只给通过第 5 步检查的执行 Bot 写主 Bot 与它之间的群内协作授权（现在 CLI 建群和 approve-dag 已有同样的调用）。授权写入是幂等的，续做时重写一遍即可。授权放在检查之后，是为了换 Bot 时不给被换掉的 Bot 留下授权；如果某个 Bot 在之前的尝试里已经写过授权、后来被换掉，换 Bot 时显式撤销它在这个群的授权（撤销不要求它还在群里）。
7. **写 `run.json`**：绑定（主 Bot、群、`chatType: group`、主话题根、会话、发起人），授权段记发起人和第二道确认的时间与摘要（第 7.3 节）。写入前核对：当前流程定义的摘要必须等于第二道确认时记下的摘要，不等就回到 4.4 重新确认。
8. **启动**：与 `workflow start` 相同的启动路径。

**断点续做**：这是一串多步写入。每一步完成后都记进草稿目录里的拉群记录：群 id、主话题根消息 id、迁入结果、检查结果、协作授权结果、`run.json` 摘要。任何一步失败或 daemon 重启后，再点「继续」从记录的位置往下做：
- 已有群 id：不再建群；
- 有建群意图、没有群 id（建群已成功、记录落盘前崩溃）：先按群名标记反查主 Bot 所在的群，找到就认回这个群继续，找不到才建。
  - 前半照搬「拉群领取 issue」流程：建群前意图先落盘（`recordClaimIntent`）、群名带标记（`claimMarker`）、建群时不发 kickoff。
  - 后半「按标记认回」仓库里还没有实现：那个流程的对账只写在注释里，意图读取函数在生产代码里没有调用方。D4 要新写这段对账：用 `listChats` 列出主 Bot 所在的群，按群名末尾的标记匹配。
- 已有主话题根消息 id：不再发；
- `run.json` 已写：直接走启动（启动本身是幂等的）。

反查不到、但其实已经建过的极端情况（例如标记被人改掉），页面列出「可能留下的孤儿群」，由人手动处理。已建好的群在页面上给出链接。用户也可以「放弃」：草稿标记为放弃，已建的群保留，在主话题根卡片上写明「这次启动已放弃」。

### 4.6 草稿列表

- 工作流页面新增「草稿」分组，列出本机所有未启动的草稿：标题、编排 Bot、发起人、状态（澄清中 / 待确认需求 / 编排中 / 待确认流程 / 拉群中 / 已放弃）、更新时间。
- 草稿只有发起人能继续操作；其他人能看、能复制（第 6 节）。
- 超过 30 天没有动静的草稿标灰，提供「删除」；不自动删除。

## 5. 模板（Saved Workflow）

### 5.1 保存

- **从结束的 run 保存**：运行详情页加「保存为模板」。默认原样保存（与飞书里 `/workflow save` 一样），保存的是最终生效的流程版本（运行中修改合入后）和实际执行节点的 Bot（受阻卡改派过的按改派后的 Bot），页面上标出哪些节点的 Bot 与批准时不同。
- **从草稿保存**：草稿通过第二道确认（「确认流程」）之后，可以「存为模板」，不需要先跑一遍。保存时再展示一次 4.4 定义的流程摘要，记下确认人、时间和摘要。没有通过第二道确认的草稿不能存成模板。
  - 背景：现在飞书里保存的模板版本都来自已批准、已结束的 run（保存只在 Gate-2 已批准时放行，是否发布由 run 是否成功结束决定），「已发布的版本 = 批准过的流程」是代码结构保证的。从草稿保存是新的写入口，所以要把确认人和确认时的摘要写进模板版本。
  - 这需要把模板版本格式从 v2 升到 v3：新增的确认信息不能塞进 `gateDigest`（它是按流程重算校验的推导字段），也放不进 `run.json`（模板运行的授权段没有确认人位置）。老版本走只读迁移、字节不变；新版本的 id 是内容哈希，会因为多了字段而变化。这是 D5 的前置项。
- **谁能保存**：只能把自己发起的 run 或草稿存成模板、给自己的模板追加版本；模板的 owner 就是保存它的人（I9）。想基于别人的 run 或模板，先「复制为新工作流」（第 6 节），复制出的草稿归复制者，再保存。
- **可见范围**：Dashboard 保存的模板默认全局（同一编排 Bot 在所有群都可见），因为 Dashboard 发起的 run 每次都在新群里，「本群」范围没有意义（I9）。
- **人工确认的变化**：追加版本时，与上一版比较人工确认（Gate）的数量和位置；少了的在保存确认框和版本历史里明确标出「比上一版少了 N 道人工确认」（I10）。现在的 gateDigest 只防同一版本内被改，不比较前后版本，这里补上比较和展示。

### 5.2 参数

- **手工声明**：保存时可以选中目标 / 节点目标里的一段文字「设为参数」，填参数名、类型（文本、数字、是/否）、默认值、说明；页面把选中的文字替换成 `${params.名字}`。参数只能出现在现有规则允许的位置（节点目标、追加提示、宿主动作的输入），人工确认、拓扑、Bot 字段里不允许，页面不提供这些位置的「设为参数」。
- **自动提取**：现有的「提取参数」（`--distill`）作为可选按钮保留，只在满足它现有条件（Linux 上的 claude-code 编排 Bot）时出现。
- 标为「敏感」的参数现在不能执行，保持不变，页面不提供「敏感」选项。

### 5.3 列表和一键再跑

- `#/workflows/library`：模板列表，显示名称、编排 Bot、最新版本时间、owner、参数个数、节点数、人工确认数；可按 Bot 和关键字筛选。详情页显示流程图、参数说明、版本历史。
- **owner 的含义**：模板 owner 是保存它的人，负责后续版本；每次运行的发起人是点「运行」的人，run 上的改派、运行中修改确认等发起人权利归他。列表和详情里两者分开显示。
- **再跑**：「运行」按钮打开参数表单（按参数声明生成，必填项校验、类型转换沿用现有规则），下面是群设置（同 4.5）。点「拉群开始」按 4.5 的步骤执行，区别是不经过澄清，也不再经过两道确认，与飞书里 `/workflow run` 一致（I13）：
  - 来源是已结束 run 的模板版本：直接运行，`run.json` 不带确认记录；
  - 来源是草稿的模板版本：同样直接运行（Dashboard 和飞书都可以）。保存时的第二道确认（确认人、确认时间、流程摘要）原样写进这次运行 `run.json` 的授权段，确认人是保存时确认的人，不一定是这次的发起人。
- **群范围的模板**：飞书里存成「本群」范围的模板，在 Dashboard 上能看到，但只能在原群里用 `/workflow run` 运行，Dashboard 不提供「运行」（保持它现在的范围规则）。
- 运行前检查同 4.5 第 5 步，不合格时停下列出原因，可以给节点换 Bot：换了 Bot 就不再是「按模板原样运行」，转成第 6 节的「复制后启动」，要求确认流程。
- 「在已有群里运行」不在第一版里，飞书里 `/workflow run` 已经能做。

## 6. 基于历史创建

- **来源**：任意历史 run（不要求已结束），或任意模板的任一版本。入口：运行详情页和模板详情页的「复制为新工作流」。
- **来源 run 还没结束时**：取复制那一刻已生效的流程版本（运行中修改以运行记录里已生效的为准），草稿上标注「来源 run 尚未结束，复制的是复制时的版本」。读取来源 run 走单独的只读入口（现在加载 run 的函数只接受指定的几类来源），不改动来源 run。
- **复制出什么**：一个新草稿，spec 和流程都已预填，处于「待确认需求」：
  - spec 和流程定义复制过来（run 取最终生效的版本；模板版本取它的定义，参数保留为参数）；
  - 每个节点的执行 Bot 取实际执行过的 Bot（run）或模板里写的 Bot；
  - 编排 Bot 默认与来源相同，可以改；
  - 不复制运行记录、产物、澄清会话。
- **可以改什么**：
  - 目标：改了目标可以选「按新目标重新编排」（重新澄清或重跑 Architect）或「只改文字」（保留流程）；
  - 节点：改节点目标、完成标准；增删节点和改依赖在第一版里通过「退回改需求 → 重新编排」完成，页面不提供拖拽编辑；
  - 执行 Bot：同 4.4；
  - 参数：同 5.2。
- **之后**：「存为模板」（新模板；如果来源就是自己的模板，也可以追加为新版本），或「确认需求 → 确认流程 → 拉群开始」直接启动。复制出来的草稿也要经过两道确认，因为内容可能已经改过；确认需求时不重跑 Architect，直接用预填的流程。
- **实现**：新增一个「从来源生成草稿」的操作，把复制来的 spec 和流程定义写进草稿目录，经现有的 spec 校验和流程定义校验后，草稿状态设为「待确认需求」，并记下预填流程。确认需求后直接进入「待确认流程」，跳过 Architect。这样 `run.json` 的来源仍然是现有的「即兴 run」，不用新增来源类型。

## 7. 身份与权限

### 7.1 发起人身份从哪来

| Dashboard 登录方式 | 能拿到的人的标识 | 处理 |
|---|---|---|
| 本地管理 token（个人部署最常见） | 没有 | 按 I2：算作编排 Bot 的 owner 发起（`getOwnerOpenId`，多个管理员时规则同 4.5 第 2 步），页面和 run 记录标明「本地登录，以 Bot owner 身份发起」 |
| 平台（m- 域名） | 平台注入的 union_id（按定时任务的做法，确认请求来自平台隧道后读取，I4） | 主 Bot 的 daemon 把 union_id 换成主 Bot 应用视角的 open_id |
| 飞书 H5 免登 | H5 应用视角的 open_id，可能带 union_id | 第一版不能编排（I5），只能用侧边栏查看 |
| 平台桌面端 / 移动端 | 平台桌面端 / 移动端是否放行 `/api/v3/*` 需平台侧确认；桌面端请求不带用户标识 | 第一版不支持（I12） |

换算：只用主 Bot 自己的凭证调现有的 union_id → open_id 接口，结果分三种：拿到、确定拿不到、临时失败。确定拿不到按 I3 处理；临时失败提示稍后重试。不把其它应用视角的 open_id 拿来用。

### 7.2 谁能做什么

| 操作 | 规则 |
|---|---|
| 看工作流页面（运行、草稿、模板） | Dashboard 管理员（与现在 `/api/v3/runs` 一致） |
| 新建草稿 / 选某个编排 Bot | Dashboard 管理员，且发起人对该 Bot 有操作权限（I1） |
| 在草稿上对话、确认需求、确认流程、拉群开始、放弃 | 只有该草稿的发起人（I6） |
| 选执行 Bot | 4.4 的名单规则；不另加按人的限制 |
| 存模板 / 追加版本 | 只能存自己发起的 run 或草稿、给自己的模板追加版本（I9） |
| 运行模板 | 全局范围的模板：Dashboard 管理员，且对模板所属的编排 Bot 有操作权限；群范围的模板只能在原群里运行（I9） |
| 复制为新工作流 | Dashboard 管理员；复制者成为新草稿的发起人 |
| 群里的审批卡、阻塞卡 | 与飞书里发起的 run 一样：能操作主 Bot 的群成员，加上节点指定的审批人（I8） |
| 改派、运行中修改的确认 | 只限发起人（沿用群内 Bot 接力设计 §13） |

「Dashboard 现有权限」实际只分管理员、工作台、匿名几档，不按人区分资源。本设计按这个现状来：能进工作流页面的就是管理员；按人的限制只加在「用哪个 Bot」上，规则复用飞书里已有的「能不能操作这个 Bot」判定，不另造一套。

**这些规则都在主 Bot 的 daemon 接口里校验**，不只靠页面按钮。Dashboard 本身不按人区分，任何管理员换个接口都能发请求，而确认人还要写进 `run.json`。所以每个草稿写接口（对话、确认、改 Bot、拉群、放弃、存模板）都由 Dashboard 经宿主签名转发到主 Bot 的 daemon，带上已认证的发起人身份（与 Dashboard 定时任务创建人的转发方式相同），daemon 侧比对草稿记录的发起人，不一致就拒绝。页面上的禁用只是展示。

### 7.3 run 上记录什么

`run.json` 的授权段新增：

- `initiator`：主 Bot 应用视角的 open_id、union_id（有就记）、来源（`dashboard-local` / `dashboard-platform` / `feishu`）；
- 第二道确认的确认人、时间、确认时的流程摘要（现在的 `authorizedByOpenId` 记的是 grill 发起人，这里改为如实记录确认人；飞书入口仍由模型执行 approve-dag，确认人记为当前回合的人）。

`run.json` 的结构是严格校验的，新字段会让旧版本 daemon 拒绝驱动这些 run，与群内 Bot 接力设计 §15.3 的口径一致。

另在顶层记 `nodeProjectDir`：草稿的项目（4.1），普通拉群和运行模板都写。没有默认目录的节点 Bot 在它里面起会话，目录范围和发起人操作权按群内 Bot 接力设计 §15.4 同一条规则判定，不通过就受阻；有默认目录的照旧。只有除主 Bot 外的每个执行 Bot 的 daemon 都声明能读它（`workflowNodeProjectDir: "v1"`）时才写，否则不写、节点按原来的目录规则执行（§15.3）。编排 Bot 有默认目录时，项目就是这个目录。

### 7.4 平台部署

- m- 上 Dashboard 页面的请求不带 role，机器端把它当成本机管理身份，所以能到达 m- 的人（至少是机器 owner 和协管者）能用全部工作流页面。发起人身份按 I4 从平台隧道注入的 union_id 取得。
- 群友（非 owner、非协管者）能否经 m- 看侧边栏或运行页，取决于平台是否按路径放行（见第 1 节），需平台侧确认和跟进，不在本系列里。

## 8. 与现有流程的关系

- 飞书里的 `/workflow`、`/workflow run`、`/workflow save` 不变。
- Dashboard 发起的 run 在执行期与飞书发起的完全一样：交接、回报、看板、侧边栏入口、运行中修改、改派。
- 在飞书里保存的模板在 Dashboard 上也能看到、能运行；Dashboard 保存的全局模板在飞书里也能 `/workflow run`。
- Dashboard 的建群接口只新增可选参数（话题群模式、协作授权开关），不传时行为不变；CLI `create-group` 不改。

## 9. 失败与恢复

| 情况 | 处理 |
|---|---|
| 澄清会话的 CLI 崩溃 / daemon 重启 | 草稿状态在磁盘上；先按 4.2 的生命周期规则恢复原会话；恢复不了时对话面板显示「会话已断开」，点「继续」重新起会话，把已有的 spec 草稿和最近几轮对话作为上下文带入 |
| Architect 超时 / 失败 | 回到「待编排」，显示错误，可以重跑 |
| 拉群开始中途失败 | 按 4.5 的拉群记录断点续做；建群这一步用「意图 + 群名标记」认回，不重复建群，也不重复发主话题根卡片；认不回的列为可能的孤儿群 |
| 拉群后执行 Bot 不合格 | 停在 4.5 第 5 步，换 Bot 或重试；换 Bot 后要重新确认流程，被换掉的 Bot 如已写过授权要撤销 |
| 写 `run.json` 前发现流程摘要与确认时不一致 | 拒绝启动，回到「待确认流程」 |
| 发起人在 Dashboard 上的身份失效（例如换了登录方式） | 草稿只认创建时记录的发起人；身份对不上时只能看、能复制，不能继续 |
| 澄清会话或 Architect 因编排 Bot 的模型 / 凭据失败 | 草稿页失败面板写明哪个 Bot（显示名 + CLI）、哪一步、原因分类（按错误码），附**原始报错**与**终端输出**（澄清会话给现有的只读终端链接，Architect 给日志尾部）；Bot 配置了 `model` 才顺带显示模型名，不从环境变量推导。原文落盘与展示前先做凭据形状脱敏、再截断。出路：①换一个编排 Bot 重试，目标、澄清记录、spec 候选都保留；②跳到该 Bot 的模型配置 |

**换编排 Bot（维护者 11-06 定）**

- 只在还没拉群的阶段可换（澄清中、待确认需求、编排失败）；只有草稿发起人能换；新 Bot 照常过 I1 闸、静态排除和管家排除。
- 一律放行：不比较新旧两个 Bot 的 owner 是否同一人，本地令牌登录也可以换。本地令牌登录时新发起人按 I2 记为新 Bot 的 owner；平台登录按同一个 union_id 在新 Bot 应用里换算 open_id。任何 open_id 都只在签发它的应用里使用，不跨应用复制。
- 第一道「确认需求」的确认人改写成新应用下的身份；草稿历史 `handoffs[]` 记一条交接：谁、从哪个 Bot 到哪个 Bot、何时、确认人改写前后（各自应用视角）。页面上的交接记录只写确认人改到了哪个 Bot 的应用下，不显示 open_id。
- 归属始终只看 `orchestratorAppId` 一个字段：旧 Bot 的 daemon 先关澄清会话并记下交接令牌，新 Bot 的 daemon 加锁写盘接管并带着已有对话与 spec 候选开新会话；中途崩溃时页面给「继续更换 / 取消更换」，任何时刻只有一个属主。

## 10. 对现有用户的影响

前提：工作流总开关 `workflow.enabled` 默认关；Dashboard 编排还要求「节点交给群里的 Bot 执行」开关打开（默认关）。

- **开关都没开**：Dashboard 上没有任何新入口，其余页面、接口、卡片、命令都不变。
- **开了开关、但不用 Dashboard 编排**：飞书里的使用方式不变；工作流页面多出「新建工作流」「草稿」「模板」三个入口，只读展示，不改变已有 run 的显示。
- **Dashboard 建群接口**：只加可选参数，不传时行为与现在一致。
- **飞书入口的 Bot 名单**：开了「节点交给群里的 Bot 执行」时，Architect 名单不再包含管家 Bot（4.4）。
- **`run.json`**：只有新建的 run 带新的授权字段；已有 run 照常运行。降级到旧版本 daemon 时，带新字段的 run 会被拒绝驱动。
- **模板**：模板版本格式升到 v3（新增确认信息），老版本只读迁移、文件不变；旧版本 daemon 读不了 v3 的版本。Dashboard 保存的模板是全局范围，在飞书里也能用；从草稿保存的版本在两边都可以直接运行，运行的 `run.json` 带上保存时的确认记录，旧版本 daemon 拒绝驱动这类 run。老模板运行的 `run.json` 不变。
