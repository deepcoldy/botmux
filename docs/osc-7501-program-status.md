# OSC 7501 状态协议详解与 Botmux 的 Claude 深度适配

> 💡 **一句话总结**：OSC 7501 让 AI 编程命令行（CLI）彻底告别了“靠猜终端动静判定干没干完”的原始时代。配合 Botmux 的端到端协同，Claude Code 在飞书/IM 桥接与网页终端交互中实现了**零假死、零延迟、零引用污染**的丝滑体验。

---

## 一、OSC 7501 是个啥？（用人话说）

如果你熟悉终端底层，一定知道 **OSC（Operating System Command，操作系统控制码）**。

在 ANSI 转义序列里，以 `\x1b]` 开头、以 `\x07`（BEL）或 `\x1b\`（ST）结尾的代码就是 OSC。比如：
- `OSC 0;`：用来改终端窗口的标题；
- `OSC 8;`：用来在终端文本里插超链接；
- `OSC 52;`：用来读写系统剪贴板。

而 **OSC 7501**，就是现代 AI CLI（以 Claude Code 为代表）专门为终端模拟器和外部宿主程序设计的一套**程序运行状态汇报协议（Program Status Protocol）**。

### 它长什么样？

Claude Code 在执行任务时，会在标准输出（PTY 流）中静默吐出这样格式的转义信令：

```text
\x1b]7501;state=working:id=tool_1:app=claude:msg=... \x1b\
```

它通过类似 URL 参数的方式，用冒号分隔的 `key=value` 传递状态：
- `state`：核心状态，目前支持 `idle` | `working` | `done` | `blocked` | `error` | `clear`；
- `id`：任务/子任务标识符（支持多层级，如 `tool/bash/1`）；
- `kind`：被阻塞的类别（如权限询问、工具审批）；
- `msg`：Base64 编码的状态描述信息（安全传文本）；
- `progress`：0~100 的任务进度百分比。

## 二、为什么必须有它？以前“看动静猜心思”有多折磨？

在没有 OSC 7501 之前，像 Botmux 这样的后台常驻守护程序要把终端里的 Claude Code 桥接到飞书群，必须实时判断：**“这轮任务 Claude 到底干完了没有？我该不该把结果发给用户？”**

以前只能用**启发式空闲检测（Heuristic Idle Detection）**——通俗讲就是**“隔着门板听动静”**：
1. **看屏幕动静**：终端有多久没输出新字符了？（比如静默 2 秒）
2. **看屏幕文本**：屏幕最底下是不是画出了输入提示符 `❯ ` 或 `? `？

这种“盲人摸象”的方式在复杂的真实场景下极其脆弱，经常踩中三大天坑：

| 痛点 | “猜动静”的尴尬下场 | 现实类比 |
| :--- | :--- | :--- |
| **假完成 / 抢跑（False Idle）** | Claude 正在深度思考大模型推理、跑耗时的编译、或者下载大文件，终端连续 3 秒没打字。宿主以为它完事了，提前触发结算把半截话发到飞书，结果 Claude 紧接着又输出了后半截。 | 以为人走了，刚推门进去，结果人家只是在闭目沉思。 |
| **高延迟（Latency）** | 为了防止上面的抢跑，宿主不得不加防抖：必须连续静默 2~3 秒才敢认“真的完成了”。这就导致 Claude 明明 0.01 秒前就已经彻底写完，飞书群里还要傻等 3 秒才收到卡片，顿挫感极强。 | 考卷做完交卷了，监考老师非要在考场傻站三分钟确认你没在动笔，才肯收卷。 |
| **卡住等待不可知（Blocked State）** | 当 Claude 遇到敏感命令弹窗询问 `Do you want to run this command? (y/n)` 时，终端不动了。宿主程序只能看到“没输出”，根本分不清它是死机了、在思考、还是在等待人类审批。 | 里面的人在等领导签字盖章，门外的人以为里面在开会，谁也不知道卡在哪。 |

### OSC 7501 带来的质变

有了 OSC 7501，交互模式彻底从**“宿主被动猜”**进化为**“Claude 主动报”**：
- **亮黄灯（`working`）**：我在干活，不管屏幕静止多久都不许打扰，绝不抢跑；
- **亮红灯（`blocked`）**：我需要人类审批/交互，精准上报阻塞原因，IM 侧立刻能亮灯提示“需要您介入”；
- **亮绿灯（`done` / `idle`）**：已完成！零延迟瞬间感知，立即投递消息并收尾。

## 三、Botmux 为 Claude 做的深度适配架构

Botmux 从来不做简单的“套壳”，而是针对企业级复杂多会话、长程任务协作、即时通讯多并发等严苛场景，为 Claude Code 量身打造了一整套底层支撑基础设施。

```
┌────────────────────────────────────────────────────────────────────────┐
│                              Claude Code                               │
│  (内部发出 OSC 7501 信令: working -> blocked -> done -> clear)           │
└────────────────────────────────────┬───────────────────────────────────┘
                                     │ PTY 字节流
                                     ▼
┌────────────────────────────────────────────────────────────────────────┐
│                   Botmux ProgramStatusFramingStream                    │
│  • 流式分帧 (安全拆解 \x1b]7501;... 字节序列，防止跨 chunk 截断)          │
│  • 自动握手 (响应 Claude 启动探针)                                      │
│  • 字符清洗 (过滤控制字符，Base64 解码，4KB 防爆保护)                   │
├────────────────────────────────────┬───────────────────────────────────┤
│                                    │ 提取出的结构化事件 (state, id, msg)
│ 纯净显示文本                        ▼
│ (过滤掉 7501 乱码)    ┌───────────────────────────────────────────────┐
│                      │           Botmux ProgramStatusAuthority       │
│                      │  • 权威状态机接管 (启发式正则自动靠边站)         │
│                      │  • 树形任务追踪 (多任务并发/层级 clear)          │
│                      │  • 粘性忙态保护 (淘汰记录防过早判空闲)           │
│                      │  • 启动横幅加载门控 (防冷启动瞬时早产)           │
│                      └───────────────────────┬───────────────────────┘
│                                              │ 权威空闲 / 阻塞事件
▼                                              ▼
┌──────────────────────────────┐ ┌──────────────────────────────────────┐
│     Web 网页终端 (xterm.js)   │ │      Botmux 调度内核 & Worker 线程     │
│  高保真 ANSI 颜色与排版原样呈现 │ │  • 飞书状态卡片秒级更新 ("需要您介入") │
└──────────────────────────────┘ │  • 排队轮次 (Type-Ahead) 隔离保护     │
                                 │  • 原生 CLI 发送账本与精准引用推进     │
                                 └──────────────────────────────────────┘
```

### 1. 透明流式分帧器（`ProgramStatusFramingStream`）
- **无感剥离**：如果终端模拟器不支持某个 OSC，屏幕上可能会残留转义字符乱码。Botmux 在 Worker 的 PTY 字节流中挂载了高性能流式分帧器，不仅把纯净文本送入网页终端（xterm.js）显示，还在内存中把 7501 控制指令直接接管剥离；
- **探针握手**：Claude Code 启动时会发送探针 `\x1b]7501;?\x1b\` 询问宿主环境是否支持该协议，Botmux 在底层完成标准应答；
- **极致防御**：网络包或 PTY 缓存经常会把一段转义码拆在两个不同的 chunk（数据块）里。分帧器具备完备的跨 chunk 拼包与滑动窗口机制，支持 Base64 安全解码、控制字符清洗以及 4KB 缓冲上限保护，坚如磐石。

### 2. 权威状态机接管（`ProgramStatusAuthority`）
- **一键切换权威态**：只要探测到 Claude Code 吐出了第一帧合法的 7501 状态，Botmux 的传统空闲检测器立刻交出控制权，由 Claude 的官方状态全程主导；
- **树形任务追踪与粘性忙态（Sticky Busy）**：Claude 在复杂场景下会并发执行子任务（例如调用多个 Bash/MCP 工具）。Botmux 内部维护了层级任务树；只要还有任意一个任务处于 `working` 或 `blocked`，宿主坚决保持忙碌；就算任务树达到上限淘汰了旧记录，也会保留粘性忙态，杜绝空闲误判；
- **启动横幅门控联动**：Claude Code 冷启动时常带有一段加载动画。即便协议提前报了 idle，Botmux 也会优雅等启动 banner 完全走完再宣布就绪，杜绝启动期“假就绪”。

### 3. 连续消息排队与 Steer 签名双重防护
在 IM 场景下，用户经常会在 Claude 正在思考时接连发消息（插话 / Steer，或者连续多条需求）：
- **忙态排队不抢跑**：借助 7501 的精准忙态，后续进入的消息会被安全归入 `queuedTypeAheadTurns` 排队队列，不会提前篡夺活跃会话的轮次 ID（Turn ID）；
- **发送侧原子推进与死锁解除**：当 Claude 处理完毕并调用 `botmux send` 交付最终回答时，Botmux 能够自动识别已完结的前序轮次，将 PID 标记原子推进到当前正在执行的排队轮次；
- **精准引用**：彻底根除“连续发 4 条消息，机器人回复 4 次却全都在引用第 1 条消息”的历史难题，让每一轮回复精准指向触发它的那条消息。

## 四、各 CLI 支持情况与版本门槛

只有适配器声明了 `supportsProgramStatus` 的 CLI，worker 才会在输出流上挂 `ProgramStatusFramingStream` 解析 7501；其它 CLI 的 7501 字节按普通输出处理。声明了版本门槛（`programStatusMinVersion`）的适配器，只在 daemon 探测到的安装版本不低于门槛时解析；版本未知、较旧、adopt 的既有窗格、RPC `--remote` 查看器一律走读屏，行为与接入前一致（`src/core/program-status-gate.ts`）。

| CLI | 版本门槛 | 探测握手 | 启动期报告 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| Claude Code | 无 | 发 `7501;?`，tmux 走 pane 内中继抢答（#1881） | 可信（配合启动横幅门控） | 最早接入（#1781） |
| Pi | 无 | 发 `7501;?` | 可信 | #1813 |
| Kimi Code | 无 | tmux 下不发，靠 `PI_PROGRAM_STATUS=1` 强制开启；报告包在 tmux 透传封套里 | 首条输入后先报 `clear`+`idle`，提交后须等到 busy（`programStatusSubmitAwaitsBusy`） | #2640、#2665 |
| oh-my-pi | 18.10 起才发（老版本自然走读屏） | 不发 | `init()` 时的 `idle` 早于输入框可用，启动期不信（`programStatusStartupIdleUntrusted`） | |
| Codex | **≥ 0.163.0** | 不发，无条件直发，tmux pipe-pane 直接收到 | **不信**：见下 | 0.163.0 引入（openai/codex#52725，idle/working/blocked），0.164.0 补 `done`/`error` 与 `kind=permission\|question\|auth`（#54114）；0.162.0 不发 |
| TraeX（traecli） | **≥ 0.214.1** | 不发 | 只作「输入框就绪」的旁证：见下 | 0.213.1 不发 |

### Codex / TraeX 的状态语义（真机录制）

报文均为裸 OSC、ST 终止、冒号分隔：`ESC ] 7501 ; state=working:app=codex ESC \`（TraeX 为 `app=traecli`）。在私有 tmux（pipe-pane）与 PTY 两种后端下录到的顺序（字节夹具见 `test/fixtures/program-status/codex-traex-osc7501.json`）：

- **启动**：Codex 在「临时输入框」（底栏还没画出、尚不接受输入，即 #3289 的画面）就报 `idle`，紧接着 `working` → `idle`；有慢 MCP server 时会一直 `working` 到 server 起来，而这期间输入框已经能接收并执行消息。TraeX 在输入框可用时报 `idle`（即使底栏只有快捷键提示、模型列表拉取卡住），MCP 启动期同样报 `working`；但恢复一个被别的进程占用的会话时，`idle` 和「会话被锁」页面在同一批输出里。信任、hooks 审核、登录页不发任何报告。
- **一轮对话**：第一个按键时先报 `idle`（确认上一轮的 `done`），再 `working` → `done`（Codex 0.163 为 `idle`）。审批弹窗报 `blocked:kind=permission`，批准后回到 `working`。在 MCP 启动期写入的首条消息不再报 `working`，只报该轮的 `done`。
- **不启动对话的命令**（`/status`、`/clear`、`/rename`）：不发任何报告。

botmux 据此的接法（`programStatusFollowsInputCycle` 等适配器开关，见 `src/adapters/cli/types.ts`）：

1. **启动期只记不用**：第一次写入前的报告不产生空闲/忙碌边沿，首条消息仍由各自的读屏门控放行（Codex 的空输入框判定 #3289、TraeX 的启动横幅/底栏判定）。第一个 `idle` 对 Codex 是假就绪，对 TraeX 可能紧跟着锁页。唯一的用处：TraeX 最近一次报告是 `idle` 且没有 Web 终端输入时，屏幕上的底栏即使是谓词不认识的新布局，也不再拦下首条消息等到 90 秒硬超时（#3307、#3338 那类）。报告只说明「没在跑一轮」，不说明输入框在屏上：此时渲染画面仍须有提示符行、且没有任何已知阻断页（会话锁、hooks 审核、迁移菜单）或由它们挂起的输入拦截，否则照旧由谓词判定——锁页上发出 prompt_ready 会让 daemon 把锁页卡片改成已完成、废掉它的重试按钮。放行时机仍是屏幕静默。
2. **每次写入后先交给读屏，直到 CLI 报 busy**：写入与 `working` 之间的 `idle` 是对上一轮的确认，忽略；`/status` 这类不报告的命令由屏幕静默收尾，不会卡住。CLI 一报 `working`/`blocked` 就接管：`blocked` 期间不结束本轮，`done`/`error` 立即结束。写入时 CLI 最近一次报告仍是 busy（输入排在进行中的工作后面，如 MCP 启动期的首条消息、运行中的追问），则直接以该状态接管，等这轮的 `done`。
3. **审批期间不插队**：CLI 报 `blocked` 时，排队消息不再以 type-ahead 方式写入——审批框里的 Enter 会选中默认项（「Yes, proceed」），等这轮 `done` 后再写入（`programStatusBlockedHoldsInput`）。`kind=question` 不拦：下一条消息就是它的回答，拦到本轮结束会自己等自己，维持接入前的写入方式。
4. **会话记录的终态优先于悬挂的 `working`**：rollout 里的 `assistant_final` / `task_complete` 仍结束本轮，即使 `working` 没有等来终态（终态报告丢失、或 Codex 对活动 goal 保持 `working`）——这也是「信号中途丢了」的兜底；`blocked` 不被覆盖（`programStatusYieldsToTranscriptTerminal`）。报告和屏幕矛盾时：接管期间以报告为准（屏幕静默、提示符、忙碌页脚都不再单独决定空闲），其余时间以屏幕为准。

## 五、写在最后：给开发者的一句话

**大模型不仅需要聪明的 Prompt，更需要坚固的工程底座。**

Claude Code 引入 OSC 7501，标志着 AI CLI 正在从“纯文本的人机黑盒”走向“标准协议化的机器通信”。而 Botmux 在第一时间提供原生工业级适配，正是为了让团队在将 AI 引入企业微信、飞书、网页工作台等真实工作流时，拥有像原生终端一样稳定、即时、放心的开发体验。
