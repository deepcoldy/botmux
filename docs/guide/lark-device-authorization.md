# 飞书按需补授权

首次登录的默认 Scope 不变，不预先加入多维表格或未来可能用到的业务权限。用户执行任务遇到 `missing_scope` 后，Agent 先根据已确定的操作步骤和工具文档核对本任务所需权限，再通过现有 `botmux auth request --scope` 一次申请多个必要权限。不能只申请首个报错的权限、等待下一步失败后再发新链接，也不能为了减少点击而申请与当前任务无关的权限。

例如，任务需要先读多维表格字段、再查找和回读记录，补授权可一次请求：

```bash
botmux auth request --scope "base:field:read base:record:read" --json
```

只读取字段的任务不应附加记录权限；只读任务不申请创建、编辑或删除权限。同一操作返回的多个候选权限是任选其一，不是全部申请。两项 Base 读取权限进入用户 Scope 目录，避免合法的合并请求被误判为 `unknown_scopes`。

Agent 向当前用户说明用途和权限，发送返回的 `authUrl`，再使用 `botmux auth wait --request-id <requestId> --json` 等待。只有返回 `ready` 才重试原操作。补授权保留同一应用、同一用户已有的权限，并检查新申请的权限均已获批；不借用其他人的登录态。签发应用需要先开通这些用户权限，用户仍须本人同意。应用权限缺失、资源无访问权或网络错误不能通过循环登录解决。

设备授权依赖同一个设备码完成。Botmux 对 lark-cli 的单次等待上限是 30 秒；本地等待超时、网络错误或未知失败不证明设备码失效，应保留尚在有效期内的请求。只有明确的授权拒绝、设备码无效或过期才清除请求。未取得授权时仍拒绝操作。

本次不改变默认登录权限、bytedcli 登录、群内对话额度或管理员权限。上述任务权限判断由 Agent 按实际操作完成，授权接口只接收显式 Scope，不自动扩展权限。源码测试不替代目标环境中新用户按需补授权、恢复查询和回复的完整验收。
