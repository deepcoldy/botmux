# 跨机器人派发的用户身份委托

状态：Proposed（随实现 PR 评审）

## 问题与决定

多人鉴权按当前消息发送者解析个人凭据。机器人派发消息的发送者是机器人，不能据此识别原用户，也不能借用 session owner 或最近一个真人的登录态。

在同一 Botmux 部署的 `botmux dispatch --bot-app` 链路中，由来源 daemon 为实际发送的派发消息签署用户委托。沿用现有派发、回报和 CLI 身份发布模块，不建立独立授权服务，不在提示词或 CLI 参数中接受执行用户。

## 当前实现

1. CLI 通过受认证的 `/api/dispatch-user/deliver` 让来源 daemon 发送简报。新话题和 `--into` 共用此入口，`--standby` 的后续激活以激活时的真实回合身份为准。
   完整 UTF-8 JSON 请求（含路由字段和编码后的简报）上限为 64 KiB，超限返回 HTTP 413 / `dispatch_body_too_large`。没有应用目标或来源未启用工具鉴权的派发保留原认证、路由和策略检查，但不解析或读取委托身份。话题归属查询失败返回 502；查询成功但没有群信息或群不匹配才返回 403，不把暂时无法校验误报成跨群派发。
2. 来源 daemon 从当前 managed turn 对应的真人记录取得身份；恢复场景只接受该回合明确标记为真人的发送者。已有签名委托可继续向下派发，但每一跳重新检查当前目标的用户访问权限，并且只能收窄允许的工具。
3. `dispatch-user-delegations.json` 保存签名记录：来源应用、session、turn、原用户的应用身份和 union_id、目标应用列表、群、话题根以及实际发送的消息 ID。没有 token、登录链接或密钥。签名使用既有宿主回报绑定密钥及独立协议域。
4. 消息可能早于发送响应到达目标。发送前写入不授予权限的 pending 记录；接收端最多等待 5 秒取得消息 ID 的签名绑定。发送失败清除 pending；崩溃、超时、伪造或存储异常均不获得用户身份，也不自动重发任务。
5. 目标 daemon 必须验证签名、消息 ID、目标应用、群和话题，再把 union_id 解析为目标应用的 open_id，检查目标对话权限和实际群成员关系。原用户不在目标群时拒绝，不能通过机器人在群内这一事实扩大人的可见范围。
6. ByteCloud 和 lark-cli 设备登录沿用原用户现有个人登录存储引用，每次执行重新解析有效凭据，不复制登录状态。ByteCloud 登录状态以原用户独立目录中 `bytedcli auth status --json` 的个人登录结果为准，不依据 CLI/SDK 私有凭据文件名判断；查询失败、未登录或应用身份均拒绝。旧的飞书应用 OAuth 仅接受目标应用自己的用户 token，不把来源应用 token 当作目标应用授权。
   设备登录固定查询签发应用视角的原用户目录；即使该用户在目标应用下另有设备登录，也不隐式切换目录。旧应用 OAuth 的授权本身绑定应用，因此只查询目标应用下的用户授权。
7. 凭据仍绑定具体 turn。后来的人类消息、普通机器人互相 @、定时任务和无身份的自动触发不继承委托。恢复与重试仅在保留原消息和话题的准确绑定时继续使用委托。
8. 缺少目标应用的用户授权时，工具拒绝执行，并提示目标 Agent 通过 `botmux auth request` 为已验证的原请求者申请本次所需权限。授权链接绑定目标应用及其视角下的原用户，Agent 可在当前任务话题将链接提供给该真人，等待授权后重试；同一真人的后续回合可以完成等待，另一人的回合不能取得该请求结果或凭据。不会给派发机器人创建登录挑战，也不会回退到机器或 owner 身份。权限不匹配、授权失败或授权撤销时，通过该任务的 `botmux report --dispatch-root` 回报阻塞。
   目标访问拒绝、成员校验不可用（包括超过现有 2000 人分页上限）与个人未登录分别提示；校验不可用不要求重新登录。已被当前回合或精确恢复记录确证为真人的消息不查询委托存储，委托存储损坏只阻断需要从中取得身份的路径。

9. `botmux send --mention <同机 Bot>` 交接同样附带委托（来源 Bot 的 `triggerUserAuth.delegateOnMention`，默认开，Dashboard「按触发人鉴权」里可关）。消息由 CLI 自己发出，所以分两步：发送前 CLI 调 `/api/dispatch-user/mention-prepare`，只传目标 Bot 的应用 ID 和群；来源 daemon 在当前回合是真人直接触发，或本回合已带有经验证的委托时写 pending 记录（定时任务、不带委托的机器人消息都不算）；后一种与 `botmux dispatch` 一致，按当前群重新检查原用户的访问权限，只能收窄工具，否则主编排收到一个 Bot 的回报后再 @ 下一个 Bot，原用户身份就会断掉，目标限本机已配置的其它 Bot、限本会话所在群。发送后 CLI 调 `/api/dispatch-user/mention-bind`，daemon 向飞书取回这条消息，确认是本 Bot 在发送前登记之后发到该群的，才把记录绑定到这个消息 ID；校验不过或发送失败都撤销登记。交接消息可能在普通群顶层、引用回复或话题里，所以这类记录不写话题根，只绑定精确的消息 ID；`botmux dispatch` 的记录仍要求话题根一致。任何一步不成，消息照常发出，只是接收方这一轮没有委托身份。正文里写的 `@Bot`（被注入成真正 @ 的那种）与 `--mention` 同样算交接目标。交接被拒时，接收方提示里的 `--dispatch-root` 指向这条交接消息本身；它在 dispatch 回报登记里没有条目，`botmux report` 会按「未送达主编排」的公告发到群里，而不是回到发起方会话。
10. 接收方每次按委托发布身份时记一条 `[dispatch-user:audit] receive`（来源 Bot、目标 Bot、union_id、会话、回合、工具、结果）；来源 daemon 在登记和绑定时各记一条 `mention-prepare` / `mention-bind`，不签委托时记一条 `mention-prepare skipped` 及原因。其中本轮确为真人直连、但本 Bot 策略对该目标签不出任何工具时记 `no_delegatable_tool`，与本轮根本没有真人直连的 `no_direct_human` 区分，避免排查审计日志时把「无工具可签」误读成「非真人发起」。

### 指定目标的派发专用工具权限

来源 Bot 可在 `triggerUserAuth.dispatchOnly` 配置 `tools`、`targetAppIds` 和 `chatIds`。这份工具权限仅在当前真人直接发起、来源群等于目标群、目标应用全部在白名单中，且本轮没有继承委托时，加入 `botmux dispatch` 或同机 `botmux send --mention` 的签名；配置缺失或任一条件不满足时不增加权限。策略启用时字段必须完整且使用精确应用 ID / 群 ID，非法配置拒绝加载；策略为 `enabled:false` 时该字段被接受但忽略、不参与加载校验，便于把 `enabled` 当手动总开关，而不会让一个 Bot 的编辑在下次启动时拖垮整份 bots.json。`--mention` 的白名单按过滤掉非本机 Bot 之后、实际接收签名的目标判定：同一条消息里一个不在本机的 @ 目标，不会否决命中白名单的本机目标。

`dispatchOnly` 不改变来源 Bot 自己的 CLI 身份、定时任务的运行 scope 或机器人回合。自动附加的定时授权不得覆盖这份真人即时委派；显式请求定时授权仍遵循原授权规则。目标 Bot 仍逐项验证签名、真人访问权限、群成员关系，并按目标 Bot 自己的 `triggerUserAuth` 获取该人的凭据。部署新配置前须确认 Botmux 的 `capabilities --json` 包含 `dispatch_only_user_auth_v1`；旧版本不会执行这条派发规则。

白名单只约束来源 Bot 自己发出的第一跳。目标 Bot 在后续机器人回合里把这份委托再转给第三方时，走的是既有「继承只能收窄」规则：按目标 Bot 自己的 `tools` 过滤，不再回头校验来源 Bot 的 `targetAppIds` / `chatIds`。因此「未列入白名单的目标不能获得额外权限」只对第一跳成立；第二跳及以后，第三方拿到的只是上游已签、并经每一跳收窄后的工具集，不会比本改动之前更宽。

与定时授权的边界：自动附加的 `schedule:create` 不得覆盖非管理员真人的这份即时委派，管理员本人的定时权限可与其共存。但定时运行 scope 的可用性校验只看来源 Bot 的基础 `tools`、不看 `dispatchOnly.tools`；所以按推荐的 `tools: []` 配置、又同时命中宿主 `runScopes`（如 bytedcli）与默认定时授权时，管理员派发会收到 `schedule_delegation_source_run_scope_unavailable`，需要带 `--no-delegate schedule:create` 才能派发——这种情况下 dispatchOnly 工具仍照常签名。

## 边界与取舍

- 双方须使用同一部署的数据目录和宿主信任域，并开启相应工具的 `triggerUserAuth`。跨机器派发和跨机器的 `--mention` 交接、旧的仅 `--bot open_id` 派发没有这份委托。
- 普通 report 回到父会话仍是现有合成触发，不因此获得个人权限；本次委托只附着于 daemon 实际发送的 dispatch 消息，不把整个话题升级为永久个人会话。
- 不修改 CLI/backend 实现或改变沙箱隔离保证。macOS、Linux 使用相同的宿主 IPC、文件锁和签名格式；TCE 无沙箱时仍依赖既有宿主进程信任边界。
- 本地代码和测试通过不等于已部署、已通过真实飞书/OAuth/Codebase 操作验收。PR 不变更运行中 fleet、TCC、发布版本或平台权限。

Codex RPC 模式由 app-server 执行工具，必须在其启动和首轮提交之前安装与普通 CLI 相同的按人 wrapper、登录 shell 路径和 Git 凭据辅助程序；只配置终端 viewer 不构成鉴权。进程环境只携带本会话定位信息，凭据仍由 wrapper 每次调用按当前回合读取。

## 验证

- 真实来源 IPC handler：隔离 CLI capability、宿主 HMAC 信任、伪造用户字段、过期 capability、跨群根消息、身份解析期间换回合、多跳派发。
- 签名与持久化：消息复制、目标/群/话题改写、双用户并发、发送先于响应、发送失败、同消息重试。
- 真实目标身份发布函数：普通群折叠会话与话题会话、跨应用映射、目标权限/成员缺失、原用户凭据使用及撤销、旧 OAuth 应用边界、后续用户不继承身份。
- 原有 dispatch 回执、report 绑定、IPC 权限和 shell 身份封装回归。
