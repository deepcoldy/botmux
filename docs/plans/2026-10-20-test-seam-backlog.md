    - 超时语义要统一：四份里前三份（strict-env-worker、session-env-worker、credential-only-send-authority）是**同步函数 + 超时返回 null**（`spawnSync('sleep')` 阻塞轮询），第四份 zmx 与 `pid-file.ts` 是 async + 到点抛错。公共件先选定一种（建议 async + 抛错，对齐 pid-file.ts / zmx），各调用点跟着改。
  - **helper 形态约束**：落在 `test/helpers/wait-for-json.ts`，纯手写 deadline 循环，参照 `test/helpers/pid-file.ts` 的 `readPidFile` / `waitForPidFile`：`readJsonFile<T>(path): T | undefined`（ENOENT / 空文件 / 半截 JSON 一律返回 undefined 表示未就绪），`waitForJson<T>(path, { timeoutMs, intervalMs, diagnostics })` 到点抛错。**禁止用 `expect.poll`**：它是 vitest-only API，`bun test` 下为 undefined，会在任何断言之前以 `expect.poll is not a function` 死掉（反向指针：`test/worker-kimi-effort.integration.test.ts:46-51` 与 `test/worker-tmux-pane-launch.integration.test.ts:71` 的注释）。
  - **超时必须保留调用点现场日志**：两个 JSON 调用点现在靠 null 返回值把 worker 的 stdout+stderr 挂到断言上（`strict-env-worker.integration.test.ts:103-104` 与 `session-env-worker.integration.test.ts:108-109` 的 `expect(x, diagnostics).not.toBeNull()`，`diagnostics` 是 worker 输出累积）。改成抛错后若错误里只有 parse 错误与字节数，这条最有用的现场就丢了。因此 helper 接受可选 `diagnostics?: string | (() => string)` 并拼进超时错误（惰性函数形式避免每轮拼接）；或调用点显式 `try/catch` 后追加 logs。实现时不得静默降级这一诊断能力。同类的另一面：`credential-only-send-authority.test.ts:399 / 410` 现在是 `expect(waitForFile(...)).toBe(expected)` 的**断言失败**语义（失败时 dprint 出 expected/received 实际值），换成 zmx 式 reject 后失败分类会变成「超时异常」——这些调用点的抛错消息必须包含实际观测值（zmx 的 `last observed` 正好覆盖），否则会从带 expected/received 的断言失败退化成无信息超时。连带形态改动：`credential-only-send-authority.test.ts:356` 的用例体当前是非 async 的 `() => {...}`，在 399 / 410 行调用同步 `waitForFile`；换 async 公共件后该用例要加 `async` 并在两处加 `await`。
  - **语义边界**：单文件 JSON 无法区分「写到一半」与「写完了但内容非法」（参照 `test/helpers/read-json-lines.ts` 头注释原则：完整但非 JSON 是 fixture bug，必须抛）。因此超时错误必须带上最后一次 parse 错误与当前字节数（错误形态直接采用 zmx `waitForFileContent` 的 `last observed` 写法），保证真实 fixture 错误可诊断；并写死约束：**断言「文件内容非法」的用例不得使用这个 helper**，否则真实 fixture 错误会被吞成重试直到超时。
  - **验收**：7 个落点 + 四份现成实现所在文件（strict-env-worker、session-env-worker、credential-only-send-authority、zmx-backend-helpers），在 bun test 与 vitest 两个引擎下跑真实 worker / tmux / 容器链路通过；`scratch-credential-boundary.test.ts` 在本机 root 环境两引擎真跑（CI 非 root skip，按上条门控记录）；七份可选若一并收编，所在文件按同样的双引擎标准验证（均 in-leg，scratch-submount 同为 root 门控）；helper 自身两个变异——桩先建空文件、延迟再写完整 JSON → 用例必须绿；桩只建空文件、永不写完 → 必须在有界时间内变红且错误消息含 parse 错误、字节数与 diagnostics 现场。多轮 / 全量 / 竞态探针走 isolate-run。**zmx 文件的验收要单独标注门控**：`waitForFileContent` 的唯一调用用例是 `it.skipIf(!realFishShell)`（`zmx-backend-helpers.test.ts:43` 探测 `/bin/fish` 或 `/usr/bin/fish`，646 行门控、695 行调用），而 CI 的 ubuntu-latest 不预装 fish、ci.yml 只装 bubblewrap（91 / 200 行），该用例在 CI 上是 skip 而非真跑。注意该文件在 bun 腿**不**被 defer（`isDeferredFromBunLeg` 对它返回 false，bun:test 自带 `it.skipIf`），两个引擎都会执行该文件、skip 的唯一原因是 runner 缺 fish——因此本地有 fish 的环境（如本机 /bin/fish）两引擎都必须真跑、不能当成「反正 skip」；zmx 仅作为错误文案模板引用（读代码即可照做，不需要跑）；CI 验收时 runner 无 fish 就要显式记录这条 skip，或给公共 helper 的 zmx 形态另加一条不依赖 fish 的覆盖——「zmx 文件跑绿」不等于该路径被验证过。
