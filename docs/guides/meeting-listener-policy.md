# 会议监听输出策略与纪要分享

本配置不绑定群号、会议号或某个机器人。全局默认适用于本机后续创建的所有会议监听会话，Bot 可以覆盖单个字段；活动会议、恢复中的会议以及会后追问保留原会议的策略快照。修改配置不回放历史会议。

## 全局默认与 Bot 覆盖

在实际使用的全局 `config.json`（默认 `~/.botmux/config.json`，也支持 `BOTMUX_GLOBAL_CONFIG_FILE`）里合并以下字段，保留已有配置：

```json
{
  "vcMeetingAgent": {
    "listenerPolicy": {
      "rawMessages": false,
      "finalSummary": true,
      "allowSummarySharing": true
    }
  }
}
```

| 字段 | 未配置时 | 作用 |
|---|---|---|
| `rawMessages` | `true` | 是否向监听群发送字幕、聊天和原始活动事件。关闭不停止采集、修订、consumer 投递和游标推进。 |
| `finalSummary` | `false` | 对启用监听群回复的 consumer，在收到 final 批次并处理末批数据后要求一份完整纪要；不再按增量新颖性跳过。 |
| `allowSummarySharing` | `false` | 允许当前真人通过下面的精确指令授权一次纪要跨群分享。不允许字幕或自动回合决定外发目标。 |

在 `bots.json` 某个 Bot 的 `vcMeetingAgent.listenerPolicy` 中使用同名字段覆盖全局。例如 `{ "rawMessages": true }` 只恢复该 Bot 后续会议的原文同步，其余字段仍继承全局。字段须为布尔值；Bot/协议写入中的未知字段和错误类型被拒绝；全局文件读取遇到错误策略会告警，并关闭该策略的三个输出/分享标志，不影响其它全局设置。不会把字符串 `"false"` 当作开启。

这是高级配置入口；现有 Dashboard 的会议总开关和角色目录继续使用，没有新增一套逐群规则。

## 只同步关键结论，结束后汇总

`rawMessages: false` 只控制原文发布，不能代替 consumer 的选择。请通过已有共享角色目录 `vcMeetingAgent.consumerCatalog`（或 Dashboard 的共享会议角色预设）设置：

- `defaultMode: "agents"`；
- `defaultConsumerIds` 选择一个纪要角色，避免多个监听回复角色各自输出一份总结；
- 该角色 `responseMode: "listener_thread"`，使用 `meeting.read` 和 `listener.output.request` 能力；不需要会内语音/文字权限；
- 角色职责可配置为：

> 持续整理已确认决策、待办（负责人、截止时间）及未解决风险。只在出现新的关键结论、明确待办、风险或信息修正时输出简洁增量；其余保持静默。更新已有事项，不重复记录，不输出逐句字幕。

关键增量沿已有角色指令和语义判断处理，没有字数阈值、固定心跳或关键词打分。最终纪要由宿主 final 批次另外要求，包括决策、待办、未决问题和风险；缺失负责人/时间标为未明确，输入不完整时说明缺口。`silent` consumer、纯监听模式、旧版本 plain 协议的重试不会被自动改成可见输出。

最终批次沿原有 delivery/receipt、顺序处理和主消息去重流程，不新建定时器，不在 meeting-ended 事件刚到时提前忽略最后一批字幕。启用后 final 回答必须是 publish 信封，skip/畸形信封不会作为成功纪要展示。模型无法生成有效结果或输入流失败时应沿原有诊断/重试入口排查，不能把会议终态当作纪要已发布的证明；本功能不保证模型事实正确。

## 真人授权跨群分享

在关联的会议监听群中，单独发送文本消息（不要放在引用、转发、卡片或富文本里）：

```text
@你的机器人 会议纪要转发 oc_目标群ID
```

也支持 `@你的机器人 share meeting summary oc_目标群ID`。这里的 @ 必须是飞书真实提及，并仍受正常入口门禁约束。本次选择精确语法，而不是从自然语言、引文或字幕中猜测授权目标；多个会议存在歧义时，用 `@你的机器人 会议纪要转发 meeting:会议ID oc_目标群ID` 显式指定本场会议（也可用会议号）；沿原有机制消歧并再次核对引用，不任取一场。

宿主将当前人类消息、会议、成员代次和唯一目标群绑定到当前回合。Agent 根据现有会议上下文整理纪要，然后调用：

```bash
botmux vc-agent share-summary --content "纪要正文"
```

目标由宿主决定，CLI 不接受 `--chat-id` 改向，也不能从上一回合继承授权。普通 `botmux send --chat-id` 的会议隔离限制保持不变。此操作是群消息，不是会内聊天/语音；会议结束后仍可使用已保留的会议上下文。

发送前和限流队列真正发出消息前，都复核当前回合能力、会议归属和成员代次。机器人须已在目标群，发起人须仍属于来源群与目标群；无法核实、缺权限或平台拒绝时不发送，不自动申请权限、不拉人入群、不切换账号。

每条真人授权只允许一个目标和一个正文哈希，写入前保存 pending 回执；成功后重复调用返回同一 message ID，不重复发布。网络超时、进程中断或成功回执落盘失败属于**结果未知**，自动重试不会再次发送；先到目标群核对，确认没有发布后再发起新的真人指令。不要通过删回执强制重放。只有收到 `ok: true` 的回执才能告知用户已发送。

## 升级与验证边界

- 缺省配置保持原行为；既有会议不会因新默认值而突然静默、汇总或开放跨群权限。
- 全局默认变更只影响之后创建的会议；成员/receiver 恢复使用已冻结快照。
- 本实现不合入或启动任何本地 daemon；上线须走正常发布流程。
- 单元/集成测试用模拟 Lark 和隔离临时目录验证；真实会议、不同 CLI 的模型输出质量与真实群权限仍需发布前验收。
