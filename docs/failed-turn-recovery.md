# 外部看门狗的受控失败恢复

Botmux 提供失败恢复原语，外部管理员进程负责错误分类、轮询和退避。接口不自行安装或启用看门狗，也不改变普通对话、手动 `/retry` 或已有定时任务。

## 接口与身份

`controlled_failure_recovery_v1` 声明本构建包含这组能力；实际 daemon 是否可用仍须查询接口。以下接口仅接受既有宿主 IPC 鉴权，Worker capability、会话 Owner 和客户端自报的用户身份均不能授权恢复。

- `GET /api/sessions/:sessionId/failure-recovery`：返回最近失败的 `turnId`、`failedAt`、`originalTurnId`、`actorBound` 和恢复回执。不会返回任务正文、用户身份或凭据。
- `POST /api/sessions/:sessionId/failure-recovery`：请求必须恰好包含 `turnId`、`failedAt`、`requestId`、`mode`。`mode=retry` 使用原会话的准确输入；`mode=fresh` 确认旧进程关闭后，在原群和话题建立新的原生上下文，并重新装配 Runtime 输入。

```json
{"turnId":"om_example","failedAt":"2026-10-16T00:00:00.000Z","requestId":"watchdog-example","mode":"fresh"}
```

身份由 daemon 在真实失败终态或原生限流状态冻结。恢复只使用对应轮次已证实的真人／定时创建者，重新检查对话权限，并调用正常的每轮工具身份准备；工具执行时仍检查当前个人凭据与资源权限。定时创建者继续使用既有定时任务 authority，不升级为刚发送消息的真人。Owner 与发起人不同、没有身份快照、用户访问被撤销时，均不借用其他身份。非真人且不能证明原请求者的失败不自动恢复；升级前缺少快照的旧记录也不从 Owner 补齐。

原生 `limited` 帧只产生带 `limitedSnapshot` 的临时观察，不等于失败终态。CLI 离开限流状态或同一轮次成功完成后，未被认领的观察会失效；恢复接口在派发前还会重新检查实际限流状态，防止没有后续屏幕帧的自行恢复被重放。已经持久化恢复回执的记录保留，迟到的成功／失败终态不能抹掉派发栅栏；真实失败终态也不会因屏幕状态改变而被清除。

原轮次显式绑定到其他应用的身份会被拒绝，不能退回回复目标元数据来改写 App ID。回复目标的真人证据只有在原会话行归属与当前 Bot 一致时才可使用。

恢复派发使用独立 turn；同一逻辑任务的 `originalTurnId` 不变。看门狗应据此限制整个任务的恢复次数，而非按新 session 重新计数。新生 turn 的授权来源明确标记为恢复或定时创建者，不能借此取得要求刚发生真人操作的管理能力。

## 并发与回执

同一 Bot 的原生 mutation gate 串行化生命周期变更。新 IM 在等待 gate、关闭旧进程和准备工具身份期间到达时，会取消过期恢复；已有新输入、排队输入、运行中的任务或原生恢复同样拒绝重投。仅在最终同步检查通过后接受 Worker 输入。

在关闭或发送前先持久化 `attempting`。同一失败只接受一个请求；相同 `requestId` 重取回执，不重复派发。不同请求 ID、变化的失败引用或 mode 不可覆盖已有请求。关闭残留、崩溃或 IPC 结果不确定时保留 `dispatch_unknown`／`attempting`，不能通过换 ID 重试。

- `accepted`：Runtime 接受了恢复派发，不证明模型完成、工具成功或飞书最终回复。
- `cancelled`：新输入取消了旧恢复，不再提交原任务。
- `attempting`、`dispatch_unknown`：需要核对真实执行，禁止盲目重投。

远程 backend、adopt、退休工作区及专用 principal lane 不通过这个会重建本地生命周期的入口；普通会话的既有机制不变。新上下文保留原话题、工作区、冻结配置和任务输入，不复用损坏的 CLI resume ID。旧会话及回执保留供审计。

干净恢复的新会话会落盘原 Bot 的应用归属和话题路由，并与正常 fork 复用同一套启动配置继承：CLI 配置目录、模型后端变体、沙箱存储／路径／网络决策和工作区准入约束均保留；可变配置对象独立复制。既有 Owner 元数据和原任务发起人各自保留，不把 Owner 当成本轮工具使用者。

Codex CLI 恢复后的启动判断只使用底部空输入框及原生已初始化状态栏。自定义 `status_line` 省略目录和 Context 时，完整且唯一的 `thread-id` 也可证明初始化完成；截断、路径内或含歧义的 UUID、loading、容量等待和后续对话框不作为这项证据。这只解除启动等待，不构造新任务或任务完成事件，也不补造原始发起人身份。

## 验证边界

定向测试覆盖宿主 HTTP 鉴权、客户端身份注入拒绝、双用户／Owner 区分、限流快照、输入竞态、权限撤销、并发、重启后的回执和关闭残留。测试与构建不等于已经部署；真实模型、受保护工具和消息回执仍需在目标 Runtime 验收。

## 发布中断后的普通任务续跑

本地 tmux 的普通 Codex TUI 任务在原生会话确认收到了当前真人输入后，保存 `Session.deploymentContinuation`。记录只包含原 turn、原生会话 ID、发起人和 worker generation，不保存或重放原任务正文。输入必须具有明确的普通交互分类；durable-primary、带 attempt／at-most-once 的输入、adopt、RPC、专用 principal lane、共享工作区准入与其他持久任务所有者保持各自恢复协议。

重启时，仅当后端明确不存在、记录不超过一天、会话仍有效且原发起人仍有对话权限，才先持久化 `claimed` 再启动 worker。后端存活时只重连；探测不确定时不提交续跑。worker 必须恢复相同的原生会话，并从对应 transcript 确认仍有未完成工作，才发送现有的检查点续跑指令。身份使用原发起人，来源标记为 `failed_turn_recovery`；它不代表一条新的真人管理指令。已完成或原生中止的任务不再次执行，fresh fallback 不携带旧恢复指令。

检查点及人工取消使用同一执行身份：新的准入回合阻止旧执行回执；首个空闲提示撤销准入标记后，使用当前 worker 重新发布的 `managedTurnOrigin`，并尊重其中显式缺失的身份。冷恢复尚未发布实时身份时，仅允许匹配持久 `claimed` 的回复目标及原发起人。普通历史回复目标、仅含策略权限的 origin 都不能建立恢复权，话题首轮也不要求存在回复根。

新输入、停止和准确的终态撤销旧恢复权。原生透传、命令注入和卡片自定义输入都先在 daemon 持久取消，再由 worker 清除尚未投递的恢复指令；卡片输入仍等待 IPC 回执，发送失败时释放卡片处理标记。Web 终端输入也须先取得 daemon 的持久取消回执，才转发按键。普通元数据写不能复活旧记录；恢复等待资源与 worker IPC bootstrap 后重新检查认领是否仍有效。明确未派发的拒绝／异常释放认领；IPC 已尝试而结果不确定时保留 `claimed`，不跨重启盲目再次提交。原生确认接收续跑后回到 `running`，允许后续发布继续同一任务。

这条链路由 Botmux 自身的会话恢复驱动，不依赖外部看门狗伪造 `lastFailedTurn`。旧版本没有保存的发起人／原生接收证据不能补造。验证包含 SQLite 重载、撤销与迟到回执、恢复并发、真实 worker 配合隔离假 CLI；尚不能替代目标 Runtime 上的发布中断与真实业务交付验收。
