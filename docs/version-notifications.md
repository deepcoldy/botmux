# botmux 版本通知

Dashboard → 全局设置 → 自动维护中的 **新版私聊提醒** 默认关闭。飞书 `/dashboard settings` 设置卡中也可切换；沿用设置页和设置卡的管理员写权限。

对应配置为 `~/.botmux/config.json`：

```json
{
  "maintenance": {
    "notifyOnNewVersion": true
  }
}
```

它与 `autoUpdate`、`autoRestart`、`notifyOnRestart` 独立。打开提醒不要求打开自动更新；只查询版本、发送提醒。关闭时不查询版本、不写通知账本、不发送提醒。配置热读取，开关变更最迟在下一次一分钟扫描时生效；首次启动延迟 20 秒检查。

开启后，每小时检查一次当前安装方式对应的最新版：包管理器/源码安装使用 npm 配置的 registry 的 `latest`；发布资产安装先用公共源，失败时沿用 Dashboard 的镜像回退。只在最新版严格高于当前版本时提醒；领先于稳定版的 canary 不会被当作过期版本。源码安装沿用其 `package.json` 版本（通常为 `0.0.0`），因此提醒表示有正式发布版本，不表示源码工作树落后于某个提交。

通知由主 daemon（bot-0）通过主 bot 私聊它解析得到的 owner；不逐个通知其他 bot 或会话 owner。卡片包含当前版本、新版、发布说明链接和 Dashboard 入口。主 daemon 缺少 owner 时等待身份解析成功。

通知状态保存在 dataDir 的 `botmux-update-notify.json`，采用文件锁和持久化原子写。成功投递后保存已提醒版本，后续扫描及重启不会再次提醒该版本或更旧版本。查询失败或发送失败按五分钟窗口重试。投递准备时先保存 UUID；首次发送边界的守卫通过后、允许实际 POST 前，再持久化 `egressStartedAt`。如果守卫在首次请求前取消，本轮新建且没有该标记的 pending 会回滚，之后重新开启仍能提醒同一版本；标记落盘后即使在 POST 前崩溃，也按可能已经发送处理，重启继续沿用原 UUID。升级前留下的无标记 pending 以及其它预存记录一律保守视为可能已经发送，仍从 `createdAt` 计算截止窗口，首次补写标记也保留这个原始起点，不会因升级或混合版本运行而延长去重窗口、重复投递。发送响应丢失或发送后保存状态失败时，重试同样沿用 UUID，飞书在其一小时去重窗口内不会产生重复消息。未知投递自 `egressStartedAt` 起 55 分钟仍未成功落账时，会保留 pending 并停止该版本的自动重发，记录 `automatic retry suspended`；避免超出飞书去重窗口后重复发送。可从日志和账本核对投递结果，后续更高版本仍能提醒。损坏或无法读取的账本保持原样并记录错误，避免静默丢掉去重记录。

提醒在版本查询后和实际发送前再次核对开关、owner 和当前版本；限流等待期间关闭提醒、变更 owner 或已经升级，尚未执行的发送会停止。已经提交给飞书的请求按其最终响应落账。

“botmux 维护通知”仍由 `notifyOnRestart` 控制，表示完成更新/回滚或主动重启后的报告。新版提醒表示尚未升级时发现新版本，两者使用独立开关。
